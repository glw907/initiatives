### Commands in a worktree

The worktree guard refuses a compound shell command, an inline `PATH=... setsid`, and a `git -C`
into another worktree. Both earlier passes lost rewrites to it, and the docs friction executor
used small wrapper scripts kept outside the repo. So:

- Every command in this plan is one plain command run from the directory it acts on: a `cd <dir>`
  on its own, then each command on its own. No `&&`, no `;`, no inline environment assignment, and
  no `git -C` into a worktree, in any task or subagent prompt.
- Every throwaway instance runs through the wrapper scripts T0 writes (call 19), which set the
  environment themselves.
- A subagent's Bash calls do not keep a `cd`, so a subagent writes every path absolute and runs
  the gate as `bash <its worktree>/scripts/gate.sh`, which does its own `cd`.
- Every subagent dispatch runs from the pass worktree, since `isolation: "worktree"` cuts the new
  worktree from the session's current directory.

3. **#31: `collect` after a withdraw, and the race windows.** The command lives in
   `bin/.local/bin/approval-queue`; the app half in `src/lib/server/items.ts` and the item route.
   - The wait loop (`while [ ! -e "$item/decision.json" ] && { [ -n "$collecting" ] || [ ! -e
     "$item/deferred.json" ]; }`) also ends when `item.json` is gone. After the loop, a
     `decision.json` wins as today; otherwise, with `item.json` gone, the command prints
     `approval-queue: <id> was withdrawn; nothing to collect` on stderr, nothing on stdout, and
     exits 1. The queuing command takes the same branch, though a live waiter normally leaves by
     TERM first.
   - Item removal goes through one function, `retire_item <dir>`, defined beside `proc_running`
     above the `withdraw` branch so every caller can reach it: rename `item.json` to
     `item.json.gone`; if `decision.json` exists then, rename it back and return 1; otherwise remove
     `item.json.gone` and `item.json.tmp`. A `rename` is atomic, so a decision that landed before
     the rename is seen and kept.
   - The queuing command's EXIT trap keeps today's guards and never fails:
     `[ -e "$item/decision.json" ] || [ -e "$item/deferred.json" ] || retire_item "$item" || true`,
     with its cleanup (`check_body`, `check_err`, `fetch`) run unconditionally. Probed by the
     reviewer: under `set -euo pipefail` a failing last command in an EXIT trap aborts the trap and
     turns the exit status to 1, so the `|| true` and the guard order matter.
   - `withdraw` on a dead or deferred waiter calls `retire_item` and exits 1 with "decided while
     withdrawing; run collect" when it fails. On a live waiter it sends TERM, then waits up to 5
     seconds, polling every 0.1 seconds, for the waiter to exit (`proc_running "$wpid" "$wstart"`
     false), never for `item.json` to vanish, since `retire_item`'s rename makes it vanish briefly.
     Then it decides by the files: no `item.json` exits 0; a `decision.json` gives "decided while
     withdrawing; run collect" and exit 1; a `deferred.json` (a defer that landed in the same
     instant, so the trap kept `item.json`) is retired by `withdraw` itself, exit 0; anything else
     gives today's "still queued after its command was told to stop" and exit 1.
   - The app re-checks after it writes: `writeDecision` and `writeDecisionOnce` look for
     `item.json` once `decision.json` is in place, and when it is gone they unlink their
     `decision.json` and report the item gone. The route's `gone(request)` cannot answer here,
     since every action has already read the form before `decide` runs and a second read gives
     null. So `decide` and `decideOnce` take a `packet` flag from their callers (the parsed form
     has `fingerprint`, the test `gone()` makes) and return
     `fail(410, { message: 'This item was withdrawn by its session; nothing was recorded', board: '/' })`
     for a packet, else a 404, as `gone()` answers today. Together the two sides leave no decision
     written beside a removed `item.json`. In the narrow case where both back off, the item stays
     on the board with no decision and Geoff's page says it was withdrawn; nothing is lost, and the
     PR names this case.
   - `check_body` and `check_err` are assigned before the EXIT traps are set, so a TERM in that
     window no longer hits an unbound variable under `set -u`.
   - Tests that fail on `dbe553b`, each wait bounded as `finish()` bounds it:
     - `tests/lifecycle.test.sh`: a `collect` on a deferred item exits 1 with the withdrawn message
       after a `withdraw`, and so does a `collect` on an undecided item whose recorded pid is dead
       (`fake_item` with an exited pid).
     - `items.test.ts`: `writeDecision` and `writeDecisionOnce` on a directory with no `item.json`
       leave no `decision.json` and report gone; the route test covers a packet post answering 410.
   - A regression guard, labelled so in the test and the commit: TERM after `decision.json`
     lands leaves `item.json` in place (today's trap already does this). The instant windows are
     not deterministic in a test; R1's task-scope read covers them, naming both: the trap's
     check-then-remove and `withdraw`'s wait after TERM.

5. **#33: the traced cause.** The planning session reproduced it. The lifecycle test's first
   `queue_design` leaves `$state/tab.seen` about a second old. The defer case's command then sees
   a `tab.seen` younger than 5 seconds and waits up to 5 seconds for a poll newer than
   `item.json` (the command's `for _ in $(seq 50)` loop under "One tab serves the whole queue"),
   which never comes, before it reaches its wait loop. `finish` allows 5 seconds. Timed: the
