### What Cloudflare documents (all fetched 2026-11-07)
- Template URL (https://developers.cloudflare.com/fundamentals/api/how-to/account-owned-token-template/): user token `https://dash.cloudflare.com/profile/api-tokens?permissionGroupKeys=[{key,type}]&accountId=*&zoneId=all&name=`; account token `https://dash.cloudflare.com/?to=/:account/api-tokens&permissionGroupKeys=...&name=`. Parameters documented: permissionGroupKeys, accountId, zoneId, name. NO expiry/TTL parameter documented. User-token keys must be short keys and type `edit`; unmatched entries are silently dropped (matches prefill.mjs header). Account-token keys may be permission-group IDs. Account URLs do not take accountId/zoneId.
- Minting by API (https://developers.cloudflare.com/fundamentals/api/how-to/create-via-api/): `POST /user/tokens` (user) or `POST /accounts/{id}/tokens` (account); body `name`, `policies[{effect, resources, permission_groups[{id}]}]`, optional `not_before`, `expires_on`, `condition.request_ip`. One zone is `"com.cloudflare.api.account.zone.<ZONE_ID>": "*"`. Secret shown once. The required bootstrap permission is `User > API Tokens > Edit`, which exists ONLY in the "Create additional tokens" template ("not available in any other template or in the Custom Token builder"); the docs warn such a token "can create tokens with access to any of a user's resources". Permission-group list needs API Tokens Read/Write.
- Account-owned creation needs Account API Tokens Edit and the new token may only be a subset of the creator's account permissions (https://developers.cloudflare.com/fundamentals/api/troubleshooting/, via search).
- Workstation evidence of the mint pattern (cloudflare-estate-inventory.md, "API token scheme" rule 6): Geoff creates `tmp-token-setup` from the "Create Additional Tokens" template with nothing added and a TTL ending tomorrow, and it works; Cloudflare refuses a user and an account token minting each other ("sub-token is not allowed to have permissions to manage other tokens", error 1001, 2026-10-18); a token that verifies active but answers 9109 on token endpoints had a wrong TTL start date.
- `GET /user/tokens/verify` returns `id`, `status` (active/disabled/expired), `expires_on`, `not_before` (https://developers.cloudflare.com/api/resources/user/subresources/tokens/methods/verify/). The estate file notes `accounts/{id}/tokens/verify` answers 1000 for a user token; use the user path (prefill.mjs `verifyBuildToken` does).
- DELETE `/user/tokens/{id}` needs API Tokens Write; docs do not say whether a token may delete itself. UNCONFIRMED.
- Third-party OAuth: Cloudflare has an end-user consent screen and a "Manage OAuth authorizations" page (https://developers.cloudflare.com/fundamentals/oauth/authorizing-an-application/), but NO documented way for a third party to register a client, and no scope list. I found none. So the Go tool cannot have its own Cloudflare OAuth app. (The cairn tool at tool/internal/providers/cloudflare.go uses a pasted bearer credential.)
- Wrangler (https://developers.cloudflare.com/workers/wrangler/commands/general/): `wrangler login` flags `--browser=false` (print link), `--scopes`, `--callback-host`, `--callback-port` (default 8976), `--device` (RFC 8628 device grant, no localhost callback; polls up to 5 min, cli.js:133452). Credentials in `~/.config/.wrangler/config/default.toml` (plaintext) or an encrypted file with `--use-keyring`; fields oauth_token, refresh_token, expiration_time, scopes (cli.js:130446). `wrangler auth token [--json]` prints the active credential in order CLOUDFLARE_API_TOKEN, API key+email, then the OAuth token (auto-refreshed); I did not find it in the local wrangler 4.156.2 via grep, so UNCONFIRMED which version added it. Wrangler profiles (beta, 2026-07-02: `wrangler auth create/activate`, https://developers.cloudflare.com/workers/wrangler/profiles/) resolve CLOUDFLARE_API_TOKEN first, then `--profile`, then the directory profile, then the default login.
- Wrangler honors `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` (https://developers.cloudflare.com/workers/wrangler/system-environment-variables/). The present code already relies on this for the account id (exec.mjs:361).

## 3. The 2-minute wrangler OAuth timeout
Cause, verified in the installed wrangler 4.156.2 (examples/showcase/node_modules/wrangler/wrangler-dist/cli.js:131354-131363): `getOauthToken` starts a `setTimeout(..., 12e4)` when it begins, and on expiry closes the local server and rejects with `UserError("Timed out waiting for authorization code, please try again.")`. The callback is fixed at `http://localhost:8976/oauth/callback` (cli.js:135514), listening on 8976 (210163 is a different, pipelines flow). The timer is a hard cap on the whole browser round trip including Cloudflare sign-in, account choice, and consent, and wrangler prints nothing about the budget. A workers-sdk changelog notes the 120 s was also the fallback when the callback returned an error other than access_denied and wrangler never answered the browser (since fixed to surface invalid_scope etc.). Device flow (`--device`) polls up to 300 s (cli.js:133452, docs say 5 minutes).

Can a Go setup avoid `wrangler login`? Yes. wrangler reads `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` and needs no login then; deploy needs Workers Scripts Edit + D1 Edit + R2 Edit; with the account id given, no membership lookup is needed (UNCONFIRMED for every subcommand the tool uses; the d1 execute / secret put / deployments list / r2 bucket info calls should be probed once with a token-only environment). If a live session is wanted anyway: run `wrangler login --device` (5 min, no localhost listener) or, for the callback flow, start the browser immediately and show a 120 s countdown.

## 4. What can be checked up front (before the unattended stretch)
With the bootstrap/minted token and no state change, all by GET:
- Token health: `GET /user/tokens/verify` (status, expires_on) for every token; abort if expiry is shorter than the expected run, or absent for the bootstrap.
- Permission coverage: `GET /user/tokens/{id}` (needs API Tokens Read; the bootstrap has it) to read the policies and compare to the required list; a read cannot prove a write permission (prefill.mjs header). For the minted tokens the tool wrote the policy itself, so coverage is known by construction. Resolve every permission-group name to an id up front (names have drifted, e.g. Workers CI vs Workers Builds Configuration); fail the opening on a missing name.
- Account: `GET /accounts` (needs Account Settings Read) and pick the id; this replaces `wrangler whoami`.
- Name clashes: `GET /accounts/{id}/workers/scripts` (also gives `created_on`; this is the #367 fix source), `GET /accounts/{id}/d1/database?name=`, `GET /accounts/{id}/r2/buckets/{name}`. Same logic as deploy.mjs:387-469 without wrangler.
- workers.dev subdomain: `GET /accounts/{id}/workers/subdomain` (documented, https://developers.cloudflare.com/api/resources/workers/subresources/subdomains/); if missing, `PUT` creates it (a tiny write, no dashboard). Replaces the `subdomain-unregistered` dashboard step (catalogue.mjs:143-152). Permission not stated in docs; UNCONFIRMED.

## Browser-step floor (owner request)

### Existing local credentials: can they be detected and reused?
- `CLOUDFLARE_API_TOKEN` in the environment: detectable (wrangler honors it, deploy.mjs:44-49; `wrangler auth token --json` ranks it first). It is reusable only if it carries what setup needs. Reads prove read scope only (prefill.mjs:15-21). If the token can read its own policy (`GET /user/tokens/{id}` needs API Tokens Read), coverage is checkable; if not, it is a guess. On this workstation the env token is `ws-admin`: it has Workers/D1/R2/DNS/Zone/Email Sending but no Workers Builds and no API-token management (cloudflare-estate-inventory.md), so it covers site deploy and domain, not Builds. Policy: reuse when coverage is proven; otherwise offer to mint a narrow token (below) or fall back to 1 visit. Reusing an owner's broad admin token for a one-time run is also a least-privilege smell; prefer minting.
- A live `wrangler login` session: detectable (`wrangler whoami --json`, `wrangler auth token --json`, or `~/.config/.wrangler/config/default.toml` fields `oauth_token`, `expiration_time`, `scopes`; encrypted if `--use-keyring`). It auto-refreshes. Its scopes (list in section 2) cover deploy, D1, secrets, email_sending, but not zone edit, DNS, or Workers Builds, so it can replace only chapter 1's `wrangler login`. It cannot lift the floor on its own for a site with a domain and Builds.
- Prior setup's retained token (new): if setup stores `cairn-setup` in the OS keyring (the Go tool already depends on `github.com/zalando/go-keyring`, tool/go.mod), the next run can verify it and skip everything.

### Single bootstrap that mints the rest
Yes, per the docs: a user token with `API Tokens Edit` (only obtainable from the "Create additional tokens" template) can create user tokens with any of the user's resources (create-via-api page), including `expires_on` and per-zone resources, via `POST /user/tokens`. That is exactly how Geoff provisions tokens today (estate file rule 6). Mint from it: `cairn-setup` (short expiry, account-scoped, deploy + zone/DNS/SSL/email + Workers CI) and `cairn-build` (account-scoped, no expiry). Both are user-owned, which Builds requires. Because the template URL has no expiry parameter and, per the docs, the `API Tokens Edit` group is not offered by the custom builder, UNCONFIRMED whether `permissionGroupKeys=[{"key":"api_tokens","type":"edit"}]` pre-fills it on the user URL. Test it once (a silent empty "Select..." control is the failure signal, prefill.mjs:7-14). If it does not pre-fill, the owner clicks Create Token, then "Use template" on Create additional tokens, then sets an expiry: still one visit, but the tool cannot pre-fill the expiry and must enforce it by reading `expires_on` from verify.
Alternative with the same visit count: keep today's single fully-prefilled token (no minting) with `zoneId=<id>` instead of `all`; but there is no expiry parameter and the Builds token is still a second page. The mint design dominates because expiry and the build token need no second page.
