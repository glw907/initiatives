## 1. Core inventory

### bin.mjs (782 lines): the router
Order of a run (bin.mjs:412-780): parseArgs (strict; bad flag -> message + "Next step" + exit 1, :415-420) -> `--version` prints package.json version (:422) -> runPreflight, prints `[ok|fail] check: remedy`, first failure exits 1 (:428-436) -> resume lookup -> cost preamble -> branch ladder -> else fresh path (collectAnswers, scaffold, hand-over text, GitHub chapter, Cloudflare chapter, chapter 2 domain/email, chapter 3 Builds).
- Resume lookup is `findSiteByDir(flags.dir)` and happens ONLY when `--dir` was passed and not `--dry-run` (:445). An interactive rerun with no `--dir` takes the fresh path: it re-asks every question, then `scaffold` refuses with "already exists and is not empty" (scaffold.mjs:289-294). This is the resume's core weakness: identity is the directory, supplied on the command line.
- Branch ladder after lookup (each prints a next step before stopping):
  1. `--start-over` refuses at chapter-2 steps (zone/records/delegated/domain-live/email-onboarded/email-live/email-declined) and chapter-3 steps (:453-487), because real Cloudflare/Workers Builds resources hang off the record; otherwise `retireSite` (:489-493).
  2. `--connect` (:495-533) enters chapter 3 from any step at/after `live`; refuses earlier with a next step. If Builds is already connected and chapter 2 is mid-way it resumes chapter 2 instead.
  3. Chapter-2 terminal steps (`email-live`, the recorded decline): `--sign-in` reseeds and opens the confirm page (:540-553); `email-live` prints the closing block and stops (:556); a decline re-enters chapter 2 so the owner can opt in later (:567-575, fix 2cba39ebf).
  4. `live`: prints "already live", `--sign-in` shortcut, else continue into chapter 2 (:578-602).
  5. Chapter-2 steps `zone-created, records-carried, delegated, domain-live, email-onboarded` -> chapter 2 (:604-614).
  6. Chapter-3 resumable steps `builds-connected, config-reconciled` -> chapter 3 (:621-644). Chapter-3 terminals `builds-live, builds-connect-declined` print the closing block, but reopen chapter 2 when an email decline is open or no domain is connected (:655-687).
  7. GitHub/Cloudflare-1 resumable steps `scaffolded, app-created, awaiting-org-approval, installed, repo-created, pushed, deployed` (:689-730). Prints "Resuming <name> at <step>" with a note naming any of `--org --repo-name --app-name --owner-email` that overrides a saved answer. Steps `pushed`/`deployed` skip the GitHub chapter entirely.
- Closing blocks: `printLiveInfo`, `printEmailLiveInfo`, `printDeclinedInfo`, `printBuildsChapterInfo` share `closingInfoLines` (repo URL, App URL, installation-settings URL, `cairn doctor` install hint `go install github.com/glw907/cairn-cms/tool/v2/cmd/cairn@latest`, :84-99) and `publishLine` (says whether Builds deploys a publish, :107-116).
- `--sign-in` (`reseedAndOpen`, :351-381) guards: needs a saved `ownerEmail` (or `--owner-email`), a saved `cloudflare.url`, and a saved `cloudflare.accountId` (else wrangler would seed a default account), each failing loud with a "Next step". It then `openBrowser(url+confirmPath, {secret:true})`.
- Failure path (:769-779): prints message; adds a generic "Next step" only if the error carries no `catalogue` and no "Next" text; exit 1. Success paths return (no `process.exit(0)`, so piped stdout flushes).

## 2. Node tooling dependence; #365

Where the scaffold shells out to Node tooling (a Go binary still must run these or replace them):
- `npm install` in the new site (cloudflare/deploy.mjs:68, `runNpm(['install'])`, skipped if `node_modules` exists) and `npm run build` (deploy.mjs:85). Both via `runNpm` (cloudflare/exec.mjs:169-178, `CAIRN_NPM_BIN` seam). Order: install runs inside the Cloudflare chapter, AFTER the GitHub chapter has already pushed the scaffold (github/chapter.mjs:433 pushScaffold vs cloudflare/chapter.mjs:209). So anything that needs installed deps (the manifest) currently cannot run before the first push.
- wrangler is the site's own devDependency, run through `runWrangler` (exec.mjs:140-150, `CAIRN_WRANGLER_BIN` seam): `whoami`, `login` (browser OAuth, ~2 min timeout per BACKLOG #366), deploy, d1/r2/secret, the seed of the owner + sign-in token, `deployments list`. Go has no wrangler replacement short of calling the Cloudflare API directly (the API-first path exists for much of this already in src/cloudflare/api.mjs; deploy of a Worker bundle through the API is a larger step, UNCONFIRMED feasibility).
- `npx cairn-manifest` (engine bin `dist/vite/bin.js`, src/lib/vite/bin.ts) is NOT called by setup today; that omission is #365. It evaluates the site's Vite config through Vite (`loadCairnBuild`, `evalVirtual`), so it needs `npm install` first.
- The build plugin `cairnManifest` verifies `site-facts.json` in `buildStart` on every build and fails the build when stale (src/lib/vite/internal.ts:342-347).
- The template bake needs the compiled engine (`dist/guidance/install.js`, via `npm run package`) and the monorepo; it stays a CI/release-time Node step. Runtime scaffolding in Go needs only the baked tree (embed or fetch).
- The gate's pty driver uses util-linux `script` (scripts/gate/driver.mjs header); the gate needs Node regardless.

How #365 arises: `applySubstitutions` writes `aiPosture: 'invite'|'decline'` into `src/theme/cairn.config.ts` (substitute.mjs:280-291) but the template ships `src/content/.cairn/site-facts.json` baked for the unset posture (`{"version":1,"mediaBucketBinding":"MEDIA_BUCKET"}`, templates/waymark/src/content/.cairn/site-facts.json). The plugin recomputes the facts from the adapter (`adapterFactsSource` reads `cairn.media.bucketBinding`, `cairn.roles`, `cairn.aiPosture`, internal.ts:597-608), serializes with `formatSiteFacts` (key order `version, mediaBucketBinding, roles, aiPosture`, omitted when undefined, trailing newline, internal.ts:665-676), and compares byte for byte: mismatch -> "site-facts.json is stale". Since the pushed repository carries the same stale file, the first Workers Builds deploy fails too. Every gate leg passes `--ai-posture none` (legs.mjs:644), the one answer that leaves the template byte-identical, so no leg exercised it. (Also content `index.json`: not touched by the substitutions; name/description/brand color do not enter it, UNCONFIRMED beyond reading substitute.mjs.)

Where regeneration belongs (recommendation):
- Option A, in the scaffolder, no Node: because site-facts is a tiny deterministic JSON (version + the three adapter-derived fields), the Go scaffold step that applies the posture can write the file itself with the same serialization (and the Go `cairn doctor` already consumes this file; the engine comment says it exists "for a Go process (which cannot evaluate a site's adapter)", internal.ts:665-668). This runs before the first commit/push with no npm install, fixes the pushed-repo half of #365 and the first Builds deploy. Guard it with a cross-check test: after `npm install`, `npx cairn-manifest --check`/build must report "unchanged" for every posture value. Risk: a second writer of the format; the cross-check test covers drift.
- Option B, call `npx cairn-manifest` after substitution: requires `npm install` before the first push (reorders chapters: install, manifest, then push) and keeps Go dependent on Node at scaffold time.
- Option C, bake variants: ship three site-facts variants (none/decline/invite) selected by the posture; simplest, but each new adapter-derived fact or prompt (e.g. a theme that declares roles) multiplies variants. A theme choice (#361) changes `src/theme/` wholesale, so site-facts must come from the chosen theme's adapter: favors A (compute) or B (run), not C.
- Whatever is chosen, the gate should run the matrix of posture values and the theme catalogue through `npm run check`, `cairn-manifest --check`, `npm run build` offline (#366a).

## 3. The browser with no copying (web research)

### gh (GitHub CLI)
- gh's `internal/browser` is a thin wrapper: `Browser` interface `Browse(string) error`; `New(launcher, stdout, stderr)` delegates to go-gh (https://raw.githubusercontent.com/cli/cli/trunk/internal/browser/browser.go).
- go-gh `pkg/browser` resolves the launcher in order: explicit argument, `GH_BROWSER`, the `browser` key in gh's config file, then `BROWSER`; empty -> default opener (cli/browser `OpenURL`). With a launcher set it `shlex.Split`s the string, `safeexec.LookPath`s the binary, appends the URL, and `exec.Command(...).Run()`; every failure returns an `error` (URL scheme not http/https/vscode, bad shlex, binary not found, non-zero exit) (https://raw.githubusercontent.com/cli/go-gh/trunk/pkg/browser/browser.go). Docs: "`GH_BROWSER`, `BROWSER` (in order of precedence)" (https://cli.github.com/manual/gh_help_environment). Caveat noted by the fetch: a whitespace-only launcher could index an empty slice (unconfirmed by running).
- gh's device flow (`internal/authflow/flow.go`, https://raw.githubusercontent.com/cli/cli/trunk/internal/authflow/flow.go): interactive -> prints "Press Enter to open <url> in your browser" and waits, then opens; non-interactive -> prints the URL with an "Open this URL" instruction and does not try to open. On open failure it prints a red "! Failed opening a web browser at <url>", the indented error, and "Please try entering the URL in your browser manually", then returns nil (the flow continues; the URL was printed, the user must copy it). It displays the one-time code in bold and can copy the code to the clipboard (`--clipboard`). Take-away: gh's fallback is exactly the copy step the owner calls a failure, with good wording.

### Go browser libraries
- `github.com/cli/browser` (fork of pkg/browser used by gh): `OpenURL`, `OpenFile`, `OpenReader`; `runCmd` uses `exec.Command(...).Run()` with package-level `Stdout`/`Stderr` writers. Linux tries, via `exec.LookPath`, `xdg-open`, `x-www-browser`, `www-browser`, `wslview` and returns `&exec.Error{Name: "<list>", Err: exec.ErrNotFound}` when none exist; darwin runs `open`; Windows calls `ShellExecute` (x/sys/windows) with `SW_SHOWNORMAL` (https://raw.githubusercontent.com/cli/browser/main/browser.go, browser_linux.go, browser_darwin.go, browser_windows.go). The fetch summary of browser_linux.go used `Start()` in its paraphrase while browser.go shows `Run()`; treat the exact call as unconfirmed.
- `github.com/pkg/browser`: same shape; Linux list is `xdg-open, x-www-browser, www-browser`; returns the same `exec.ErrNotFound`-wrapping error, otherwise the `runCmd` error (https://raw.githubusercontent.com/pkg/browser/master/browser_linux.go).
- Failure reporting for both: only (a) no launcher binary, or (b) the launcher process exits non-zero. A launcher that exits 0 without showing a browser (a stub, or xdg-open handing off to a dead session) is invisible. Neither detects a missing display.
- Honoring `$BROWSER` is not done by cli/browser or pkg/browser themselves (nothing in the fetched code); go-gh adds it. `xdg-open` itself reads `$BROWSER` and, when unset, builds a list of text browsers (links2, elinks, links, lynx, w3m) and adds graphical ones only when `$DISPLAY` is set (xdg-open script, https://chromium.googlesource.com/chromium/deps/xdg-utils/+/cb54d9db2e535ee4ef13cc91b65a1e2741a94a44/scripts/xdg-open.in).

### Detecting "no browser can open"
- xdg-open exit codes: 0 success; 1 command-line syntax; 2 file missing; 3 required tool not found; 4 action failed (https://portland.freedesktop.org/doc/xdg-open.html; newer man pages add 5 = permission denied, unconfirmed here). That page also says "xdg-open is for use inside a desktop session only." One report of an SSH session with no X11 forwarding got exit 4; the "no method available for opening" message is an "operation impossible" failure (code not confirmed) (https://github.com/posit-dev/rsconnect-python/issues/296, xdg-open script above).
- Linux heuristic (a Go port decides, not the library): headless if both `DISPLAY` and `WAYLAND_DISPLAY` are unset, or `SSH_CONNECTION`/`SSH_TTY` is set without a forwarded display, or no launcher on PATH (`exec.ErrNotFound`), or the launcher exits non-zero. A caveat: with `DISPLAY` unset xdg-open may open lynx/w3m in the owner's own terminal (the fish issue https://github.com/fish-shell/fish-shell/issues/6739 reports it opening "links"), which blocks or corrupts a TUI: run the opener with stdin/stdout/stderr detached and a timeout, and treat a text-browser fallback as "no browser". Also a dead D-Bus session (the exact rc.4 failure: `env -i`, dead session bus, BACKLOG #363) can make xdg-open exit 0 or non-zero depending on the DE; only a non-zero exit is observable, so "exit 0" is not proof the page appeared.
- macOS: `open <url>` exit code is reliable on a logged-in GUI session; over SSH it still asks the Mac's GUI session to open a browser on the remote Mac's screen (not detectable via the exit code); `SSH_CONNECTION` is the signal. Windows: `ShellExecute` returns an error code (>32 is success); WSL needs `wslview` (cli/browser lists it first-class); `WT_SESSION` marks Windows Terminal.
- Cannot detect: a browser that opens in a different profile/session than the owner is looking at; remote desktops.

### OSC 8 hyperlinks
- Syntax: `OSC 8 ; params ; URI ST` ... text ... `OSC 8 ; ; ST`; `params` colon-separated key=value, only `id` defined; BEL accepted for ST; simple stdout utilities should not set `id`; full-screen apps should assign explicit ids so a link stays grouped across wraps and repaints. Spec says: "Currently there's no way of detecting whether the terminal emulator supports hyperlinks", a hyperlink "should not be the only means of figuring out the target", and an unsupporting terminal simply shows the text (https://gist.github.com/egmontkob/eb114294efbcd5adb1944c9f3cb5feda).
- Support (Alhadis OSC8-Adoption table, fetched via https://raw.githubusercontent.com/Alhadis/OSC8-Adoption/master/README.md; the github.com page 504ed): GNOME Terminal / VTE since 0.50 (3.26; skip VTE 0.50.0, crashes; use 0.50.4/0.52.2+), GNOME Console 46.0, Ptyxis 47.6 (copy, open), kitty since 0.19, iTerm2 3.1, WezTerm since early 2018, Windows Terminal since 1.4.3141.0 (2020-11-12), Konsole supported but disabled by default (since Jul 2020), Alacritty 0.11, foot 1.7.0, Ghostty (2024-07), Hyper, Terminator 2.0, tmux 3.4+ supported only with setup (`set -ga terminal-features "*:hyperlinks"`; tmux re-emits only when the outer terminal's terminfo advertises `Hls`, per a Ghostty discussion https://github.com/ghostty-org/ghostty/discussions/13063, one report), GNU screen not supported. macOS Terminal.app is not on the Alhadis list; a terminfo.dev matrix (May 2026) lists Terminal.app as supporting OSC 8 while an older blog says no: UNCONFIRMED, verify on the target macOS (https://terminfo-dev.pages.dev/terminals/terminal-app). xterm unlisted. Ptyxis here is the owner's daily terminal; VTE support is in range for a current Bluefin.
- Detection (heuristic, since a terminal cannot be queried): the supports-hyperlinks rules (https://raw.githubusercontent.com/jamestalmage/supports-hyperlinks/master/index.js): `FORCE_HYPERLINK` (non-0 forces on, 0 off); disabled if stdout is not a TTY or has no color; `WT_SESSION` -> on; win32 without it -> off; `CI`/`TEAMCITY_VERSION` -> off; `TERM_PROGRAM` iTerm.app >= 3.1, WezTerm >= 20200620, vscode >= 1.72, ghostty -> on; `VTE_VERSION` >= 0.50 (not 0.50.0) -> on; `TERM=alacritty` -> on; else off. Missing from that list: kitty (`KITTY_WINDOW_ID`/`TERM=xterm-kitty`), Konsole (off by default anyway), foot, tmux (check `tmux display -p '#{client_termfeatures}'` per https://github.com/D0n9X1n/SonicTerm/wiki/Terminal-Multiplexers, secondary source). Windows Terminal auto-detect gaps are reported elsewhere (claudeissues.com 59100). Charm: `github.com/charmbracelet/x/ansi` exports `SetHyperlink(uri, params...)` and `ResetHyperlink(params...)` (https://raw.githubusercontent.com/charmbracelet/x/main/ansi/hyperlink.go); Lip Gloss/Bubble Tea would carry the sequences as text, with width-measurement concerns (unconfirmed).
- Does a clickable link satisfy "no copying" as the fallback? Partly. It removes the copy step when the terminal supports OSC 8 and the owner can ctrl/cmd-click (VTE: Ptyxis, GNOME Terminal, kitty, iTerm2, WezTerm, Windows Terminal, Ghostty, Alacritty, foot). Weaknesses: (1) support cannot be detected reliably, so an unsupported terminal (older Terminal.app, GNU screen, tmux without config, Konsole by default, an SSH hop through a multiplexer) shows plain text that the owner must select and copy: the failure mode returns silently; (2) a headless/SSH session has no local browser at all, so even a clickable link opens on the machine running the terminal, which is the right machine only when the owner's terminal is local; for SSH the terminal emulator is local, so ctrl-click does open the owner's local browser, but loopback callbacks (127.0.0.1:port) then land on the wrong machine; (3) modifier-click and underline conventions differ. So treat OSC 8 as the fallback tier: order = (1) open the browser automatically; (2) on failure/headless, print an OSC 8 link plus the plain URL set apart in a box; (3) for pure no-click cases, the only copy-free options are device-code flows (GitHub's device flow shows a short code that the owner types, still a manual step but not a URL copy) or a pty-independent mechanism such as a QR code (no smartphone per workstation notes, so a poor fit for the owner) or `$BROWSER`/`GH_BROWSER`-style override. The decided rule ("any copy and paste of URLs required ... is a failure") is only fully satisfiable when a local browser can open or the terminal supports OSC 8; the design should say so, detect, and tell the owner which they have. Also consider one local landing page at 127.0.0.1 that walks every step (BACKLOG #363's own proposal): after one open (or one click), the page carries the later links, so only the first link ever needs opening.
