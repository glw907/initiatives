## 2. Can create and install be ONE browser trip with no copying?

Yes in principle; GitHub documents each hop and prior art does it.
- Manifest flow (https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest): POST manifest to /settings/apps/new (user) or /organizations/ORG/settings/apps/new; GitHub redirects to `redirect_url` with `code`; POST /app-manifests/{code}/conversions; "You must complete all three steps ... within one hour." `state` is optional, returned on redirect. `callback_urls` up to 10; `setup_url`, `setup_on_update`, `request_oauth_on_install` are all manifest fields.
- Proposed single trip: loopback `/manifest` handler does the conversion synchronously, then replies `302 Location: https://github.com/apps/<slug>/installations/new`. Probot does exactly this (https://github.com/probot/probot/blob/master/src/apps/setup.ts: after createAppFromCode, `location: ${response}/installations/new`), and Backstage's create-github-app does the same per a search summary (source not read; unconfirmed). Then the owner clicks Install & Authorize; GitHub redirects to the first callback URL with `code`, `installation_id`, `setup_action=install` (spike (b), observed live). The same loopback receives it. Nothing is copied; the opening is two clicks (Create, Install & Authorize) in a continuous browser flow.
- Do the conversion BEFORE the 302 (do not park the code for later); the 1-hour limit is then irrelevant. Answer the final callback at once with the landing page and do exchange work after (spike out-of-band finding).
- setup_url: docs (https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url) say users are redirected there after install with an `installation_id` query parameter, and that it must not be trusted alone (spoofable). The docs do NOT say whether it is honored together with request_oauth_on_install. GHES docs (e.g. https://docs.github.com/en/enterprise-server@2.20/developers/apps/creating-a-github-app) say selecting "Request user authorization (OAuth) during installation" disables the Setup URL field and sends the user to the callback URL instead (I could not re-read that exact wording on current github.com docs: treat as likely, unconfirmed on github.com). Consequence: use request_oauth_on_install and read `installation_id` from the CALLBACK; setup_url is not needed and should not be set. setup_on_update is irrelevant.
- Can setup_url be 127.0.0.1? Docs only say "a full URL"; no loopback rule found. callback_urls on 127.0.0.1 with a port is proven by the spike. setup_url on loopback: unconfirmed, but moot.
- Loopback redirect rule (https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps): "The redirect_uri does not need to match the port specified in the callback URL"; localhost not documented as accepted (RFC advises against), use 127.0.0.1 or ::1. The install-time redirect is different: no redirect_uri is supplied, GitHub uses the first callback URL verbatim (https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), so the manifest's first callback URL must carry the real port, and the SAME listener must still be up at install time. This is why a resumed run's second install trip dead-ends (spike (c)). Docs note: wildcard callback matching changed for apps after 2026-08-03; unconfirmed whether it affects manifest-made apps.
- Personal vs org: the manifest target URL differs (above). Creating an org-owned App needs the user to be an org owner or App manager (docs implication; unconfirmed wording). A private App (public:false) is installable only on its owning account ("apps set to 'Only on this account' can be installed only on the account that created them", https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app), so for the owner the install target is fixed. For an org-owned App, a non-owner member sees a "Request" button and GitHub notifies owners (https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party); the redirect shape after a request is undocumented (setup_action=request per third-party references; unconfirmed on GitHub). Today's code never reads setup_action, so a request is only noticed after 10 minutes (install.mjs:299-302); a port should read it on the callback and park immediately.
- Does setup need a separate OAuth sign-in? The user access token is needed for: POST /user/repos (personal repo creation needs a user token; an installation token cannot create a user-account repo), GET /user/installations/{id}/repositories (user-only; the installation equivalent is GET /installation/repositories), and the chapter-3 reconcile commit. With request_oauth_on_install the token is already minted in the install click (code in the callback), so NO separate sign-in is needed on a fresh run; oauth.mjs `reauthorize` exists only for resume and for chapter 3. To remove those: (1) keep the user token for the whole run. It expires after 8 h with a 6-month refresh token (https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens; refresh needs client_secret, which the state record holds), so persist the refresh token or just hold it in the process (the unattended stretch is short); or (2) mint an INSTALLATION token from the App JWT for the push and reconcile (contents:write and workflows:write are already requested), but the pem is destroyed after it moves into Worker secrets (cloudflare/secret.mjs:42), so reconcile must run before that or hold the pem until the end. Repo creation for a personal account must use the user token either way. Org repo creation with an installation token (Administration permission): unconfirmed.
- Device flow (https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app) avoids a callback but must be enabled in App settings, and no manifest field for it is listed in the manifest doc: would be a manual toggle, so rejected; also types a code, which is copy by hand.

## 3. Why the rc.4 install poll stalled; deterministic detection

- What the code shows: the poll can only match `installation.account.login === owner` (install.mjs:79), with owner = the App creator's login. Because the App is private it can only ever be installed on that account (docs above), so the account mismatch cannot normally occur for it. I found no code defect that explains a stall. The rc.4 ledger (lines 384-385) only records: record reached repo-created with installation 179774962, #364(d) unconfirmed, 33069 was setup's own port. Most likely the install simply had not been completed in the polled window (the link was opened in a stale tab, per BACKLOG #364(b)); the poll did what it was written to do, but its copy never says what it waits for.
- Contributing UX facts: the poll names neither account nor URL (87); the callback is also racing, so with a fully working redirect the callback should have won in seconds and the poll never mattered, which suggests the browser never completed the Install & Authorize click, or the redirect was not followed (unconfirmed). Pagination: GET /app/installations default 30 per page (fine for a fresh App).
- Deterministic alternatives: (a) the callback itself: `installation_id` + `setup_action=install` + `code` arrive together on the first callback URL (spike (b)); this is the primary signal and needs no polling. (b) as fallback, query the owner directly with the App JWT: `GET /users/{owner}/installation` or `GET /orgs/{org}/installation` (https://docs.github.com/en/rest/apps/apps), JWT auth, which returns the installation or 404 (404 not documented there; the by-id endpoint documents it). Or take any installation from GET /app/installations (a private App has at most its owner's). (c) Webhooks cannot be used (hook inactive; no public endpoint). So detection = callback first, direct JWT lookup as backstop, and the waiting line should say "Waiting for you to click Install & Authorize for <account> at <link>".

## Suggested port shape (GitHub side)
Pre-flight (before any browser): org existence and role, App-name availability, repo-name availability (GET /repos/<owner>/<name> 404 means free, unauthenticated for public names only; private-name collisions only show on create), browser availability. Then one continuous browser run: loopback `/` form -> GitHub Create -> `/manifest` (convert, save creds, 302 to install) -> Install & Authorize -> `/callback` (code, installation_id, setup_action) -> exchange code, hold user token (and refresh token) for the run. Create repo, verify coverage, push, reconcile with the held token, so chapter 3 needs no further GitHub sign-in. Keep: state nonce, Host allowlist, immediate landing responses, repo-created saved before coverage check, whole-literal finalize idempotence, paged coverage read, gitignore-honoring push, real default branch (and fix finalize's hard-coded 'main').

## 5. The floor: fewest browser visits (added at the owner's request)

Definitions: a "visit" is one browser launch that the tool drives; a "click" is a human approval on a GitHub page inside it.

### 5a. Can a local credential do repo creation and push with no browser?
- Yes for the repository half, with caveats. `POST /user/repos` and the Git Data push need only a user-level token with `repo` (classic/OAuth) scope; nothing about them needs the App. Sources: a gh token has `repo` by default (gh docs: minimum scopes `repo`, `read:org`, `gist`, https://cli.github.com/manual/gh_auth_login); `gh auth token` prints it; `GH_TOKEN`/`GITHUB_TOKEN` are honored by gh for headless use (same page). On this machine `gh auth status` shows glw907 with scopes delete_repo, gist, read:org, repo, workflow, so the owner's own token would work here.
- Caveat 1: the scaffold bakes `.github/workflows/check.yml` (src/scaffold.mjs:224-253). Pushing a workflow file with a classic/OAuth token needs the `workflow` scope (GitHub behavior, widely reported; not read on a docs page here, treat as unconfirmed); a default `gh auth login` token lacks it, and `gh auth refresh -s workflow` is itself a browser device-code visit. A fine-grained PAT needs Contents and Workflows write plus repo-creation (Administration) permission (unconfirmed exact set).
- Caveat 2: a git credential helper may hold a usable token (`git credential fill` for host=github.com), but its scopes are unknown until probed. A pre-flight can call `GET /user` and read the `X-OAuth-Scopes` response header (present for classic/OAuth tokens, absent for fine-grained; header behavior from memory, unconfirmed here).
- Caveat 3: a token like this does NOT remove the App. The App is the site's runtime identity: `createGithubApp({ owner, repo, branch, appId, installationId })` (src/lib/github/backend.ts:116-123 region) plus the private key as a Worker secret. So the browser is still needed for App creation and install; what a gh token removes is only the App's own OAuth step.
- Bonus: `PUT /user/installations/{id}/repositories/{repo_id}` is refused for an App user token (spike e) but its docs page ties PAT (classic) `repo` scope to the sibling DELETE endpoint (https://docs.github.com/en/rest/apps/installations); so a classic gh token may be able to add a new repo to a "selected repositories" installation with no browser. Unconfirmed for the PUT; worth one live probe.

### 5b. Can App creation happen without a browser? Can creation + install collapse?
- Creation: no. The manifest flow is the only programmatic route and it ends in a human "Create GitHub App" click on github.com (https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest, flow step 1 is a browser redirect and POST). The REST reference's apps/installations pages list no create-App endpoint (https://docs.github.com/en/rest/apps/installations). The spike also noted App deletion has no API (spike record). Community sources agree (search results: gamf, Vellum, a Jan 2026 post: "no API's to install the App"); no official statement found, so "believed, not proven absent".
- Install: no API either (same sources). One enterprise-only path may exist for enterprise-owned apps (unconfirmed, irrelevant to a personal owner).
- Collapse: creation and install cannot be one CLICK (two separate GitHub pages, each needing approval), but they CAN be one browser VISIT with no copying: loopback `/manifest` converts the code and 302s to `https://github.com/apps/<slug>/installations/new` (Probot does this: https://github.com/probot/probot/blob/master/src/apps/setup.ts, `location: ${response}/installations/new`). With `request_oauth_on_install: true` the Install click also authorizes and returns `code` + `installation_id` to the loopback callback. Count: 1 visit, 2 clicks (Create, then Install & Authorize), plus GitHub sign-in/2FA inside the same visit if signed out (the signed-out dead end needs a fix: spike (a)). Whether GitHub skips the account picker for a private single-target App is unconfirmed.

### 5c. Can the user OAuth step be dropped?
- On a first site it costs NOTHING in visits: with `request_oauth_on_install` the authorization rides on the Install click (spike (b): "Install & Authorize"), no extra page. Dropping it saves a consent line, not a visit.
- It can be dropped only if another credential covers `POST /user/repos` and the push: a local gh/`GH_TOKEN` token (5a), or, for the push and reconcile only, an installation token minted from the App JWT (contents and workflows are already in the manifest; but the pem is deleted after it moves to Worker secrets, cloudflare/secret.mjs:42, so mint before that). A personal-account repo cannot be created by an installation token; an org repo possibly can (Administration permission; unconfirmed).
- If OAuth is dropped, the install redirect must come back some other way: `setup_url` (gets `installation_id`, https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url; loopback setup_url unconfirmed), or the JWT lookup `GET /users/{owner}/installation` (https://docs.github.com/en/rest/apps/apps). Not recommended: it adds risk to save no visit.
- The late reauthorize in chapter 3 (cloudflare/chapter3.mjs:266) IS droppable and should be: hold the install-time user token for the run (8 h life, refresh token 6 months, https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens), or use a gh token.

### 5d. Second site by the same owner: reuse or adopt an existing App?
- Technically reusable. The runtime needs only appId, installationId, owner/repo and the private key (backend.ts:116-123; the key is a Worker secret). A private App is installable only on its owner ("Only on this account", https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app), and if that one installation is "All repositories" it covers every future repo of the owner, so site 2 needs no new App and no new install. Today's tool never reuses: one App per site (chapter.mjs:210 copy; name default `cairn-<slug>`), and the state record is per site.
- Blockers to fix in a port: (1) the pem exists only in the first site's state record and then its Worker secret, and is deleted from state after the move (secret.mjs:42); Worker secrets cannot be read back, and there is no API to generate a new key (community-reported, unconfirmed), so a new key is a settings-page browser visit. A port must keep a per-owner identity record (appId, slug, clientId, clientSecret, pem, installationId, ownerLogin, refresh token) in the 0600 config home (state.mjs pattern) or the OS keyring, BEFORE the pem is dropped. (2) The install must have been "All repositories"; under "selected repositories" a repo made by site 2 is auto-added only when created with the App's own user token (spike e), and the adding API is refused for that token. (3) A user token for repo creation: reuse via the stored refresh token (rotates on every use, new 6-month life; needs client_secret, which is stored) or the gh token (5a). If the refresh token is lost or older than 6 months: one re-authorize visit (one click or none, GitHub skips consent for an authorized App).
- Adopting an App the owner made by hand or an earlier run: needs the pem (file path or paste: a copy step, so unwanted) and the install id (`GET /users/{owner}/installation` with the JWT, no browser). Manifest-made Apps are the only ones the tool has a key for.
- Trade-off needing a ruling (scope, security): the App holds contents/administration/workflows write over the installation. PERMISSION_COST (chapter.mjs:31) promises an App "that only this site uses"; one App across sites widens the blast radius of a leaked key to every repo of the owner. A middle option: one App per site (today) but still zero extra visits on site 2 is impossible, since creation and install need a browser each time.
- Later Cloudflare-side GitHub steps are also once-per-owner: authorizing Cloudflare's "Workers and Pages" GitHub App (chapter3.mjs:959) and its repo selection (cloudflare/catalogue.mjs:797) are one-time if that App is installed on "All repositories"; otherwise each new repo needs a settings visit. Whether Cloudflare's App can be installed from a deep link in the same opening is unconfirmed.
