Design: `907-rebuild/specs/2026-11-07-907-rebuild-design.md`. Plan: `907-rebuild/plans/2026-11-07-907-rebuild-plan.md`. Fold record: `907-rebuild/plans/2026-11-07-907-rebuild-fold.md`. This spec states the mechanisms the plan builds on. Each one is quoted from its source, or left for T1's probe to prove.

## The clean room

### Layout

The clean room lives at `/var/tmp/cairn-cleanroom/`, outside Geoff's home:

- `A/` and `B/` are the two builders' home directories. Each holds the builder's Claude config at `~/.claude` (the default under that home, so no `CLAUDE_CONFIG_DIR`), its `gh` and wrangler sign-ins, its npm cache, setup's state record, and its working directory `~/work/`.
- `acceptance/` is a third home the observer uses for T7's fresh scaffold, so the observer's own setup state is never touched.
- `logs/` holds each run's stream-json log, written by the launcher outside both builders' homes.

Living outside `/var/home/glw907` removes the ancestor problem at its root. Claude Code "loads `CLAUDE.md` and `CLAUDE.local.md` from your current working directory and every directory above it" (docs/en/memory), counts "a `CLAUDE.md`, `.claude/CLAUDE.md`, or `CLAUDE.local.md` in your working directory or any directory above it" (same page), and "loads project skills from `.claude/skills/` in the directory where you start it and in every parent directory up to the repository root" (docs/en/skills). Under `~/Projects/cleanroom/`, `/var/home/glw907/.claude/CLAUDE.md` and `.claude/skills` would be ancestors. Under `/var/tmp`, no ancestor holds a `.claude`. systemd-tmpfiles ages `/var/tmp` at 30 days (`q /var/tmp 1777 root root 30d`), longer than the run, and T13 archives the logs.

Separate homes also mean separate session transcripts and auto memory, so the two builders can't read each other's notes. Auto memory stays on, as it would for a newcomer.

### The launch

`907-rebuild/tools/cleanroom-run` has three forms:

- `cleanroom-run install` creates the four directories and installs each builder's `settings.json` from `907-rebuild/tools/cleanroom-settings.json`.
- `cleanroom-run <A|B> [--resume <uuid>] "<prompt>"` runs one headless turn.
- `cleanroom-run <A|B> --shell` opens an interactive shell with the same environment, for Geoff's sign-ins and setup.

Every form runs `cd "$HOME/work"` before it starts Claude or the shell, so setup creates the site inside the work tree the read block opens. T1 checks that `pwd` prints `/var/tmp/cairn-cleanroom/<A|B>/work` in a headless turn and in the shell.

Every form runs through `env -i` with this allowlist and nothing else:

- `HOME=/var/tmp/cairn-cleanroom/<A|B>`;
- `PATH=/var/home/glw907/.local/share/mise/installs/node/lts/bin:/home/linuxbrew/.linuxbrew/bin:/usr/bin:/bin`, with no `~/.local/bin` or dotfiles directory;
- `LANG=C.UTF-8` and `TERM=xterm-256color`;
- `TMPDIR` and `CLAUDE_CODE_TMPDIR`, both `/var/tmp/cairn-cleanroom/<A|B>/tmp`. "Claude Code's own temp files always use your override", but "sandboxed Bash subprocesses receive a short fallback `$TMPDIR` under the system default when your override is a long path" (docs/en/env-vars), so T1 records the `$TMPDIR` a sandboxed command actually sees.

A probe on 2026-11-07 ran that launch with a scratch home. Its environment held only `HOME LANG PATH PWD SHLVL TERM _`. `node` v26.13.0, `npx` 11.20.0, `gh` 2.103.3, `git` 2.56.0, and `claude` 2.1.319 all ran, and `gh auth status` reported "You are not logged into any GitHub hosts." So no exported secret, `SSH_AUTH_SOCK`, `DBUS_SESSION_BUS_ADDRESS`, or askpass helper reaches a builder through its environment. Wrangler, `gh`, npm, and setup all read their state from the clean home. A cleared environment doesn't close paths, though: `/tmp` holds other sessions' files, `/run/user/1000` holds the D-Bus socket and the keyring directory, and `/dev/shm` can hold `claude-askpass`'s sudo cache. "Settings" closes those.

A headless turn adds `-p --permission-mode dontAsk --output-format stream-json --verbose --session-id <uuid>`, or `--resume <uuid>` on a follow-up, and tees the stream to `logs/<builder>-<n>.jsonl`. `--session-id` takes "a valid UUID" and `--resume` takes a session "by ID" (docs/en/cli-reference). "A `-p` session shows no workspace trust dialog" (docs/en/headless).

### Settings

Each builder's `~/.claude/settings.json` is user-scope settings for that home. It sets the following.

- **Permission mode `dontAsk`**, passed on every launch. "Auto-denies every call that would otherwise prompt", while "tools pre-approved via `/permissions` or `permissions.allow` rules" still run (docs/en/permissions). Auto mode is not used: in `-p`, "When repeated blocks reach a threshold, the action doesn't run and Claude keeps working," and auto mode drops "broad allow rules that grant arbitrary code execution", among them "Package-manager run commands" (docs/en/permission-modes).
- **Allow:** `Edit`, `Write`, `WebFetch`, `WebSearch`, and `Bash(npm *)`, `Bash(npx *)`, `Bash(node *)`, `Bash(git *)`, `Bash(gh *)`, `Bash(ls *)`, `Bash(cat *)`, `Bash(mkdir *)`, `Bash(cp *)`, `Bash(mv *)`.
- **File tools held to the working directory:** `permissions.blockReadsOutsideWorkingDirectories` and `permissions.blockWritesOutsideWorkingDirectories`, both `true`, with the working directory `~/work/`. "Claude Code denies `Read`, `Grep`, `Glob`, and `LSP` calls on those paths", and the write key makes "the `Write`, `Edit`, and `NotebookEdit` tools refuse paths outside your working directories", which needs v2.1.314 or later, and the read key v2.1.257 (docs/en/settings-reference; the CLI is 2.1.319). So the file tools can't reach `/tmp`, `/run/user`, `/dev/shm`, the rest of `/var/tmp`, Geoff's home, the other builder, or the builder's own `~/.config`. Path deny rules can't express "everything but `~/work/`", since the clean home sits under `/var/tmp`, and "Claude Code reads a `!` pattern relative to the current directory even when `/`, `~/`, or `//` follows the `!`" (docs/en/permissions).
- **Deny, as tripwires beside the block:** `Read(//var/home/glw907/**)`, `Read(//home/glw907/**)`, `Read(//tmp/**)`, `Read(//run/user/**)`, `Read(//dev/shm/**)`, `Edit(~/.claude/**)`, `Write(~/.claude/**)`, and the other builder's home and `logs/` by `//var/tmp/cairn-cleanroom/...` paths. "Use `//Users/alice/file` for absolute paths" (docs/en/permissions).
- **Bash deny:** `Bash(*907-life-legacy*)`, `Bash(*cairn-build*)`, `Bash(*cairn-907-auth*)`, `Bash(*wrangler delete*)`, `Bash(*d1 delete*)`, `Bash(*r2 bucket delete*)`, `Bash(*r2 object delete*)`, `Bash(*repo delete*)`, `Bash(*-X DELETE*)`, `Bash(*--method DELETE*)`, `Bash(git push*--force*)`, and `Bash(git push* -f*)`. Builder B also denies `Bash(*create-cairn-site*)` (see "Setup runs in Geoff's terminal"). "Deny and ask rules apply when any subcommand matches them" (docs/en/permissions).
- **Sandbox:** `sandbox.enabled`, `sandbox.failIfUnavailable`, and `allowUnsandboxedCommands: false`, with no `excludedCommands`. `filesystem.denyRead` is `["/var/home/glw907", "/home/glw907", "/tmp", "/var/tmp", "/run/user/1000", "/dev/shm"]`. `filesystem.allowRead` is `["~/work", "~/.npm", "~/.cache", "~/.config/gh", "/var/home/glw907/.local/share/mise/installs/node", "/home/linuxbrew/.linuxbrew", "/var/home/linuxbrew/.linuxbrew"]`, plus the sandboxed `$TMPDIR` T1 records. Builder A's copy also adds `~/.config/cairn`, since its local scaffold writes setup's record there. "When read rules overlap, the rule with the narrower path applies" (docs/en/sandboxing). With the read block on, "the block also covers sandboxed commands. Claude Code denies them read access to your home directory", then "re-opens the working directories ... the session temp directory", and only "`allowRead` and `allowWrite` entries from repository settings don't count" (docs/en/settings-reference), so these user-settings entries do. So a sandboxed command reads its work tree, its npm cache, its `gh` sign-in, the Node toolchain, and Homebrew, where `gh` lives, and builder B's `~/.config/cairn/` stays closed. `filesystem.allowWrite` is `["~/.npm", "~/.cache", "~/.config/gh"]`, plus `~/.config/cairn` for A, beside the default "current working directory and its subdirectories" and `$TMPDIR` (docs/en/sandboxing).
- **What the sandbox masks, from sandbox-runtime's source** (`@anthropic-ai/sandbox-runtime` 0.0.81, `dist/sandbox/linux-sandbox-utils.js`; T1 confirms against the bundled build). A denied directory gets "a tmpfs over a read-denied directory", then the allowed paths are bound back. So `/run/user/1000/bus` and the keyring directory don't exist inside the sandbox, and a connect by path fails. Network restriction runs `--unshare-net` ("This removes all network interfaces"), which also cuts abstract sockets. Every command gets `--unshare-pid` and a fresh `--proc /proc` ("If we don't have --proc, it is possible to read host /proc"), so no host process's `environ` is visible, and `--dev /dev`, a fresh `/dev`. The optional seccomp filter adds "Unix domain socket blocking" (docs/en/sandboxing). It isn't installed in the clean toolchain, and the masking above should make it unnecessary for these paths. T1 proves that rather than assuming it: if the bus connect or a `/dev/shm` canary succeeds, the seccomp filter goes into the clean toolchain's Node and T1 reruns. If a normal build needs a path these lists close, T1 adds that one path and records it.
- **Network:** `sandbox.network.allowedDomains` names `registry.npmjs.org`, `github.com`, `api.github.com`, `codeload.github.com`, `*.githubusercontent.com`, `api.cloudflare.com`, `*.workers.dev`, and `907.life`, plus the browser download host T1 finds. `strictAllowlist: true` "denies sandboxed commands access to any host outside the allowlist instead of prompting" (docs/en/sandboxing). If T1's in-sandbox `node -e "fetch(...)"` fails, `env` sets `NODE_USE_ENV_PROXY=1`: "When enabled, Node.js parses the `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` environment variables during startup, and routes requests through the specified proxy" (nodejs `doc/api/cli.md`).
- **Account-borne context off:** `disableClaudeAiConnectors: true` ("Claude Code neither fetches nor connects those connectors") and `syncClaudeAiSkills: false` ("stops downloading synced skills and stops loading the ones already in `~/.claude/skills/synced/`") (docs/en/settings-reference). Geoff's claude.ai account carries a Cloudflare connector with account access.

The rules are tripwires, not a boundary around a program: "a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program" (docs/en/permissions). Under `dontAsk`, a form off the allow list is denied anyway. The residual risk is an allowed interpreter (`node -e`, `npx <package>`) calling an API with the builder's credentials. That is why the credentials stay small: builder A holds only `gh`, and builder B holds `gh` alone once the setup sitting ends. Wrangler is signed out, and setup's record, which can hold a pasted Cloudflare token, sits in `~/.config/cairn/`, outside everything B can read. `gh auth login`'s "minimum required scopes" are `repo`, `read:org`, and `gist`, with no `delete_repo` (`gh auth login --help`). The observer reads the logs as the builders run, but a check made after a call can't prevent it.

Two sandbox limits shape the run, both from docs/en/sandboxing. On Linux "a sandboxed command's `localhost` is private to that command. The command can listen on a port and reach servers it started itself", so a dev server and its check must run in one command. "Chromium exits with `No usable sandbox!`", and the fix is to "start the browser with `--no-sandbox`." A backlog item caused by either limit is a harness item. It goes in the fold record, not to the conductor.

### Setup runs in Geoff's terminal

cairn's docs make setup a person's task at a terminal. Its page "is for someone who is comfortable pasting a command into a terminal and clicking through a dashboard" (`docs/admin/create-your-site.md`, line 5), and "A run that can't ask, such as `--yes` without `--email` or a script with no terminal, stays declined" (`own-your-domain.md`, line 89). A run with output redirected parks: "both waits park exactly as they always have: exit `0`" (setup README, line 462). On a non-TTY, the owner sign-in link "is not printed to this non-interactive output" (`src/github/open.mjs`, line 64). That matches Geoff's ruling that setup is his step-12 install.

So builder B works out the command from the published docs and ends its turn asking the person to run it. Its deny rule on `create-cairn-site` makes the hand-off explicit instead of a half-run in the sandbox. Geoff runs that command in `cleanroom-run B --shell`, interactively, with the domain, sign-in email, and Workers Builds. Setup opens its own prefilled create-token page for each token it needs. Geoff leaves the permission rows as setup filled them, sets an end date two days out, since Cloudflare tokens take an optional TTL (developers.cloudflare.com/fundamentals/api), and pastes the value into setup's own prompt. The token never enters chat or a builder's environment. Setup keeps it in its record as `cloudflare.apiToken` (`saveChapter2Token`, `chapter2.mjs`, line 236; chapter 3 likewise at line 1135) and deletes it only when its chapter finishes. A run that stops short leaves it there. B can't read that record, and T6's acceptance checks the key is gone without printing it. When the sitting ends, Geoff runs `npx wrangler logout` in the same shell, so builder B holds no Cloudflare sign-in while it builds.

## The observer

907-life-e7 watches each builder's log with the Monitor tool. It acts on five events:

1. **A hand-off.** The builder's turn ends asking the person to run something, such as setup or `--sign-in`. The observer checks that the command names nothing outside the brief, runs `notify-send -u critical "907 rebuild: your terminal is needed"`, and gives Geoff the exact command in chat.
2. **A permission denial.** If the action belongs in the build, the observer widens the template and re-runs `cleanroom-run install`, then resumes the builder. If auto mode refuses the observer that write (T1 tries it once), a widening becomes a `[you]` re-run of `cleanroom-run install`. A denial that doesn't belong is logged.
3. **Stuck.** The builder is stuck after the same failure three times running, 30 minutes with no new file or commit, or a denied destructive pattern. The observer gives one hint by follow-up prompt, and logs it as a backlog item. It doesn't step in before then (Geoff, 2026-11-07).
4. **Done.** The builder's final result reports the task finished, and the observer runs that task's acceptance check.
5. **Stopped short.** The builder's turn ends with a question or half-finished work. The observer answers from the design and the prototype and resumes it, or resumes it with "continue". A question they don't settle goes to Geoff.

When the shared subscription hits its usage limit, the observer waits for the reset and resumes each builder by its session id.

### Where backlog items go

Each builder keeps `BACKLOG.md` in its working repo. The brief asks it to add an item whenever the published tools left it guessing, stuck, or wrong. The observer reads that file and the log, and routes each item:

- **Engine, scaffolder, packaged skills, admin docs, and the `cairn` CLI** go to `conductor-cairn-cms` in batches, in `engine-consult`'s four-field schema with a repro and a file or page. A blocker goes at once.
- **Survey** items go to `~/Projects/survey/BACKLOG.md` as a direct commit.
- **907.life's own** items go to the new repo's `BACKLOG.md` at T13.
- **Workstation** items go to a `glw907/workstation` PR in the final packet.
- **Harness** items, caused by the clean room rather than the published tools, go in the fold record.

An item that matches an open cairn item is noted against that item, not filed again. T1 re-reads the open list from `cairn-cms/BACKLOG.md`. At planning it was #351 to #354, #204, #298, and #304.

## The theme's bar

The observer runs every check on a fresh scaffold in the `acceptance/` home: `create-cairn-site --yes` with no GitHub or deploy, with `cairn-theme/` copied into `src/theme/` from the PR's head commit, and no `cairn-audit.config.json`. Each check can fail.

1. **The audit.** `npx cairn-audit --rule public-literals --rule theme-conformance --rule theme-contrast --fail-on advisory` exits 0. Without the flag the check is empty: "All three are advisory on a consumer: a finding never changes the exit code unless the run sets the `fail-on` flag to `advisory`" (`references/checking-a-theme.md`, line 13). The report lists no unmeasured pair ("A value the resolver cannot evaluate is reported unmeasured, never passed") and no Unread imports ("never a finding"). `grep -rn cairn-audit-disable-next-line src/` exits 1, since that comment is the audit's suppression ("Suppress one finding with a comment above it", `src/lib/audit/config.ts`, line 341). As a positive control, a planted `style="color: #abc"` in `src/theme/SiteFooter.svelte` yields a `public-literals` finding naming it, then comes out (the skill's own coverage test).
2. **No `!important`.** `cairn-theme/` exists and holds files, and `grep -rn '!important' cairn-theme/` exits 1.
3. **No hand-written theme selector.** `grep -rnE '\[data-theme' cairn-theme/` exits 1. daisyUI 5 names a theme with `name:` inside `@plugin "daisyui/theme"`, so no exception is needed.
4. **Tokens and stock components.** `public-literals` covers color literals and absolute font sizes only, and "A custom-property definition is legal anywhere under a theme root" (`checking-a-theme.md`, line 20). Check 1 enforces that much. Radius and font family are graded by the verifier against Survey's token table. Every `site-` class in `cairn-theme/` is one of the five signature names, which keeps everything else on stock daisyUI.
5. **The signature details, rendered.** The served HTML of `/` carries the Survey daisyUI theme's `name` and the classes `site-contour-texture`, `site-benchmark`, `site-contour-rule`, and `site-collar`. The tags or archive route carries `site-index-rail`. Changing the collar's two site settings changes the footer's text.
6. **The prose.** `standards:visual-verifier` grades it against the Cairn site recipe's step 3, with Survey's specimen as the reference (cairn-themes commit `c19e7ac`, `survey-theme/reference/2026-10-07-approved-specimen.html`).

## Mail

Geoff's mail keeps working throughout (Geoff, 2026-11-07: "my mail needs to continue to work"). It is a requirement, and a stop condition at every step that can touch the zone: T4's dry run, T5's teardown, T6's setup sitting, and any later setup re-run.

### The mail records

- The apex MX (`servers/cloudflare/dns/mx`) and the apex SPF TXT.
- The DKIM selectors `w1-ed25519._domainkey` and `w1-rsa._domainkey`, and `_dmarc`.
- The five SRV records, the `autoconfig`, `autodiscover`, and `ua-auto-config` CNAMEs with `_ua-auto-config`, `_smtp._tls`, and `_mta-sts` (all in `dns/ward`), and the `mta-sts` Worker's host.
- The `/.well-known/{jmap,caldav,carddav}` redirects, which return 308 to `ward.907.life` today (checked 2026-11-07) and are zone-level Single Redirects (`servers/docs/decisions.md`, line 103).

Records setup adds under new names are expected, and T11 declares them.

### The redirects and the apex

Single Redirects run ahead of the Worker. They are first in the rules execution order, a redirect is a terminating action, "executed immediately" (developers.cloudflare.com/rules/url-forwarding), and "Requests handled by Workers will suppress Page Rules actions, but they will not suppress actions from modern Rules features" (developers.cloudflare.com/rules/reference/page-rules-migration). So they survive the new Worker. They don't survive a missing record: "Single Redirects require that the incoming traffic for the hostname referenced in visitors' requests is proxied by Cloudflare" (developers.cloudflare.com/rules/url-forwarding/single-redirects/create-api). Today the only proxied apex record is the old Worker's custom-domain AAAA, which the teardown removes. setup's attach writes "a proxied AAAA at the apex pointing at 100::" (`src/cloudflare/hostname.mjs`, line 12).

So the redirects are down from the moment `teardown.sh` detaches the old custom domain until setup's attach puts a proxied apex record back in T6. The plan expects that gap to last about an hour: T5's remaining steps, then T6 up to setup's domain chapter. It runs longer only if setup stops first. No placeholder bridges it. Wrangler treats an existing apex record as a conflict and overrides it only on request (`override_existing_dns_record: false`, then "You already have DNS records that conflict for these Custom Domains", wrangler's `cli.js`). cairn's attach sends no override field (`api.mjs`), so a placeholder would most likely fail setup's attach (Geoff, 2026-11-07, ruling the verification's M1). The redirects serve only a mail client's first discovery of the server. Delivery, sending, and already-configured clients don't use them. T6's acceptance checks that all three return 308 again. If they don't, that is a stop under the mail requirement.

### The mail check

The mail check runs before T5, after T5, after T6, and at T12. It uses only tools that exist, and the observer sends no mail (Geoff, 2026-11-07, ruling the verification's M3):

1. **The records, every time.** `conductor-servers` runs `cloudflare/dns.sh --check`, which is read-only with its scoped `CF_WS_SERVERS_TOKEN`, and reports no drift on any declared mail record. That covers the MX, the apex SPF, both `w1-*` selectors, `_dmarc`, the SRV records, the CNAMEs, `_smtp._tls`, and `_mta-sts`.
2. **The redirects, before T5, after T6, and at T12.** The observer runs `curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://907.life/.well-known/$p` for `jmap`, `caldav`, and `carddav`. Each prints `308 https://ward.907.life/.well-known/$p`. After T5 they are expected down, per "The redirects and the apex".
3. **One inbound message, before T5 and after T6.** In P3 before the apply, and in P4 after setup, Geoff sends one message with a marker subject from an outside mailbox he names to `glw@907.life`. ## The domain step

The domain step happens inside T6's setup sitting:

1. The observer asks `conductor-servers` to hold `dns.sh --apply` for the sitting, and records its acknowledgement.
2. It snapshots the zone's full record list through the Cloudflare API as `dns-before.json` beside the plan.
3. Geoff runs setup, which connects the domain, sign-in email, and Workers Builds.
4. The observer snapshots again as `dns-after.json`, diffs the two, runs the mail check, and releases the hold.

The step passes when the mail check passes and every record in the before snapshot is unchanged, `_dmarc` included at its declared `v=DMARC1; p=none; rua=mailto:dmarc-reports@907.life`. Every addition must also be listed by name. The zone is already onboarded for Email Sending (`cf-bounce.907.life` resolves on 2026-11-07), `ensureSendingDomain` creates nothing for an existing entry (`src/cloudflare/email.mjs`, line 94), and Cloudflare's docs say "If you already have a DMARC record, Cloudflare keeps it unchanged" (developers.cloudflare.com/email-service/reference/troubleshooting). Setup still prints "Onboarding also wrote a p=reject DMARC policy" (`chapter2.mjs`, line 1064). With `_dmarc` unchanged, that message is a cairn item.

If a pre-existing record changed, the run stops as "When the check fails" says. The observer first checks the servers repo's log for a legitimate change. A change setup made is restored through the servers path and becomes a cairn item.

## Failure modes and limits

| Case | What happens |
|---|---|
| rc.4 isn't promoted | Nothing past T4 runs. The plan waits with no time limit, since the conductor owns the release. |
| Setup finds a name clash | It stops before deploying, once the #200 fix ships. T5's acceptance has already proved the Cloudflare names are free. |
| Setup fails after the teardown | 907.life stays dark. The observer reports to Geoff at once and files a blocker with the conductor. Per the design's outage ruling, at 48 hours dark the observer brings Geoff the choice of waiting or restoring from the archive. |
| The sandbox can't start | `failIfUnavailable` stops the builder. T1 catches this before any launch. |
| A builder runs over | The stuck rule, then one hint. The ceiling is 1,200 path minutes for the whole run. |
| The ceiling or an unreachable bar ends the run | T11's DNS declarations and the setup-token deletions still run. Then the run closes and reports the bar unmet. |
| A browser approval in setup times out | Setup's loopback waits ten minutes (`src/github/loopback.mjs`, line 17). Geoff re-runs the same command, and setup resumes from its saved state in B's home. |
| A mail check fails, or a mail record changes | The run stops before anything further runs. The servers path restores the record, and the run resumes when the mail check passes. |
| The new site's PR checks fail like the old site's (#5) | It's a backlog item for cairn, and acceptance doesn't block on it. |
