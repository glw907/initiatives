# 907.life rebuild spec

Design: `907-rebuild/specs/2026-11-07-907-rebuild-design.md` (the approved shape). Plan: `907-rebuild/plans/2026-11-07-907-rebuild-plan.md`. This spec states the mechanisms the plan builds on. Each one is quoted from its source or left for T1's probe to prove.

## The clean room

### What loads

A builder is `claude -p` run with `CLAUDE_CONFIG_DIR=$HOME/.local/state/cairn-cleanroom/claude`.

- **What the variable moves.** "Override the configuration directory (default: `~/.claude`). All settings, session history, and plugins are stored under this path" (code.claude.com/docs/en/env-vars). "The same applies to `.claude.json`" (docs/en/claude-directory). Geoff's CLAUDE.md, skills, hooks, plugins, settings, and memory don't load.
- **Project files still load.** That's intended: cairn's packaged skills and `claude/CLAUDE.md` reach a site through `npx cairn-guidance install` into the site's `.claude/`, which is the newcomer's path. The builder never gets `--setting-sources user` or `--bare`. `--bare` would also break the sign-in: "In bare mode, Claude Code never reads OAuth credentials" (docs/en/headless).
- **Managed settings** load from `/etc/claude-code`, and that directory doesn't exist on pavilion (checked 2026-11-07).
- **Auto memory** is off: `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (docs/en/agent-sdk/claude-code-features). One config directory serves both builders, and "projects launched with that config directory share one auto memory directory" (docs/en/memory), so with memory on, the theme author and the site builder could read each other's notes.
- **Claude.ai connectors** "still load if you log in with a claude.ai account" (docs/en/debug-your-config). T1 reads the `system/init` event's `mcp_servers`. If Geoff's connectors appear, T1 finds the documented switch that turns them off and records it in `cleanroom-run`. If none exists, the PR records that connectors were visible, and the brief says nothing to prompt their use.
- **Trust.** "A `-p` session shows no workspace trust dialog" (docs/en/headless). Project hooks still run in an untrusted folder under `-p` (same page), which matches what a newcomer's own session would do.

### Isolation

Isolation has two layers, because neither covers both tools.

- **Read-tool deny rules**, in the clean config's `settings.json`: `Read(~/.claude/**)`, `Read(~/.local/secrets)`, `Read(~/.dotfiles/**)`, `Read(~/.config/**)`, and `Read(//var/home/glw907/Projects/*/**)`, with `cleanroom` exempt by an allow rule. Deny wins, so T1 proves the exemption works. If it doesn't, T1 lists each sibling repo instead.
- **The Bash sandbox**: `sandbox.enabled: true`, `sandbox.failIfUnavailable: true`, `allowUnsandboxedCommands: false`, and `sandbox.filesystem.denyRead` naming the same paths. "A `denyRead` entry doesn't stop the Read tool" (docs/en/sandboxing), which is why both layers are set. `bubblewrap` 0.12.0 and `socat` 1.8.1.3 are installed. The sandbox also restricts network. T1 records the domains each builder needs (the npm registry, github.com and its API, Cloudflare's API and dashboard, fonts, the Survey repo) under the sandbox's network allow key, read from docs/en/sandboxing at T1.
- **When the sandbox breaks the run.** If it breaks setup's local OAuth callback (GitHub's App manifest flow, or `wrangler login`), the documented `excludedCommands` route runs `npx create-cairn-site` and `npx wrangler` unsandboxed, and the Read deny rules still hold. T1 proves whichever form works. The PR records what ran unsandboxed.
- **Command deny rules**: `Bash(*907-life-legacy*)`, `Bash(*cairn-build*)`, and `Bash(*cairn-907-auth*)`. Deny is evaluated first: "If a tool is denied at any level, no other level can allow it" (docs/en/permissions).

### Permissions and accounts

- **Permission mode.** `--permission-mode auto`, which "needs a supported model" (docs/en/permission-modes). If T1 finds auto unavailable in `-p`, the builder runs `dontAsk` with an allow list: `Edit`, `Write`, `WebFetch`, `WebSearch`, and `Bash(npm *)`, `Bash(npx *)`, `Bash(node *)`, `Bash(git *)`, `Bash(gh *)`, `Bash(ls *)`, `Bash(cat *)`, `Bash(mkdir *)`, `Bash(cp *)`, `Bash(mv *)`. In `dontAsk`, "anything that would prompt is denied" (same page), and each denial appears as a `permission_denied` event the observer reads.
- **Accounts start signed out.** The builder gets its own `XDG_CONFIG_HOME` under the clean-room state directory, so `wrangler` and `gh` start signed out, as they would for a newcomer. Wrangler keeps its sign-in under `~/.config/.wrangler` on this machine (checked). T1 proves `npx wrangler whoami` and `gh auth status` both report signed out. `gh auth login` then joins Geoff's setup sitting.

### Logs and follow-ups

- **Logs.** Each run uses `--output-format stream-json --verbose`, with its session id chosen up front by `--session-id <uuid>` (docs/en/cli-reference). The log goes to `~/Projects/cleanroom/logs/<builder>-<n>.jsonl`.
- **Follow-ups.** A follow-up prompt is `claude -p "<text>" --resume <uuid>`, repeating the permission flags, since a resumed run "starts in the permission mode a new `claude -p` run would start in" (docs/en/sessions). `cleanroom-run` wraps both.

## The observer

907-life-e7 watches each builder's log with the Monitor tool. It acts on four events:

1. **A browser approval.** A URL to github.com, dash.cloudflare.com, or a localhost callback appears, or setup prints that it opened the browser. The observer runs `notify-send -u critical "907 rebuild: approve in your browser"` and names the step in chat.
2. **A permission denial.** If the action belongs in the build, the observer widens the rule and resumes the builder. If it doesn't, the denial is logged.
3. **Stuck.** The builder is stuck after the same failure three times running, 30 minutes with no new file or commit, or an action that would damage something. The observer gives one hint by follow-up prompt, and logs it as a backlog item. It doesn't step in before then (Geoff, 2026-11-07).
4. **Done.** The builder's final result message arrives, and the observer runs that task's acceptance check.

### Where backlog items go

Each builder keeps `BACKLOG.md` in its working repo. The brief asks it to add an item whenever the published tools left it guessing, stuck, or wrong. The observer reads that file and the log, and routes each item:

- **Engine, scaffolder, packaged skills, admin docs, and the `cairn` CLI** go to `conductor-cairn-cms` in batches, in `engine-consult`'s four-field schema with a repro and a file or page. A blocker goes at once.
- **Survey** items go to `~/Projects/survey/BACKLOG.md` as a direct commit.
- **907.life's own** items go to the new repo's `BACKLOG.md` at T13.
- **Workstation** items go to a `glw907/workstation` PR in the final packet.

An item that matches an open cairn item (#351 to #354, #204, #298, #304) is noted against that item, not filed again.

## The theme's bar

Each check below can fail.

1. `npx cairn-audit --rule public-literals --rule theme-conformance --rule theme-contrast` exits 0 on a scaffold that carries the theme, with no suppression or config exemption added for it.
2. `grep -rn '!important' cairn-theme/` prints nothing.
3. No selector in `cairn-theme/` names a `data-theme` value, apart from the two `@plugin "daisyui/theme"` blocks.
4. Every color, radius, and font comes from a Survey token value or a daisyUI variable. A literal outside the two theme blocks fails check 1's `public-literals` rule.
5. All five signature classes from Survey's `DESIGN.md` render on the scaffold's home page: `site-contour-texture`, `site-benchmark`, `site-contour-rule`, `site-collar`, and `site-index-rail`. The index rail appears on the tags or archive list. The collar's two fields come from site settings.
6. The prose follows the Cairn site recipe's step 3, checked by the verifier against Survey's specimen (cairn-themes commit `c19e7ac`, `survey-theme/reference/2026-10-07-approved-specimen.html`).

## The domain step

T10 runs after the new-site packet is approved:

1. Snapshot the zone's full record list through the Cloudflare API, and save it as `dns-before.json` beside the plan.
2. Resume builder B with `CAIRN_CF_API_TOKEN` set. It runs setup with `--domain 907.life`, then `--connect`.
3. Snapshot again as `dns-after.json`, and diff the two.

It passes when every record in the before snapshot is unchanged, `_dmarc` included. Cloudflare's docs say "If you already have a DMARC record, Cloudflare keeps it unchanged" (developers.cloudflare.com/email-service/reference/troubleshooting). A changed or deleted record fails the step. The observer then restores that record from the before snapshot by API, and files a blocker with the conductor.

## Failure modes and limits

| Case | What happens |
|---|---|
| rc.4 isn't promoted | Nothing past T4 runs. The plan waits with no time limit, since the conductor owns the release. |
| Setup finds a name clash (the old resources weren't torn down) | It stops before deploying, once the #200 fix ships. T5's acceptance has already proved the names are free. |
| The setup token is missing at T10 | Setup stops at `token-missing`, and the plan's P2 fallback applies. |
| The sandbox can't start | `failIfUnavailable` stops the builder. T1 catches this before any launch. |
| A builder runs over | The stuck rule, then one hint. The ceiling is 1,200 path minutes for the whole run. |
| A browser approval isn't clicked within 10 minutes | Setup's own timeout applies. The observer pings again, and the re-run resumes from setup's saved state (`--dir`). |
| The new site's PR checks fail like the old site's (#5) | It's a backlog item for cairn, and acceptance doesn't block on it. |

## End-to-end check

At the close, a visitor reaches `https://907.life` and sees variant A in Survey's look, light or dark by system setting. From there, every one of the eight posts and four project pages opens. You sign in at `/admin` from an emailed link, edit a project's summary, and publish. The change shows on the live site after Workers Builds deploys it. Mail to and from 907.life still passes DKIM, and `_dmarc` still reads `p=none` with its report address.
