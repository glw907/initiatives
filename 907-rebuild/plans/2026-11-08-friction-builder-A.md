# BACKLOG: cairn instructions, from building Survey as a cairn theme

Each item is a place where cairn's published instructions (npm package docs, skills, scaffold) were missing, unclear, or wrong, or made me read much more than the step needed. Versions: `@glw907/cairn-cms` 0.98.0 (npm `latest`) and 0.99.0-rc.4 (what `create-cairn-site@latest` installs).

## Open

1. **The engine's `latest` and the scaffold's `latest` are different releases.** `npm view @glw907/cairn-cms` shows `latest: 0.98.0`, while `create-cairn-site@latest` is 0.99.0-rc.4 and pins `@glw907/cairn-cms ^0.99.0-rc.4`. I read the 0.98.0 docs first and they turned out to be laid out differently from what the site uses: `docs/extend/` and `docs/reference/` are gone from the 0.99 package, and the skill `cairn-public` became `cairn-styling-public-pages`. The repo README and `docs/README.md` don't say which version the docs describe, or that a release candidate is what a new site gets. Fix: promote 0.99 or pin the scaffold to the engine's `latest`, and print the engine version in the scaffold's "Next" output.

2. **"Theme" means two different things, and neither is "a theme you ship".** In 0.98, `docs/extend/design-your-site.md` says "One file owns the look: your own `src/theme/theme.css`", while `theme-directory.md` says a theme from scratch supplies nine files, including `cairn.config.ts` (concepts, backend) and `site-config.ts`, which are site content, not look. Nothing says how to package a theme outside one site (for example a folder in a design-system repo) or which of those files a reusable theme should leave to the site. The 0.98 `checking-a-theme.md` hints at an overlay model ("the directory needs only the files it replaces") but only for a script in the cairn-cms repo. Fix: a page called "Ship a theme for other sites", naming the look-only files a theme overlays and the site-owned files it must not ship.

3. **The design-scale names collide with any design system that has its own `--text-step-*` scale, and nothing warns about it.** The chassis `tokens.css` owns `--text-step--2` through `--text-step-5` as the reading scale (h1 is `--text-step-5`). Survey's `theme/survey.css` defines `--text-step-1` through `--text-step-13` as small interface sizes (0.64rem to 1.6rem) in `@theme`. If you follow Survey's cairn-site recipe and import `survey.css` into `theme.css`, every heading shrinks to Survey's interface sizes, with no error. The docs say a theme "redeclares the same keys", which assumes a theme has no prior vocabulary. Fix: in the retheme or theme-starter page, say which namespaces the chassis owns, and that an existing design system has to map its values onto those names rather than import its own `@theme` block over them.

4. **Renaming the themes reaches outside the theme directory.** A theme with its own daisyUI names (here `survey` and `survey-dark`) has to edit the cookie regex in `src/app.html` as well as `theme-names.ts`, so a theme can't be dropped into `src/theme/` on its own. The retheme page does document this, under "Renaming a theme", and `theme-names.test.ts` catches the drift. Fix: have `app.html` read the names from a generated file, or have the chassis inject the script from `theme-names.ts`.

5. **Eyebrows hard-code `uppercase` in route markup, with no setting behind it.** `--cairn-heading-case` controls headings, but the "Latest" and "Archive" eyebrows on the home and archive routes carry the `uppercase` utility in `src/routes/`, outside the theme. A theme with no all-caps labels has to override the utility with an unlayered rule. The tokens.css comment says this on purpose ("an eyebrow keeps its `uppercase`"), but no theme page tells you how to turn it off. Fix: an `--cairn-eyebrow-case` role beside `--cairn-heading-case`.

6. **`/styleguide` is documented but the scaffold doesn't ship it.** The 0.98 `design-your-site.md` sends you to iterate against `/styleguide`, and `public-css.md` says the CTA keys style "the styleguide's call-to-action panel". The 0.99 scaffold has no `/styleguide` route, so there's no page that shows every directive under a theme. Fix: ship the route, or drop the references and say which content page to check against instead.

7. **A theme test fails on a fresh scaffold until `svelte-kit sync` runs.** `npx vitest run src/theme/theme-names.test.ts` fails with "Failed to load tsconfig '$app/tsconfig'" until `npx svelte-kit sync` has run, and the `test:unit` script doesn't run it first (`check` does). Fix: add a `pretest:unit` script that runs `svelte-kit sync`.

8. **The audit's coverage has to be proved by hand.** `cairn-audit` with all three public rules printed "0 advisories", which also happens when the theme isn't in scope at all. `checking-a-theme.md` says to confirm coverage by planting a color literal and looking for the finding, which worked but meant two edits and a revert. Fix: have the audit list the theme files and daisyUI blocks it measured, e.g. `theme-contrast: measured survey, survey-dark (src/theme/theme.css)`.

9. **The chassis's scroll-edge cue has no off switch.** `prose.css` draws a gradient cue on `pre` and `.table-scroll`, and the `--cairn-*` roles don't cover it. A theme with no gradients finds it only by eye in a screenshot, then overrides `background-image` on two selectors. The prose-code and prose-tables catalogue pages don't mention it. Fix: a `--cairn-scroll-cue` role (or a `data-` opt-out), and a line on both catalogue pages.

10. **The docs don't say which selector a site-owned `--cairn-*` override takes, and the engine's own default shows the wrong one.** `cairn-public.css` declares its defaults (the `--cairn-code-*` ramp among them) on `:root, [data-theme]`, so I copied that pair into `survey-site.css`. Review rejected it, because a theme must not hand-write a theme selector when daisyUI 5 names a theme with `name:` in `@plugin "daisyui/theme"`. The docs don't settle it either way. The chassis README says to declare an override "in its `:root` or daisyUI block". The table in `retheme-by-tokens.md` puts the code keys in "the block", which could mean either one. Neither page says that plain `:root` is enough only because the scaffold's `app.html` sets `data-theme` on `<html>`, or that a `var()` in a `:root` override resolves at the root. To decide, I had to read `app.html`, `theme-toggle.ts`, the built CSS, and the static-cascade notes in `checking-a-theme.md`. Fix: in `retheme-by-tokens.md`, give each key's home as a literal selector (`:root`, or inside each `@plugin "daisyui/theme"` block). Say a theme never writes `[data-theme]` itself, and add a short comment in `cairn-public.css` explaining why the engine's own default needs `[data-theme]` and a theme's override doesn't.
