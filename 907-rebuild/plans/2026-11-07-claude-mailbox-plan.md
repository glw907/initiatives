## Brief

This plan builds servers BACKLOG #65: one more Stalwart account on ward, `a-claude`, whose public alias is `claude@907.life`. Claude sends from it with an app password that can sign in, send, and read the mailbox it belongs to, and nothing else. A helper, `scripts/claude-mail.sh`, sends only to a fixed list and reads the mailbox through `tech-mail.sh`'s banner. Ward itself refuses the account's mail to any address off that list at the RCPT stage. A session that went around the helper would still be stopped there. The list starts with Geoff's aksailingclub.org Google Workspace address, the mailbox the Gmail connector reads. With it a session can prove 907.life's outbound DKIM and DMARC without Geoff, as the rebuild's close check (P6) needs.

The path is 300 minutes, 60 over the design's 240 and under the 480 ceiling. The overrun is the RCPT proof: the probe needs seven rows (an on-list send, two off-list sends, a mixed send, a JMAP send, another account's send, and an inbound message) and a second ward apply to take the rehearsal list off `probe2`. Recent servers passes ran at 40 to 75 percent of plan.

The account's login is unpublished and can't be guessed, so this public plan names it only as `<claude login>`, and its account name, the login's local part, as `<claude name>`. T3 generates both, and the executor reads them from the private servers repo (`roles/stalwart/accounts.json`) or `~/.local/state/claude-mailbox/` (mode 700). The recipient address appears only in the private servers repo. Every file this pass writes to a public repo, every workstation commit message, and both PR bodies pass `~/Projects/servers/scripts/privacy-check.sh` (exit 0) before they are committed or posted.

### Facts found at planning

These correct or settle the design's wording without changing its outcome. Each goes in the servers PR's `## Decisions` and in `docs/decisions.md`. Stalwart source is quoted at tag `v0.16.27`, the pinned image (`roles/stalwart/install.sh:11-13`).

1. **An SMTP submission needs `authenticate` and `emailSend`, and nothing more.** Every sign-in asserts `Permission::Authenticate` (`crates/common/src/auth/authentication.rs:41-44`). SMTP AUTH then asserts `Permission::EmailSend` (`crates/smtp/src/inbound/auth.rs:110-120`). Without it the server answers `550 5.7.1 Your account is not authorized to use this service` at AUTH (`auth.rs:159-167`), which is the refusal pass B's check recorded for the read-only reader. So the seven names in "Calls" cover a send on 465. T2 still proves the set live, and the standing answer covers a surprise.
2. **Port 465 is the workstation's submission port.** Port 587 is open to orpheus only (`scripts/lib/app-password-check.sh:20-21`, `docs/decisions.md:216`). `plan.ndjson:2` declares only the 587 listener; 465 is Stalwart's stock implicit-TLS listener, which the setup scripts and the runbook already use (`docs/runbook.md:293, 546`).
3. **`MtaStageRcpt` has no refusal field of its own.** Its fields are `allowRelaying`, `maxFailures`, `maxRecipients`, `rewrite`, `script`, and `waitOnFail`, each an expression (ward's schema, cached by `stalwart-cli` under `~/.cache/stalwart-cli/`, object `x:MtaStageRcpt`; <https://stalw.art/docs/ref/object/mta-stage-rcpt>). The refusal is a system Sieve script (`x:SieveSystemScript`: `name`, `contents`, `isActive`, `description`) that the `script` expression names, as the forum answer does (<https://support.stalw.art/t/how-to-block-outbound-email-address/1233>). At RCPT, Stalwart evaluates `script`, loads the named script as a trusted one, and on a `reject` pops the recipient and writes the reject text as the reply (`crates/smtp/src/inbound/rcpt.rs:93-104, 117-137`). The default is `false`, so today no script runs. In this repo's format the rule is two lines: an `update` of `MtaStageRcpt` whose `script` is `{"match":{"0":{"if":"authenticated_as == '<login>'","then":"'send-only-list'"}},"else":"false"}`, in the shape `plan.ndjson:13` uses for expressions, and an `upsert` of `SieveSystemScript` matched on `name`.
4. **`authenticated_as` is the full login.** `AccountInfo::name()` returns the cached account name (`crates/common/src/cache/principals.rs:948-950`), built as `<name>@<domain>` (`principals.rs:409-413`), and SMTP's accessor returns it (`auth.rs:203-208`). Inbound mail has no `authenticated_as`, and every other account's differs, so an expression keyed on one login runs the script for that account alone. Because the login is private, the rule can't sit in `plan.ndjson`; `build-plan` renders it from `accounts.json` (fact 7).
5. **JMAP sends pass the same RCPT stage.** `EmailSubmission/set` opens a local SMTP session as the account and calls `handle_mail_from`, then `handle_rcpt_to` for each recipient (`crates/jmap/src/submission/set.rs:682-711`). So the rule binds an SMTP or JMAP submission made with the account password too, which Claude's ward applies hold (fact 11). The forum's claim holds in source. It doesn't bind mail the server generates for the account: a user Sieve `redirect` or a vacation reply goes out as an autogenerated message and skips the RCPT stage (`crates/email/src/sieve/ingest.rs`, near line 430). So T3 turns off the account's Sieve-script and vacation-response writes (see "Calls").
6. **At RCPT the envelope's `to` is the current recipient alone, lowercased** (`crates/smtp/src/scripts/exec.rs:93-97`, the `stage != "data"` branch). A message to a listed address and an unlisted one loses only the unlisted one, and a listed address can't carry an unlisted one past the rule.
7. **The list can't live in `scripts/`.** The design names `scripts/claude-mail.recipients`, but `scripts/apply.sh:98` ships only `base/` and `roles/<role>/` to ward, and `install.sh:60-62` installs `plan.ndjson`, `accounts.json`, and `build-plan` into `/usr/local/share/servers`. ### Calls this plan makes

The design leaves these to the builder. A reviewer may contest any of them.

- **The list is `sendOnlyTo` in `accounts.json`** (fact 7). Each entry is lowercased and must match `^[a-z0-9._+-]+@[a-z0-9.-]+\.[a-z]+$`, since it lands inside a Sieve string. `build-plan` refuses a second account with a list, so one script name, `send-only-list`, serves the one account that has one.
