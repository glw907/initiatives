# Research: how documentation systems express an ordered, nested page tree with prev/next, and what cairn has today

Read-only. No code changed. Every external claim has a URL; every local claim has a file:line. "Not verified" marks anything I could not confirm on a primary page. Part 2 proposes no design. Part 3 is labeled interpretation and picks nothing.

## Part 1. How other systems do it

### Starlight
- Tree lives in `starlight.sidebar` in astro.config.mjs. With no config, the sidebar is built from the filesystem using page titles. Entries are `slug` or `link`; groups are `{label, items}`; `autogenerate: {directory}` and `collapsed` exist. https://starlight.astro.build/guides/sidebar/ and https://starlight.astro.build/reference/configuration/
- Per-page frontmatter `sidebar.order` (lower sorts higher), `sidebar.label`, `sidebar.hidden`, `badge`, `attrs`; these apply only to autogenerated and slug links. Default order is "alphabetical according to the file `id`." https://starlight.astro.build/reference/frontmatter/
- Prev/next: `pagination` option (default true) and per-page `prev`/`next` frontmatter (`false`, a string, or `{link,label}`). That arrows derive from the sidebar is not stated on the reference page; a discussion summary says so (secondary, via search): https://github.com/withastro/starlight/discussions/974
- Whether a group can itself be a page: not stated.
- Pain: directory order under autogenerate has no core fix; a maintainer pointed to the third-party `starlight-auto-sidebar`. https://github.com/withastro/starlight/discussions/969 and https://github.com/withastro/starlight/discussions/1609. Folders sort by their first page's order, reported as a bug, open; suggestions include index.md frontmatter, a directory config file "similar to Docusaurus", numeric prefixes. https://github.com/withastro/starlight/issues/1223

### Docusaurus
- `sidebars.js`; with no sidebarPath the sidebar is autogenerated ("each folder creates a sidebar category, and each file creates a doc link"). Explicit items are `doc`, `category`, `link`. https://docusaurus.io/docs/sidebar
- Autogenerated order: alphabetical by file or folder name; `sidebar_position` frontmatter; number prefixes (stripped from ids and URLs); per-folder `_category_.json|yml` with `label`, `position`, `collapsible`, `collapsed`, `link`, `className`, `key`, `customProps`. A category's own page is `index`, `README`, or a doc named like the folder; `link: {type:'generated-index'}` or `link: null` are options. Docs say "Prefer using additional metadata" over number prefixes (renaming prefixes may break links). https://docusaurus.io/docs/sidebar/autogenerated
- Prev/next follow the sidebar; frontmatter `pagination_next`, `pagination_prev` (doc id or null), `pagination_label`. https://docusaurus.io/next/api/plugins/@docusaurus/plugin-content-docs
- Direction of change: PR "auto-generated sidebars, frontmatter-less sites" aimed to "infer the sidebar from the FS structure" and moved from number prefixes to `sidebar_position`; stripping prefixes was called a breaking change. https://github.com/facebook/docusaurus/pull/4582
- Pain (secondary, via search): folder and same-name file both appear, https://github.com/facebook/docusaurus/discussions/5327; request to infer position from filename prefix, https://github.com/apify/apify-docs/issues/1247

### VitePress
- `themeConfig.sidebar`, hand-written, no autogeneration; array or object keyed by path for multiple sidebars; groups `{text, items, collapsed, link, base}`; nesting deeper than 6 levels is ignored. https://vitepress.dev/reference/default-theme-sidebar
- Prev/next inferred from the sidebar; frontmatter `prev`/`next` string, `{text, link}`, or `false`. https://vitepress.dev/reference/default-theme-prev-next-links
- Pain: auto sidebar requested, not built in, open https://github.com/vuejs/vitepress/issues/1297; a duplicate closed "not planned" https://github.com/vuejs/vitepress/issues/2327

### MkDocs and Material
- `nav` in mkdocs.yml. Absent, files are listed "alphanumerically sorted, nested list"; "Index files will always be listed first within a sub-section"; section title is the nav key; "A section cannot have a page assigned to it"; pages not in nav still build but are left out of prev/next links. https://www.mkdocs.org/user-guide/configuration/ and https://www.mkdocs.org/user-guide/writing-your-docs/
- Material adds `navigation.indexes` (attach `index.md` to a section), `navigation.tabs`, `navigation.sections`, `navigation.expand`, `navigation.prune`; footer prev/next via `navigation.footer`, hidden per page with `hide: - footer`. https://squidfunk.github.io/mkdocs-material/setup/setting-up-navigation/ and https://squidfunk.github.io/mkdocs-material/setup/setting-up-the-footer/ (derivation of prev/next not stated there).
- Pain: sections cannot have their own page and no per-subdirectory YAML nav, per https://oprypin.github.io/mkdocs-literate-nav/ ; directory order hard to control, no maintainer fix, https://github.com/mkdocs/mkdocs/issues/3356 ; the awesome-pages plugin exists to give control "without having to write the entire thing by hand" via per-directory files (field names not verified), https://github.com/lukasgeiter/mkdocs-awesome-pages-plugin and issue https://github.com/lukasgeiter/mkdocs-awesome-pages-plugin/issues/99
- Theme boundary evidence: Material's blog (an interested party, author of a competing fork) says MkDocs 2.0 passes "navigation ... to themes as pre-rendered HTML", making "navigation tabs, collapsible sections" "technically impossible". https://squidfunk.github.io/mkdocs-material/blog/2026/02/18/mkdocs-2.0
- Zensical (successor project): auto nav from folders by default, explicit `nav` for control, `navigation.indexes` for section index pages, https://zensical.org/docs/setup/navigation/ ; a newsletter says it is prototyping per-section `nav.toml` files, https://mail.zensical.org/monthly/2026/02/index.html (prototype only).

### Nextra
- Co-located `_meta.{js,jsx,ts,tsx}`: key order is sidebar order, unlisted routes are appended alphabetically, `index` first; per-key titles; `type: 'page'|'separator'|'menu'`, `display: 'hidden'`; folder index via `asIndexPage: true`. https://nextra.site/docs/file-conventions/meta-file . The doc mentions no `_meta.json` (a removal commit seen only in search snippets: not verified).
- Nextra 4 adds a single `_meta.global` file (cannot be mixed with `_meta`; folder items need `items`); sidebar title priority is `_meta` title, `sidebarTitle`, `title`, first h1, filename. https://the-guild.dev/blog/nextra-4
- Prev/next: `navigation` prop default true, per-page `theme.pagination: false` in `_meta`; ordering source not stated. https://nextra.site/docs/docs-theme/built-ins/layout

### Fumadocs
- Folder structure maps to the page tree; per-folder `meta.json` (`title`, `icon`, `description`, `root`, `defaultOpen`, `collapsible`, `pages`, `pagesIndex`). Default alphabetical; `pages` array with `...` rest, `z...a` reversed rest, `!item`, separators `---Label---`, links; items not listed are excluded unless `...` is present; `index` is the folder index; `(group)` folders do not change slugs. https://www.fumadocs.dev/docs/page-conventions
- Footer prev/next "shows the neighbour pages found from page tree", overridable. https://www.fumadocs.dev/docs/ui/layouts/page

### Hugo themes
- Sidebar from the content tree; `_index.md` marks a section; order by front matter `weight` (Hugo default sort: weight ascending, date descending, title, path). https://gohugo.io/quick-reference/page-collections/
- Docsy: "ordered by page or section index `weight` (or by page creation `date` if `weight` is not set)"; `Title`/`linkTitle`; `toc_hide`. https://www.docsy.dev/docs/adding-content/navigation/ . Docsy prev/next: not found.
- Hextra: alphabetical by default, `weight` to reorder, prev/next via `PrevInSection`/`NextInSection`. https://imfing.github.io/hextra/docs/guide/organize-files/
- Hugo Book: `weight` ("Lower values appear first", none means alphabetical), `bookCollapseSection`, `bookFlatSection`, `bookHidden`. https://book.alxs.dev/docs/ . Prev/next: not verified.

### Just the Docs
- Front matter `title`, `parent` (by title), `nav_order`; top level alphabetical by title by default; numeric `nav_order` before strings; ties "unstable"; unlimited depth ("Older versions restricted navigation to three levels"); `has_children` "now redundant"; titles must be unique among siblings. https://just-the-docs.com/docs/navigation/main/ and https://just-the-docs.com/docs/navigation/main/order/ . Prev/next: not verified.

### mdBook
- Central `SUMMARY.md`: "Without this file, there is no book"; parts (`#` headers, unclickable), nested numbered chapters, prefix and suffix chapters, draft chapters, separators. https://rust-lang.github.io/mdBook/format/summary.html . Prev/next derivation and unlisted-file behavior: not stated there.

### GitBook
- Central `SUMMARY.md` (path via `.gitbook.yaml` `structure.summary`); if missing "it infers navigation from your folders and Markdown files"; `##` headings are page groups (top level only), nested links are subpages, each file once, link title sets the nav label. https://gitbook.com/docs/integrations/git-sync/content-configuration
- Non-developer editing: drag and drop in the table of contents ("Nest pages by dragging and dropping a page below another"), plus-icon to insert, groups via Add new > Group; "no limit to page nesting, but avoid more than three levels". https://gitbook.com/docs/create-content/content-structure/page . GitBook "creates or updates SUMMARY.md when you change navigation"; whether Git Sync commits that back: not stated. Prev/next: not verified.

### Mintlify
- Central `docs.json` `navigation` with recursive groups `{group, pages, icon, tag, root, expanded}`, plus tabs, anchors, dropdowns, versions; order is list order; `root` sets a group's own page. https://www.mintlify.com/docs/organize/navigation.md . Unlisted-page behavior: not on the primary page (search summaries only). Prev/next: not verified.
- Web editor: "Drag elements in Navigation to reorder or nest them", plus button to add pages and groups, dragging a folder creates a group; the editor "writes your changes to docs.json when you publish". https://www.mintlify.com/docs/editor/navigation
- Redesign evidence: mint.json to docs.json, "Logic spread across versions, anchors, and tabs made it harder to maintain and predict navigation behavior"; moved to a single recursive field. https://mintlify.com/blog/refactoring-mint-json-into-docs-json

### Docsify
- Manual `_sidebar.md` with `loadSidebar: true`; per-folder `_sidebar.md` with fallback to the parent; auto TOC from headings via `subMaxLevel`. https://raw.githubusercontent.com/docsifyjs/docsify/develop/docs/adding-pages.md . Prev/next in core: not verified.

### Sphinx
- Hierarchy lives in `toctree` directives inside document bodies; order is listed order, with `:glob:` (alphabetical), `:reversed:`, `:hidden:`, `:maxdepth:`, `:caption:`. "Sphinx knows the relative order of the documents" and generates "next chapter", "previous chapter", "parent chapter" links; a document in no toctree warns, `orphan` metadata opts out. https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html

### Zola and its book theme
- Section `_index.md` fields `sort_by` (default none; date, title, weight), `weight` default 0; a page missing the sort data "will be ignored and won't be rendered"; `page.lower`/`page.higher` give prev/next within the sorted section. https://www.getzola.org/documentation/content/section/
- Book theme: chapters are sections with `_index.md` `weight` as chapter number and `sort_by = "weight"`; subchapters are pages with `weight`; numbering on by default. https://raw.githubusercontent.com/getzola/book/master/README.md

### Jupyter Book
- v2 moved the TOC from `_toc.yml` to `project.toc` in `myst.yml` (`file`, `title`, `children`, `url`; `sections` became `children`). The stated reason for a separate toc file: "Content contributors can edit the TOC structure without touching infrastructure configuration"; the reason for the v2 move is not stated. https://jupyter-book.readthedocs.io/stable/authoring/table-of-contents and https://ebp.jupyterbook.org/en/latest/blog/2024-05-20-jupyter-book-myst/ . Implicit TOC from the filesystem when no `toc`: search summary only.

### Antora
- AsciiDoc `nav` files registered on the component version, unordered lists nested at any depth. https://docs.antora.org/antora/latest/navigation/ . Auto-from-folders and prev/next: not stated.

### Quarto
- `website.sidebar.contents` list of pages (`href`) and `section`s with nested `contents`; `contents: auto` includes all documents, `auto:` globs can sit inside a manual list. "Order is alphabetical (by filename) unless a numeric `order` field is provided in document metadata." A directory becomes a section titled from the directory name, `index.qmd` can supply the title. Prev/next via `page-navigation: true` (off by default for websites), derived from sidebar order, and a separator stops pagination across it. https://quarto.org/docs/websites/website-navigation.html (a section also linking to a page appears in an example; the page does not describe it).

### Tally by primary mechanism (my count from the above)
- Folder structure derives the tree by default, with metadata to adjust: Starlight, Docusaurus, Quarto, Zola, Hugo themes, Fumadocs, Nextra, MkDocs/Material/Zensical (default), GitBook and Jupyter Book (fallback only).
- A central file states the tree: VitePress, mdBook, Docsify, Mintlify, Antora, GitBook, Jupyter Book, MkDocs `nav`, and the explicit modes of Starlight, Docusaurus, Quarto.
- Per-page front matter carries order (and sometimes parent): Starlight `sidebar.order`, Docusaurus `sidebar_position`, Quarto `order`, Hugo `weight`, Zola `weight`, Just the Docs `nav_order` plus `parent`.
- Per-folder metadata file: Docusaurus `_category_.json`, Fumadocs `meta.json`, Nextra `_meta`, awesome-pages, Zensical prototype `nav.toml`.
- In-body tree: Sphinx toctree.
- Prev/next: where stated (Docusaurus, VitePress, Fumadocs, Quarto, Sphinx, Zola) it is derived from the same order as the sidebar, with a per-page override.

### Direction of change
- Docusaurus moved from hand-written sidebars toward autogeneration plus frontmatter and `_category_` files (PR #4582 above).
- Mintlify collapsed several navigation fields into one recursive field (blog above).
- Jupyter Book moved the TOC into one project file (above).
- Starlight and VitePress users ask for auto with ordering control (issues above).
- MkDocs users add per-folder files; Zensical prototypes `nav.toml` (above).
- Nextra added a global `_meta.global` beside per-folder `_meta` (above).
- Recurring pain across these: ordering and labeling of folders under auto mode; sections with no page of their own; number-prefix filename churn that breaks links.

### Not verified or gaps
Prev/next derivation for Docsy, Hugo Book, Just the Docs, Docsify core, mdBook, GitBook, Mintlify, Zola book theme, Antora, Nextra; Starlight prev/next-from-sidebar (search summary only); Starlight group-as-page; awesome-pages field names; Mintlify unlisted-page behavior; GitBook Git Sync commit-back; Nextra `_meta.json` removal; MkDocs 2.0, ProperDocs and Zensical claims are partly secondary and the Material blog is an interested party; Docusaurus discussion links came via search mirrors. ReadMe, Fern, Read the Docs and others were not researched.

## Part 3. Interpretation (mine, not a recommendation; no pick)

Candidates the existing pieces could express for a docs page tree, side by side. "New surface" is what the current code lacks for that candidate.

1. Central tree in site.config.yaml (the VitePress, mdBook, Mintlify, Jupyter Book family)
   - Reuses: the `menus.<name>` NavNode tree, `validateNavTree`, `readMenu`, the `/admin/nav` editor with drag and indent (comparable to GitBook and Mintlify web editors).
   - New surface: a second editable menu (`editor.nav` takes one `NavMenuConfig`); a URL picker that resolves permalinks (today `/${id}`); a depth beyond 2; prev/next computed by flattening the tree (none exists); keeping the tree in step when a page is renamed or deleted (a page absent from the tree is a case every system above handles differently).
2. Per-page front matter (the Starlight `sidebar.order`, Hugo `weight`, Quarto `order`, Just the Docs `nav_order` plus `parent` family)
   - Reuses: declared concept fields (number, reference, text exist), `summaryFields`, title-sorted default.
   - New surface: a tree builder from content; an editor control to order entries (none exists across entries); tie and default rules; how a group header without a page is expressed.
3. Folder-derived tree (the Docusaurus, Fumadocs, Hugo, Quarto autogeneration family)
   - Reuses: nothing directly; this contradicts the flat-concept rule.
   - New surface: nested folders in a concept (currently refused at types.ts:83 and BACKLOG.md:999-1000), nested permalinks, index pages or folder metadata, admin UI for folders; the largest surface of the four.
4. Per-folder metadata file (`_category_.json`, `meta.json`, `_meta`)
   - Same nesting prerequisite as 3, plus a new file type edited in the admin.

Theme boundary: scope-verdict-361 puts per-theme content or directives out of scope, and a theme today receives menu data from a layout load and renders it (SiteHeader.svelte:42-46). The MkDocs 2.0 criticism (pre-rendered navigation handed to themes) is the one external piece of evidence about handing a theme a tree versus HTML; its source is an interested party.
