## Brief

This plan builds a second mailbox on ward for technical mail. Reports, alerts, and vendor mail go to it. `glw@907.life` is its public alias, and Claude reads it with an app password that can read and do nothing else. The role addresses `postmaster@`, `dmarc-reports@`, and `tls-reports@` move to it from Geoff's account, and `abuse@` and `security@` (RFC 2142) are new. Geoff's Sieve script stops filing role mail and redirects a short list of alerts, matched by sender and subject together, to the new mailbox. A reader script prints that mailbox's mail inside an untrusted-content banner. The servers branch also clears BACKLOG #34 and #49's redirect clause, and the setup script retires the dead PikaPods names (#30). The workstation branch carries pass B's rows of the design's infrastructure table: the CLAUDE.md Email line, the auto mode text, the reader's allow rule, and `mail-tend`.

The path is 445 minutes, 85 over the design's 360 and under the 720 ceiling. The overrun comes from three pieces of work. The probe needs a reviewed script to run under auto mode. Ward's apply wipes an app password today, so `build-plan` must keep it, and a live proof of that runs on the `probe` account. The setup script checks its result before it stores anything. Recent servers passes ran at 40 to 75 percent of plan, so the run should finish near the design's figure.

The probe needs one allow rule the design did not foresee, pinned to this pass's worktree. Pass A's workstation PR carries it, since that PR already edits `permissions.allow`, so Geoff approves it in pass A's packet, and pre-flight P1 only checks that it is in place. After the merge, Geoff runs `scripts/tech-mailbox-setup.sh` once. That is the design's one set point.

The technical mailbox's login is unpublished and can't be guessed, so this public plan names it only as `<tech login>`, and its account name, the login's local part, as `<tech name>`. T3 generates both. The executor reads them from the private servers repo (`roles/stalwart/accounts.json`) or the private state folder `~/.local/state/credential-hygiene/`. Every file this pass writes to a public repo, every workstation commit message, and both PR bodies pass `~/Projects/servers/scripts/privacy-check.sh` (exit 0) before they are committed or posted.

### Facts found at planning

Each one goes in the servers PR's `## Decisions` and in `docs/decisions.md`. Stalwart source is quoted at tag `v0.16.27`, the pinned image (`roles/stalwart/install.sh:13`).

1. **Ward's apply drops an app password, by the source's reading.** `roles/stalwart/build-plan:29-37` upserts every account with `credentials: {"0": {"@type": "Password", ...}}`, and `stalwart-apply:135-136` applies that plan on every run. On an update, Stalwart keeps an old credential only when the new list carries its `credentialId` (`crates/jmap/src/registry/mapping/principal.rs:79-200`). It refuses an AppPassword sent without one: "Secondary credentials cannot be set directly" (`principal.rs:317-324`). It keeps one sent back with its id and the masked secret (`principal.rs:157-172`). T1 proves the drop live, and T2 builds the standing answer.
2. **The server makes an app password's secret.** `x:AppPassword/set` generates it and appends it to the account's credentials (`crates/jmap/src/registry/mapping/account.rs:435-447`). The secret is `serverSet`, and the permissions take `Inherit`, `Disable`, or `Replace` (ward's schema, cached by `stalwart-cli` under `~/.cache/stalwart-cli/`, objects `x:AppPassword` and `x:CredentialPermissions`). `Replace` intersects its list with the account's permissions, so it can only narrow them (`crates/common/src/auth/access_token.rs:164-170`).
3. **The JMAP call already works on ward.** sportsyou-notify's `scripts/create-app-password.sh:37-49` creates one with `x:AppPassword/set` under `urn:stalwart:jmap`, with `permissions: {"@type": "Replace", permissions: {<name>: true, ...}}`, and reads the secret from `created.n.secret`. T1 starts from its list minus `jmapEmailUpdate`: `authenticate`, `jmapEmailGet`, `jmapEmailQuery`, `jmapEmailChanges`, `jmapMailboxGet`, `jmapMailboxQuery`. Each name is in ward's `Permission` enum (schema cache).
4. **A user script may redirect once.** The user interpreter's `max_redirects` is 1 by default (`crates/registry/src/schema/structs_impl.rs:36840`), and `sieve-run` sets the same limit (`tools/sieve-run/src/main.rs:38`). The runner notes a redirect (`main.rs:159`) but never prints it (`main.rs:185`), which is #49's first clause.
5. **The renderer is hard-wired to Geoff's template.** `roles/mail-filters/render.sh:192-193` reads `geoff.sieve.in` whatever the account, and the helper passes the login, not the account name (`roles/mail-filters/mail-filters:251`). The role rows live in `data/role-addresses.tsv:3-5`.
6. **The account name is the login's local part.** `build-plan:32` sends `name` and `domainId`, and Stalwart forms the address from them. The mail-filters accounts list (`roles/mail-filters/accounts`) and the per-account template therefore carry `<tech name>`.
7. **Every mailbox signs in on each run.** `stalwart-status counts` signs in as each `mailbox: true` account (`roles/stalwart/stalwart-status:49-60`), and the backup, the heartbeat, `server-restore`, and the drill read it. The refresh signs in to each mailbox to install or deactivate (`mail-filters:92-104, 533-550`). So the account and its password must reach ward in the same apply, which the setup script does.
8. **The drill log names logins.** `scripts/drill-remote.sh:349-351` prints the counts keyed by login into `RESULT` lines, which `scripts/restore-drill.sh:154, 180-194` appends to `docs/restore-drill-log.md`. That is #34.
9. **The workstation store's allow rule is pinned elsewhere.** The `secret-set.sh` rule in `~/.claude/settings.json` covers only `self-hosting-*` worktrees and `/run/user/1000/self-hosting/*`, so this pass makes no store write. The setup script, which Geoff runs, writes the new names and deletes the dead ones.
10. **Fixtures count accounts.** `tests/stalwart.test.sh:102` counts the `household: false` entries (4 today), and `:112-115` requires the 907.life addresses in `accounts.json` to equal the fenced list in `docs/addresses.md`. `tests/apply.test.sh:140` and `tests/mail-filters.test.sh:41-46` list every Stalwart password name.

### Standing answers from the design that apply

A pass may overrun its path estimate to twice its figure before it stops. If a ward apply would replace an account's credentials, the pass changes `build-plan` to keep the app password and tests it. If the read-only app password fails a JMAP read, the run adds the one permission the error names and tests again, and it never falls back to the account's full permissions. If no permission list both reads and refuses a send and a delete, the pass closes with the reader off and reports the bar unmet. A subject goes on the alert-redirect list only with its sender, and only when no reset code or sign-in link can arrive under it. A file in a repo that a live session owns gets a backlog item there instead of an edit. If the operator runbook pass lands before this one, the pass writes its docs into the new pages and its store names through that pass's store and split env file.
