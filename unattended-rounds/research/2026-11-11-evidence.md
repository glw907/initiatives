## Anthropic guidance on the round as the unit

Geoff ruled on 2026-11-11 that the round becomes the workstation's basic unit "unless anthropic
best practice suggests that's a bad idea". One Sonnet subagent fetched 14 Anthropic pages that day
and quoted them for and against. This session then checked each sentence marked "checked" against
the live page with a fixed-string search. The headless, scheduled-tasks, and routines pages were
not fetched.

For the round:

- "the next iteration of the coding agent was then asked to work on only one feature at a time"
  (checked), <https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents>. A
  pass is one unit of work in one fresh session.
- "consider starting with a brand new context window rather than using compaction. Claude's latest
  models are extremely effective at discovering state from the local filesystem.",
  <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices>.
- "Before a run goes unattended, make sure it knows what done looks like, can check its own work,
  and can only touch what it should. Give it a cap on turns or spend, and have a person approve the
  result at the end." (last clause checked), <https://code.claude.com/docs/en/best-practices>. The
  round has a usage ceiling, a cap of twice its planned minutes, and Geoff's packets at the end.
- "stop after two or three automatic continuations on the same task rather than repeating them
  indefinitely, so that a run that is genuinely stuck ends and can be reviewed" (checked),
  <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5>.
  Standing answer 11 takes its relaunch cap from this.
- "A workflow script holds the loop, the branching, and the intermediate results itself",
  <https://code.claude.com/docs/en/workflows>. The conductor's order table is a plan held outside
  the model's turn-by-turn judgment in the same way.

Cautions:

- "we recommend finding the simplest solution possible, and only increasing complexity when
  needed" (checked), <https://www.anthropic.com/engineering/building-effective-agents>.
- "In a run you started before going to bed, nobody tells it, and you find out the next morning
  that it spent the whole night building on the wrong assumption." (checked),
  <https://code.claude.com/docs/en/best-practices>.
- "Claude declares victory on the entire project too early." (checked), the harnesses page above.
- "Running several sessions or subagents at once multiplies token usage." (checked),
  <https://code.claude.com/docs/en/agents>.
- "a fresh subagent first has to gather context your conversation already had, so it can end up
  *slower* than doing the task where you are" (checked), the best-practices page. A fresh planner
  for each pass pays this cost, and the overhaul's first round measures it.
- "For sequential tasks, same-file edits, or work with many dependencies, a single session or
  subagents are more effective." (checked), <https://code.claude.com/docs/en/agent-teams>. The
  sentence compares agent teams with a single session. A round uses no team.
- "Letting a team run unattended for too long increases the risk of wasted effort." (checked), the
  agent-teams page.

## Anthropic guidance on the design step

On 2026-11-11 Geoff asked whether brainstorming and planning were adjusted for the longer unit: "A
failure in planning could be an expensive lesson in building the wrong thing." The planning-miss
table above holds three design-level classes: a design or plan missing a part or prior art (20),
an owner decision left open (15), and an ambiguous instruction (4). They total 39 of about 220
misses, or 5.8 per 100 of the 668 merged pull requests.

What the workstation's rules do today, read at the commits the design names:

- `standards:running-passes` "Design" settles "a design of a page or less".
- `standards:spec-plan-review` gives an `ordinary` plan no read, and one `standards:plan-reviewer`
  read to a `runner` or `auth-data` plan. That reviewer reads "through one lens, mechanics and
  feasibility".
- `standards:diff-reviewer` at whole-branch scope reads the branch diff against "the spec and
  plan", so it accepts a diff that matches a wrong design.

Each sentence below was checked against the live page with a fixed-string search.

- "Does it know what done looks like? A goal condition, a spec file, or a failing test it has to
  turn green.", <https://code.claude.com/docs/en/best-practices>, the first of five questions
  before a run goes unattended.
- "Interview me until you could write the spec", and "start a fresh session to build from it, so
  the build begins with a clean context and a written definition of done", the same page.
- "set up a structured JSON file with a list of end-to-end feature descriptions", and "It is
  unacceptable to remove or edit tests because this could lead to missing or buggy
  functionality.", <https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents>.
  The article's agents change only a `passes` field on each feature.
- "ask Claude for *evidence*: the command it ran and its output, or the screenshot", and "For a
  session you weren't watching, it's also the only evidence you have", the best-practices page.
- "check every requirement is implemented and the listed edge cases have tests", the same page's
  prompt for a reviewer reading a diff against its spec.
- "In practice that makes you the test suite", the same page, on a session with no check to run.
- A caution from the same page: "A reviewer that's asked to find problems will always find
  *something*. If you fix every finding, you end up with extra abstraction layers and tests for
  cases that can't happen." The design adds one read of a round design and no second review.

## The brainstorming skill against Anthropic's guidance

On 2026-11-11 Geoff asked whether `standards:brainstorming` follows current Anthropic best practice
and whether it can be improved. The skill was read at `plugins/standards/skills/brainstorming/` in
`~/Projects/standards`, last changed in `304038c` on 2026-11-06. `THIRD-PARTY-NOTICES:126-130`
records that it derives from <https://github.com/obra/superpowers>. One Sonnet reader fetched four
Anthropic pages and quoted them. It read the skill-authoring page and the Fable 5.2 prompting page
whole, and about a third to a half of the Claude Code skills page and the prompting best-practices
page. This session did not recheck its quotes against the live pages, apart from the
best-practices passages already checked above.

Where the skill matches the guidance:

- Its description says what the skill does and when to use it, inside the 1,024-character limit
  (<https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices>).
- `SKILL.md` is 228 lines against "Keep the `SKILL.md` body under 500 lines". Its two references
  sit one level deep, and the 314-line `visual-companion.md` opens with a contents list.
- It gives a reason with each rule and uses no capitalized emphasis, which fits "Providing context
  or motivation behind your instructions" and "The fix is to soften any aggressive language"
  (<https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices>).
- Its shape is the one under "Brainstorm with Claude first": an interview, a written design, and a
  fresh session that builds from it.

Where it falls short:

| Gap | Guidance | In the standing change |
| --- | --- | --- |
| The written design's list has no statement of what done looks like. | "a written definition of done", and "Does it know what done looks like?" | The written design's list gains a statement of what done looks like. A round's acceptance lists already cover a round of two or more passes. |
| The description promises "two or three approaches with a recommendation". The body says to compare approaches privately and show the comparison "only when it helps them decide". | "The `description` field makes Skill discovery possible and should include both what the Skill does and when to use it." | The description is rewritten to match the body. |
| It asks before it looks: "They decide whether you go." | "using tools to discover any missing details instead of guessing" | The skill reads without asking first. 20 recorded misses were a design or plan missing a part or prior art. |
| It has no evaluation. `tests/` in the standards repo holds a line-count test and a scan test. | "Create evaluations BEFORE writing extensive documentation", and "Test your Skill with all the models you plan to use it with." | Filed as a backlog item. The round reports count design-level misses, which is a field measure and no eval. |

The pages say nothing for or against asking one question at a time, or open questions ahead of
multiple choice. The best-practices example shows Claude asking multiple-choice questions, as a
description of what happens and with no advice attached.

A change to the skill adds a rule to a skill, so the `workstation-refinement` freeze held it
until 2026-12-11. Geoff lifted the freeze for this overhaul on 2026-11-11, and the design now
names the skill. The build design carries the first three rows, and the fourth goes to the
standards backlog.
