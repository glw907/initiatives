# Server operating system for the mail and media boxes (2026-10-17)

Scope: which OS each of the two servers runs. The mail box runs Stalwart only. The media box runs Immich (Docker Compose) and dubplate (a Go binary under systemd). This brief builds on the [server baseline](2026-10-17-server-baseline.md), [Stalwart](2026-10-17-stalwart.md), and [backups](2026-10-17-backups.md) briefs, which all assume Debian 13. No Immich brief exists yet. "Unverified" marks claims I could not confirm from a primary source.

Method note: the Hetzner image and ISO lists below come from read-only GET calls to the Hetzner Cloud API with the existing token on 2026-10-17 (`/v1/images?type=system` and `/v1/isos`). docs.fedoraproject.org blocked automated fetches behind a bot check, so Fedora CoreOS facts come from the docs' source files in the [fedora-coreos-docs repo](https://github.com/coreos/fedora-coreos-docs), which are what that site renders.

## What Hetzner offers today

Stock images (API, `type=system`): `alma-8/9/10`, `centos-stream-9/10`, `debian-12/13`, `fedora-43/44`, `opensuse-16`, `rocky-8/9/10`, `ubuntu-22.04/24.04/26.04`. The `debian-13` image dates from 2025-08-18, `alma-10` and `rocky-10` from 2025-06-17 (so they start at 10.0), and `ubuntu-26.04` from 2026-05-18. The ISO library adds `nixos-minimal-26.05` (x86 and arm), Debian 13.3 netinst, AlmaLinux 10.1, Rocky 10.0, and Ubuntu 26.04. There is no Fedora CoreOS or Flatcar image or ISO; both need a snapshot upload.

Other candidate hosts, for the provider brief: netcup lists Debian 13 and AlmaLinux 8, 9, and 10 as ready images plus install ISOs ([netcup images](https://www.netcup.com/en/server/vserver-images)). OVHcloud's VPS page lists Debian 11 to 13, Rocky 8 to 10, and Fedora; AlmaLinux on VPS is unconfirmed ([OVHcloud VPS OS](https://www.ovhcloud.com/en/vps/os/)). BuyVM reinstalls from templates covering Debian, Ubuntu, and RHEL-family distros ([BuyVM OS](https://buyvm.net/operating-systems/)); whether it mounts custom ISOs is unverified. Debian is the one OS every candidate host offers as a stock image.

## Debian 13 (trixie)

Support runs to 2028-08-09 under the security team and to 2030-06-30 under LTS ([trixie page](https://www.debian.org/releases/trixie/)). Point releases have landed about every two months, and 13.7 shipped on 2026-09-12 (server baseline brief).

Updates: `unattended-upgrades` installs both security and stable-update fixes by default. `Automatic-Reboot` with a set time reboots only when `/run/reboot-required` exists ([50unattended-upgrades](https://sources.debian.org/data/main/u/unattended-upgrades/2.12/data/50unattended-upgrades.Debian), [wiki](https://wiki.debian.org/UnattendedUpgrades)). Debian stable takes fixes only, not new versions, so an unattended update rarely changes behavior. That is the main reason it rarely needs a rollback.

Rollback: there is none at the OS level. The substitutes are a Hetzner snapshot before risky work, Hetzner Backups on the mail box (the baseline brief prices it at about $1.30 a month), and the baseline's "rebuild is the converge path" rule, which reproduces a host from the repo and the USB backup.

Security: AppArmor is on by default ([Debian wiki](https://wiki.debian.org/AppArmor)). Docker applies its `docker-default` AppArmor profile to containers ([Docker AppArmor](https://docs.docker.com/engine/security/apparmor/)). Stalwart and dubplate run unconfined by MAC and rely on systemd sandboxing, as the baseline describes.

Containers: Docker's own repo supports "Debian Trixie 13 (stable)" ([Docker on Debian](https://docs.docker.com/engine/install/debian/)). Immich's install path is Docker with the Compose plugin ([requirements](https://docs.immich.app/install/requirements/)), so this is the path its docs and support threads assume.

Fit: `ffmpeg` and `flac` are in Debian main (baseline brief). On AlmaLinux, dubplate's cloud-init needs EPEL, CRB, and RPM Fusion, including a key bootstrap for RPM Fusion's unsigned-at-first release package (`~/Projects/dubplate/cloud-init/user-data.yaml`). On Debian that block disappears. Debian's minimal cloud image has no firewalld or SELinux userland. That makes for a light base on a 4 GB box, though I have no measured idle-memory figures to cite (inference).

Costs: Debian stable ships old versions of some tools (Caddy 2.6.2, rclone 1.60.1, Docker 26.1.5), so the media box takes Caddy and Docker from their vendors' repos (baseline brief). Stalwart has a Debian-specific failure mode: an apt dependency that pulls in exim4 stops Stalwart through `Conflicts=`, and the fix is an apt pin ([Stalwart brief](2026-10-17-stalwart.md), [Stalwart support](https://support.stalw.art/t/1826)). Debian's manuals are deep ([Administrator's Handbook](https://www.debian.org/doc/manuals/debian-handbook/)), and most Immich and self-hosting guides assume Debian or Ubuntu.

## Ubuntu Server 24.04 LTS and 26.04 LTS

Standard security maintenance runs to May 2029 for 24.04 and May 2031 for 26.04. ESM runs to 2034 and 2036, and Ubuntu Pro is "free for personal use on up to five machines" ([release cycle](https://ubuntu.com/about/release-cycle)). Pro adds Livepatch, which cuts kernel reboots.

Updates and security match Debian: `unattended-upgrades` and AppArmor. Docker supports 26.04 and 24.04 ([Docker on Ubuntu](https://docs.docker.com/engine/install/ubuntu/)). Hetzner's `ubuntu-26.04` image is five months old, the freshest of any option.

The reason not to pick 26.04 for "few surprises" is that it changed core tools. sudo-rs is the default `sudo`, and the Rust uutils coreutils replaced GNU for every command except `cp`, `mv`, and `rm`. Canonical held those back over open time-of-check bugs, and a Zellic audit found 113 issues, most since fixed ([LWN comments quoting Canonical](https://lwn.net/Articles/1069481/), [Phoronix](https://phoronix.com/news/Ubuntu-Rust-Coreutils-Audit)). sudo-rs ignores `sudo -E` (unverified, from [a secondary summary](https://www.turbogeek.co.uk/rust-coreutils-sudo-rs-ubuntu-26-04/)). The second operator's restricted sudoers file and the provisioning scripts would run on new implementations. 24.04 avoids that but gives a shorter standard life than Debian 13 LTS, and the long tail needs a Pro token, which is one more account to keep. Ubuntu Server also ships snapd (unverified on Hetzner's image). Ubuntu buys little over Debian here except Livepatch.

## AlmaLinux 10 and Rocky Linux 10

Support is the longest of any free option: active support to 2030-05-31 and security to 2035-05-31 for both ([AlmaLinux releases](https://wiki.almalinux.org/release-notes/), [Rocky dates](https://endoflife.date/rocky-linux)). The latest minors are 10.2, released 2026-05-26 (Alma) and 2026-05-29 (Rocky). Minor releases arrive in place through `dnf`, so a box can run until 2035 without a reinstall.

Updates: `dnf5` automatic supports `reboot = when-needed` ([dnf5 automatic](https://dnf5.readthedocs.io/en/latest/dnf5_plugins/automatic.8.html)). musicbox already runs `dnf-automatic` with security-only upgrades and no reboot, so it never reboots on its own today.

Security: SELinux is the RHEL-family control. Hetzner's `alma-10` image ships `SELINUX=permissive`, and getting to enforcing takes an autorelabel and a reboot during first boot, which dubplate's cloud-init does with `power_state` (`~/Projects/dubplate/cloud-init/user-data.yaml`).

Containers: Docker's RHEL page lists RHEL 8, 9, and 10 and its CentOS page lists Stream 9 and 10. Neither names AlmaLinux or Rocky, and Podman must be removed first ([Docker on RHEL](https://docs.docker.com/engine/install/rhel/), [Docker on CentOS](https://docs.docker.com/engine/install/centos/)). In practice people install from the CentOS repo, but that is outside Docker's stated support. Immich maintainers' view of SELinux, on an issue where SELinux blocked the upload directory: "If you choose to use selinux, expect to need tweaks like this" ([immich#14912](https://github.com/immich-app/immich/issues/14912)). Docker CE leaves SELinux separation off unless `selinux-enabled` is set ([dockerd reference](https://docs.docker.com/reference/cli/dockerd/)), so the tweaks are avoidable, but only by turning off the reason to choose this family for the media box.

Fit: this is what Geoff runs today. The vps-conventions skill and dubplate's cloud-init are written for it. dubplate's 957-line runbook has no AlmaLinux-specific terms (grep for selinux, dnf, restorecon, EPEL, alma: zero hits), so the AlmaLinux knowledge is concentrated in the 210-line cloud-init file. Rocky is equivalent on every axis here and offers nothing AlmaLinux does not. AlmaLinux also has bootc images, which keeps a later move to image-based open.

## Fedora CoreOS

Fedora CoreOS is "currently not available as an option in the operating system selection on Hetzner." You upload a snapshot with `hcloud-upload-image`, a third-party tool Hetzner does not support, and the docs call Hetzner support "emerging" ([provisioning-hetzner source](https://github.com/coreos/fedora-coreos-docs/blob/main/modules/ROOT/pages/provisioning-hetzner.adoc)). FCOS "does not support cloud-init. It accepts only Ignition configuration files", written in Butane.

Updates: Zincati applies updates automatically and offers immediate, fleet-lock, or weekly-window reboot strategies. The previous deployment stays on disk; rollback is a manual `rpm-ostree rollback -r` or a boot-menu choice at the console ([auto-updates](https://github.com/coreos/fedora-coreos-docs/blob/main/modules/ROOT/pages/auto-updates.adoc), [manual rollbacks](https://github.com/coreos/fedora-coreos-docs/blob/main/modules/ROOT/pages/manual-rollbacks.adoc)). The stable stream rebases onto each new Fedora major on its own, tested first in `next` ([update streams](https://github.com/coreos/fedora-coreos-docs/blob/main/modules/ROOT/pages/update-streams.adoc)). That is two major OS changes a year arriving without a decision. Operator threads show the cost: a node that failed to boot after the move to Fedora 41 with composefs, and update failures caused by layered packages ([Fedora discussion](https://discussion.fedoraproject.org/t/coreos-fails-to-boot-with-composefs-after-upgrade-to-41/143095), [layered packages](https://discussion.fedoraproject.org/t/not-possible-to-update-fedora-coreos-with-layered-packages/117658)).

Containers: Podman is the native runtime, and the `docker` CLI ships through Moby. Swapping in Docker CE means `rpm-ostree override remove` plus a reboot, and the FCOS 40 to 41 upgrade broke for people who had done so ([Docker CE on FCOS](https://github.com/coreos/fedora-coreos-docs/blob/main/modules/ROOT/pages/docker-ce.adoc)). Whether the Compose plugin is in the base image is undocumented (unverified). Immich has no Podman install page; its issue tracker has a run of Podman reports (Redis unreachable, `healthcheck.start_interval` unsupported, rootless permission errors as recent as August 2026) ([immich#12627](https://github.com/immich-app/immich/issues/12627), [immich#10580](https://github.com/immich-app/immich/issues/10580), [immich#30680](https://github.com/immich-app/immich/issues/30680)). Community reports of Immich in Podman quadlets on CoreOS working do exist ([Lemmy thread](https://communities.stormux.org/post/11578)), but they are forum posts, not support.

## Flatcar Container Linux

Flatcar is "not installable as one of the default operating system options" on Hetzner; you install through the rescue system or upload a snapshot, then pass Butane-generated Ignition as user data ([Flatcar on Hetzner](https://www.flatcar.org/docs/latest/deploy/cloud/hetzner/)). Updates download to a passive partition, and a reboot swaps partitions; locksmithd reboots by default, 5 minutes after an update, within an optional window ([update strategies](https://www.flatcar.org/docs/latest/updates-releases/releases/update-strategies/)). The LTS channel keeps each major for about 18 months ([LTS announcement](https://www.flatcar.org/blog/2022/05/flatcar-container-linux-long-term-support-lts-channel-and-advanced-features-now-available-to-community/)). Docker is built in, which suits Immich better than FCOS does. Compose comes as a systemd-sysext image ([sysext docs](https://www.flatcar.org/docs/latest/sys-ext/)). SELinux is present but "does not enforce SELinux protections by default" ([Flatcar SELinux](https://www.flatcar.org/docs/latest/security/encryption/selinux/)).

The problem is the mail box. Flatcar expects every workload in a container. The Stalwart brief found that the official image cannot write its default log file, and an unverified report says auto-ban banned the Docker bridge IP and locked everyone out ([Stalwart brief](2026-10-17-stalwart.md)). Flatcar is built for container fleets; two hand-run boxes use little of it.

## bootc images built from a Containerfile

This is the model Geoff's Bluefin workstations use. A `Containerfile` in the repo starts from a bootc base image, adds packages, units, and config, and CI pushes the image to a registry. A stock server is converted once with `bootc install to-existing-root`, which wipes `/boot` and leaves the old root under `/sysroot` for cleanup ([to-existing-root man page](https://github.com/bootc-dev/bootc/blob/main/docs/src/man/bootc-install-to-existing-root.8.md)). The box then pulls new images with `bootc upgrade`, which stages an A/B deployment; upstream ships a `bootc-fetch-apply-updates.timer`, and `bootc rollback` swaps the boot order back ([upgrades](https://github.com/bootc-dev/bootc/blob/main/docs/src/bootc-upgrades.7.md)). The install must run from the target image as a privileged Podman container ([installation](https://github.com/bootc-dev/bootc/blob/main/docs/src/bootc-installation.7.md)). The Fedora/CentOS bootc project does not publish prebuilt disk images ([GCP guide](https://docs.fedoraproject.org/be/bootc/provisioning-gcp/)).

Base choice: AlmaLinux bootc images "are currently *experimental*" ([AlmaLinux bootc-images](https://github.com/AlmaLinux/bootc-images)), although Quay shows `10.2` tags rebuilt daily as of 2026-10-17 ([Quay tags](https://quay.io/repository/almalinuxorg/almalinux-bootc?tab=tags)). CentOS Stream runs ahead of RHEL rather than behind it, and Fedora bootc carries Fedora's 13-month lifecycle. No base is both stable and supported for servers today.

The real cost is that CI becomes the patch pipeline. A Debian box patches itself from Debian's mirrors. A bootc box gets a security fix only after the repo's CI rebuilds the image on the new base, pushes it, and the box pulls it, and the box needs a registry credential if the image is private (inference from the model above). If GitHub Actions breaks or the workflow is disabled, patching stops without an error on the server. "Restorable from the repo alone" also changes meaning: the repo plus a registry plus a working build. I found no operator report of bootc on Hetzner Cloud. The second operator's emergency commands (`bootc status`, `bootc rollback`) are short, but debugging a bad deployment is Geoff's alone.

## NixOS

NixOS gives the strongest provision-from-code story: one configuration describes the whole host, and every rebuild leaves a boot-menu generation to roll back to. nixpkgs has modules for both workloads ([Immich](https://wiki.nixos.org/wiki/Immich), [Stalwart](https://wiki.nixos.org/wiki/Stalwart)), and the Stalwart module was renamed from `services.stalwart-mail` to `services.stalwart` with a new `stateVersion` option ([nixpkgs commit](https://code.ornl.gov/nix/nixpkgs/-/commit/75742d265e66b37fa9b12b60900f53f0860c09d2)). Hetzner's ISO library carries the 26.05 installer, and [nixos-anywhere](https://github.com/nix-community/nixos-anywhere) installs over SSH. `system.autoUpgrade` with `allowReboot` reboots when the kernel, initrd, or modules change ([NixOS manual](https://nixos.org/manual/nixos/stable/#sec-upgrading-automatic)).

The lifecycle rules it out for "few surprises." 26.05 reaches end of support on 2026-12-31, and 25.11 ended on 2026-06-30 ([endoflife.date](https://endoflife.date/nixos)). The boxes would need a release upgrade every six months. The module path also means Immich and Stalwart versions follow nixpkgs, not upstream, which an operator moved away from for that reason ([immich#30680](https://github.com/immich-app/immich/issues/30680)). Geoff's scripts and the second operator's runbook would not carry over.

## Image-based versus traditional, directly

The case for image-based is real: the OS becomes an artifact the repo produces, updates are atomic, and a bad update rolls back with one command. For a fleet that is decisive. For two household boxes, the evidence points the other way:

- Install: none of FCOS, Flatcar, or bootc is a stock Hetzner image. Each needs a snapshot upload through an unsupported tool or a conversion step, repeated on any other host.
- Immich: Immich supports Docker Compose. The image-based option with the best Docker story (Flatcar) is the worst fit for Stalwart, and the one closest to Geoff's Bluefin habits (bootc on AlmaLinux) is still marked experimental.
- Patching: Debian and AlmaLinux patch from their vendors' mirrors without any of Geoff's infrastructure running. A bootc box patches only while Geoff's CI runs.
- Rollback need: Debian stable and AlmaLinux minor updates are fix-only streams, so a bad unattended update is rare. Rollback matters most on fast streams (FCOS, Fedora), which are the ones that bring it.
- Restore: the baseline brief's rebuild path (`hcloud server rebuild` with cloud-init, then `apply.sh`, then a restic restore) already reproduces a host from the repo and the USB drive. Most of the reproducibility that images promise comes from that path.
- The second operator: his runbook uses `systemctl`, `journalctl`, `docker compose`, and the restore wrapper. Those are the same on Debian and AlmaLinux. On FCOS they become Podman and `rpm-ostree` commands that most web help does not cover.

The bootc route is worth revisiting when AlmaLinux bootc drops the experimental label, since it would keep AlmaLinux's 2035 lifetime and add Bluefin-style rollback.

## Recommendation

**Both servers: Debian 13 (Hetzner image `debian-13`).** This confirms the baseline's choice on evidence rather than habit. Against Geoff's three priorities:

- **Low cost.** No paid add-on is needed for the life of the boxes; Debian LTS is free, and Ubuntu's long tail needs a Pro token. It is a stock image on every candidate host. Maintenance is the lowest of the options: unattended-upgrades handles patches and timed reboots, and the media box drops the EPEL, CRB, and RPM Fusion setup that dubplate needs on AlmaLinux. One OS on both boxes means one patch system, one CI container (`debian:13`), one set of runbook commands, and one delta to the vps-conventions skill.
- **Stable.** Debian stable takes fixes only. Support runs to mid-2030, past any plausible life of these server plans, and the move to Debian 14 is a rebuild through the existing path, not an in-place gamble. Recovery is a snapshot or a rebuild plus restore, which the restore drill already exercises. There is no 26.04-style rewrite of `sudo` or coreutils underneath the second operator's commands.
- **Performs well.** The base has no SELinux userland or firewalld. Docker from Docker's own repo is officially supported on trixie and is the runtime Immich documents, which avoids Podman and SELinux friction on the box that needs containers. On the mail box, Stalwart runs as a native binary with nothing between it and the network.

**Why not a split (AlmaLinux on mail, Debian on media)?** The mail box would gain SELinux enforcing and five more years of support. The cost is two distros, two patch systems, two runbook dialects, and the second operator typing different commands on each box in an emergency. I did not find a published SELinux policy for Stalwart, so on AlmaLinux it would most likely run in the generic `unconfined_service_t` domain, and enforcing mode would protect it less than the label suggests (unverified). For the most boring box in the estate, matching the other box beats the longer calendar.

**Runner-up: AlmaLinux 10 on both.** It gives the longest free support (2035), SELinux, and the skills Geoff already has, and it keeps a later bootc move open. It loses on the media box: Docker does not name AlmaLinux as supported, Immich's maintainers expect SELinux users to fix their own denials, dubplate's host tools need third-party repos, and the first boot needs a relabel reboot. If Geoff weighs the 2035 date above these, AlmaLinux 10 on both is a sound choice; a split is the weakest of the three.

**Not recommended:** Ubuntu 26.04 (core tool rewrites), Ubuntu 24.04 (shorter than Debian without a Pro token), Fedora CoreOS (automatic major rebases, Podman-first, emerging Hetzner support), Flatcar (containers only, a poor mail fit), bootc today (experimental stable base, CI as the patch pipeline), NixOS (six-month release treadmill, skill mismatch).

## Risks

- No OS rollback. A bad Debian update is rare but has no one-command undo. Mitigations are snapshots before planned risk, Hetzner Backups on the mail box, and a rehearsed rebuild.
- Docker outside Debian's archive. Docker CE comes from Docker's repo, which Debian's security team does not cover. Its origin must be in unattended-upgrades' allowed origins, or Docker never updates (baseline brief).
- Unattended reboot of the mail box. A reboot defers inbound SMTP for a minute or two, which senders retry. A failed boot is the real risk, which is why the external probe and Hetzner Backups matter on that box.
- AppArmor confines less than SELinux enforcing. Stalwart and dubplate rely on systemd sandboxing. Acceptable for a single-purpose host, but it is a real gap compared with the runner-up.
- Debian 13's LTS end in mid-2030. LTS covers a narrower package set than full support ([Debian LTS](https://wiki.debian.org/LTS)). Plan the rebuild to Debian 14 within its full-support window, not at the LTS cliff.
- Unverified Hetzner image contents. The baseline's throwaway-server check (sources format, NTP, AppArmor presence, filesystem) still has to run first.
