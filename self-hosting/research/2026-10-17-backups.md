# Pull backups of two Hetzner servers to a LUKS USB drive on pavilion (research brief, 2026-10-17)

Scope: back up the mail server (Stalwart) and the media server (Immich and dubplate) by pulling from pavilion onto one encrypted USB drive. The drive is the only copy, by Geoff's ruling. Read-only research; nothing was installed or changed.

Claims marked "unverified" came from a search summary or memory, not from a page I read in full.

## 1. Tool choice

**Finding: restic cannot pull.** The restic forum's answer to "back up a server without running restic on it" is that restic reads only local files, so the remote must be made to look local or its data copied first ([forum thread](https://forum.restic.net/t/how-to-backup-a-server-without-running-restic-directly-on-it/1445)). The options raised there were sshfs or rclone mounts (slow, and sshfs inode handling makes change detection poor), reverse SSH (still runs restic on the source), or exporting the data to the backup host first. A second thread on a remote folder reached the same place ([forum](https://forum.restic.net/t/best-option-for-backing-up-a-remote-folder-to-a-local-restic-repository/10691)).

**Borg's documented pull mode puts the key on the server.** Borg's [pull-mode page](https://borgbackup.readthedocs.io/en/stable/deployment/pull-backup.html) has the server open an SSH connection to the client and forward a socket, and the client then runs `borg create`. Borg encrypts on the client and needs the key in plaintext at runtime ([security internals](https://borgbackup.readthedocs.io/en/stable/internals/security.html)). So the passphrase would live on each Hetzner server. That breaks the "servers hold no backup credentials" rule. (The conclusion is my inference from those two pages.) The page's other method, sshfs plus chroot, needs root on the client and warns that a server-side root can do unlimited damage to the client. Borg 2.0 is still beta in 2026 (one [comparison](https://techfuelhq.com/homelab/restic-vs-borg-vs-kopia-2026/), secondary source), so the stable choice would be 1.4.5.

**Kopia** is not installed on pavilion and I found no documented pull mode. I excluded it.

**rsync with hard-link snapshots (rsnapshot style)** is the real alternative. Restore is a plain `rsync`, with no repository password. Its costs: no block-level dedup, no built-in integrity check beyond rsync's own, and no encryption beyond LUKS. restic wins on history, dedup, and `restic check --read-data`, which is why I keep it as the history layer.

**Recommended design: staged rsync pull, then local restic.**

1. Each server prepares a consistent export directory on a server-side timer.
2. Pavilion pulls it with rsync over a read-only forced-command key into a mirror on pavilion's internal disk.
3. Pavilion runs `restic backup` from the mirror into a repository on the LUKS drive.

The servers hold only a public key. They have no write path to pavilion or the drive. Restore needs only restic, cryptsetup, and the two passwords.

restic and borg both ship in the Bluefin base image (checked: `rpm -qf` shows `restic-0.19.1-1.fc44` and `borgbackup-1.4.5-1.fc44`, and neither is in `layered-packages.txt`). No install or manifest line is needed. Because the image may drop a package, the runbook should name `brew install restic` as the fallback tier (unverified that Homebrew carries it at a matching version).

**Streaming alternative.** `restic backup --stdin-from-command -- ssh server dumpcmd` aborts the snapshot on a non-zero exit ([restic backup docs](https://restic.readthedocs.io/en/stable/040_backup.html)). It suits one database dump. It is wrong for 20 GB of photos, because a stream is stored as one file and every run re-transfers all of it. Use rsync for the files.

**Versioning and retention.** One repository per server (`restic-mail`, `restic-media`) on the drive, with the same password. Separate repositories keep a lock or corruption in one from touching the other. Suggested policy:

```
restic forget --keep-within 14d --keep-weekly 8 --keep-monthly 12 --keep-yearly 5
```

The keep options count periods that contain snapshots, so gaps from an off desktop do not break them ([forget docs](https://restic.readthedocs.io/en/stable/060_forget.html)). Run `forget` on every backup but `prune` only monthly. Prune locks the repository and can be slow on spinning disks: forum reports include a 4 TB repository on USB 3 at about 5% after many hours, though those cases had caches on slow media ([forum](https://forum.restic.net/t/recovering-from-a-full-backup-disk/5768), [prune performance](https://forum.restic.net/t/prune-performance/2127)). At roughly 60 GB, expect minutes, not hours (my estimate). Use `--max-unused` (default 5%) and `--max-repack-size` to cap work.

**Dedup.** restic dedups by content chunks. Immich originals never change, so each snapshot after the first costs almost nothing. Gzipped database dumps dedup poorly because one changed row shifts the whole stream. They are small (tens of MB for this library, my estimate), so ignore it, or dump uncompressed.

**Integrity.** Plain `restic check` verifies structure and does not read pack contents. `--read-data` reads everything. `--read-data-subset` accepts `n/t`, a percentage, or a size ([working with repos](https://restic.readthedocs.io/en/stable/045_working_with_repos.html)). At about 60 GB and USB 3 speeds a full read is on the order of ten minutes (arithmetic, not measured). Run `check --read-data-subset=10%` weekly and a full `--read-data` quarterly.

## 2. Server side: forced command and consistency

**Account.** Create a `backup` user with no password and a `/bin/sh` shell (dash on Debian). `rrsync` warns against bash because login rc files run before the forced command ([rrsync man page](https://manpages.debian.org/trixie/rsync/rrsync.1.en.html)). Its `authorized_keys` line:

```
restrict,command="/usr/bin/rrsync -ro /srv/backup-export" ssh-ed25519 AAAA... pavilion-backup-mail
```

`-ro` gives read-only access and implies no-delete. `restrict` turns off port, agent, and X11 forwarding ([sshd(8)](https://man7.org/linux/man-pages/man8/sshd.8.html)); the page I read also lists `no-pty` separately. The rrsync path on Debian 13 is unverified: the package ships the script, but run `dpkg -L rsync` to confirm. One rrsync key is limited to one directory. For several trees use either read-only bind mounts under one export root, or the documented rsync-daemon-over-SSH form with several `read only` modules (same man page). `from=` is not usable because pavilion's home IP changes.

Use one key per server. A stolen key then reads one export directory and nothing else. It cannot write, delete, or get a shell.

**Consistency, run on the server by a root systemd timer (about 03:00), so the pull needs no hooks:**

- **Immich:** the server writes its own database dump daily at 02:00 into `UPLOAD_LOCATION/backups`, keeping 14 ([Immich backup docs](https://docs.immich.app/administration/backup-and-restore)). Back up `library`, `upload`, `profile`, and `backups`; `thumbs` and `encoded-video` can be skipped (jobs regenerate them). If the server stays up, take the database first and the files second, so the worst case is files the database does not know about. So the media timer needs no dump step. It only needs ACLs so `backup` can read `UPLOAD_LOCATION` (Immich containers run as root by default; unverified for this install).
- **Stalwart:** the weak point. Official docs describe copying the RocksDB data directory; community answers from May and June 2026 say stop the server first, then copy ([forum](https://support.stalw.art/t/what-is-the-safest-way-to-backup-the-rocksdb-database/386), [RocksDB thread](https://support.stalw.art/t/automatic-server-backup-rocksdb/611)). The built-in `--export` needs a stopped server and is described as migration tooling, not routine backup ([search summary of the docs; the page itself returned 404 on fetch](https://stalw.art/docs/management/cli/database/migrate)). The server timer should rsync the live directory once (warm pass), stop Stalwart, rsync the delta, start it, and write a `VERSION` and `STAGED-AT` file. Downtime is seconds if the delta is small (my expectation, untested). Sending servers retry deferred mail, so a short stop is tolerable.
- **Stalwart, second layer:** [Vandelay](https://stalw.art/docs/migration/import-export/) is a per-account JMAP archiver whose docs call it a backup tool: a scheduled import writes one SQLite file per account, and restore is an export to any JMAP target. It runs from pavilion over JMAP, which fits the pull model, but it needs a mailbox credential per account on pavilion (unverified that an admin can impersonate). It does not cover server settings or DKIM keys. It protects against a Stalwart version break the raw copy cannot survive. Use it as a weekly extra, not the primary backup. `stalwart-cli snapshot` exports configuration while live, but a forum poster reported errors with it in June 2026, so test before relying on it.
- **dubplate:** the runbook's backup section says `dubplate-server backup` syncs the library to an rclone remote and sends a database snapshot after it, with the remote expected to be wrapped in `crypt` (`~/Projects/dubplate/docs/server-runbook.md`, "Backup"). A `local:` rclone remote pointing at the export directory would feed the pull, but that copies the 6.6 GB library a second time and `doctor` will warn about the missing crypt wrapper. Whether the verb leaves a local snapshot file is unverified. Restore takes `--from-file`, so a local snapshot is enough. This is a question for the dubplate agent.

**Freshness guard.** Pavilion refuses to snapshot an export whose `STAGED-AT` is over 36 hours old, and records a failure. A dead server timer then shows up instead of quietly backing up stale data.

## 3. Pavilion side

**Timer type: a system timer, not a user timer.** Mounting a LUKS device needs root. `udisksctl` does accept `--key-file`, but its man page says it is not meant for scripts, and polkit checks assume an active session ([udisksctl(1)](https://man.archlinux.org/man/udisksctl.1.en), [polkit reports](https://bbs.archlinux.org/viewtopic.php?id=249216)). The existing timers (`check-drift`, `vdirsyncer`, `cairn-tripwire`) are user timers. Linger is on for the user (`loginctl` showed `Linger=yes`), so a user timer would fire without a login, but it could not unlock the drive. Put `server-backup.service` and `.timer` in `~/.dotfiles/bluefin/etc/systemd/system/` and install from there, as the `/etc` rule says. `systemd-remount-fs.service` already lives in that directory as precedent.

**Service shape (sketch):**

```
[Service]
Type=oneshot
User=glw907
LoadCredentialEncrypted=restic-password:/etc/credstore.encrypted/restic-password
LoadCredentialEncrypted=luks-key:/etc/credstore.encrypted/luks-key
LoadCredentialEncrypted=ssh-mail:/etc/credstore.encrypted/ssh-mail
ExecStart=/home/glw907/.local/bin/server-backup
Nice=19
IOSchedulingClass=idle
```

Privileged `+`-prefixed `ExecStartPre=`/`ExecStopPost=` steps (the `+` exemption is stated in [systemd.exec](https://man7.org/linux/man-pages/man5/systemd.exec.5.html)) run `cryptsetup open` and `umount`/`close`. Wrap the body in the existing `awake` helper so a desktop suspend cannot interrupt a run; restic documents that a client entering standby mid-backup fails to refresh its lock ([changelog via forum summary](https://forum.restic.net/t/locks-from-restic-backup-not-being-removed-after-backup-completes/9905), unverified for USB).

**Timer:**

```
[Timer]
OnCalendar=*-*-* 04:30
Persistent=true
RandomizedDelaySec=30min
```

`Persistent=` stores the last trigger on disk so a missed run fires at the next boot; it applies only to `OnCalendar=` timers ([systemd.timer](https://man7.org/linux/man-pages/man5/systemd.timer.5.html)). The check-drift timer uses the same pattern.

**Drive absent: skip quietly.** The script, not a `Condition`, checks for the device (`/dev/disk/by-uuid/<LUKS UUID>`). A failed `Condition…=` skips the start without a failed state ([systemd.unit](https://man7.org/linux/man-pages/man5/systemd.unit.5.html)), but then nothing runs to count the miss. The script instead:

1. Pulls both servers into the internal-disk mirror (`/var/lib/server-backup/mirror/<server>`, about 30 GB; pavilion has 368 GB free) even with the drive absent.
2. Increments a `misses` counter in `/var/lib/server-backup/state/` and exits 0 when the drive is missing.
3. On a full success (pull, restic backup, forget), writes `last-success` and zeroes the counter.

Use `rsync --max-delete=N` on the pull, so a wiped server cannot empty the mirror in one run.

**Notifications, calm-desktop compliant.** A separate user timer, `backup-staleness-notify`, written like `check-drift-notify` (full PATH, journal log, `notify-send`, always exit 0), reads the state files, which the system service makes world-readable. Normal urgency fires once when consecutive unsuccessful runs reach 3. Critical fires once at 10, on the grounds that a backup that never lands loses work (Geoff's call; see open questions). It records the level it last notified, so it never repeats. Silent on success. Counting runs, not days, means a pavilion that was off for a week does not nag on boot.

**Unlock source.** The age store (`secret-set.sh`, key fetched from 1Password) cannot serve an unattended job. Instead, `systemd-creds encrypt --with-key=tpm2` produces credentials that only this machine's TPM can decrypt, loadable by `LoadCredentialEncrypted=` ([systemd-creds](https://man7.org/linux/man-pages/man1/systemd-creds.1.html)). The page I read did not show `/etc/credstore.encrypted` as a search path, so the explicit path in the unit above is deliberate. The originals stay in the age store, so a dead TPM costs nothing.

## 4. The drive

- **LUKS2** is the cryptsetup default ([cryptsetup(8)](https://man7.org/linux/man-pages/man8/cryptsetup.8.html)). Add two keyslots with `luksAddKey`: a human passphrase for the second operator and recovery, and a random keyfile for pavilion's unattended unlock. Back up the header with `cryptsetup luksHeaderBackup`; the man page warns that a damaged header loses all data without one. Store the header backup age-encrypted (the age public key can encrypt without the private key).
- **ext4.** restic hashes everything and `check --read-data` catches rot, so Btrfs checksums add little and add risk. ext4 mounts on any Linux live image the second operator might boot. (I found no source comparing filesystems for restic; this is judgment.)
- **Labels:** LUKS label `servers-backup`, ext4 label `servers-backup-data`, and a physical sticker with the drive's role. Never the passphrase.
- **SMART over USB:** use `smartctl -d sat`. Some bridges in UAS mode do not pass SAT commands, and Linux disables passthrough for those chipsets, so `smartctl` fails; `lsusb -t` shows whether the driver is `uas` or `usb-storage` ([smartmontools USB wiki](https://www.smartmontools.org/wiki/USB), [SAT with UAS](https://www.smartmontools.org/wiki/SAT-with-UAS-Linux?version=17)). Test `smartctl -d sat -a` on the actual drive at purchase. `smartmontools` 7.5 is already installed. Check health weekly inside the staleness notifier.
- **Size:** about 30 GB of data today; two repositories plus growth fit well inside 1 TB. A smaller or larger drive changes nothing in the design.

## 5. Restore

Restore is a push from the machine holding the drive to a fresh server, using Geoff's or the second operator's admin SSH key. The servers hold no repository access, so they cannot pull their own backup.

**Drills.**

- **Monthly, automatic:** `server-backup-drill.service` runs `restic check --read-data-subset=10%`. It restores the newest dump plus about 20 random files to a scratch directory and compares checksums to the mirror. It runs `gunzip -t` on any `.sql.gz` and `PRAGMA integrity_check` on SQLite files. It writes a pass or fail stamp that the notifier reads. This proves the repository is readable and the files match. It cannot prove a service starts.
- **Manual, twice a year and after any Immich or Stalwart major upgrade:** build a scratch Hetzner server from the repo, restore, verify with the checks below, destroy it. Hetzner bills hourly, so a drill costs cents.

**Verification commands (every service):**

- `restic -r <repo> check` returns clean.
- `diff -r` or `rsync -rcn` between the restored tree and the mirror shows nothing.
- Per-service checks follow.

**Outline for the second operator (the runbook turns each line into a typed command):**

*Common start*

1. Plug in the drive. `sudo cryptsetup open /dev/disk/by-label/servers-backup backup`, enter the passphrase from Proton Pass. `sudo mount /dev/mapper/backup /mnt/backup`.
2. `export RESTIC_REPOSITORY=/mnt/backup/restic-media` (or `restic-mail`), then `restic snapshots`. The password comes from `RESTIC_PASSWORD_COMMAND`, not the command line ([restic FAQ](https://restic.readthedocs.io/en/stable/faq.html), [new repo docs](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)).
3. `restic restore latest --target /tmp/restore`. Run as root so ownership returns (unverified; the restore page does not state it).
4. Create the new server from the `servers` repo's provisioning step and stop at "services installed, stopped, empty".

*Media server*

5. Copy the restored trees onto the server with `rsync -a`: `UPLOAD_LOCATION/{library,upload,profile,backups}` and the dubplate library.
6. Start Immich. On the welcome screen choose "Restore from backup" and pick the newest dump ([docs](https://docs.immich.app/administration/backup-and-restore)). Then in Administration > Jobs run the missing-thumbnail and transcoding jobs. Immich notes the restore flow changed in v2.5.0 and may run migrations on a version mismatch, so record the Immich version beside each backup.
7. dubplate: `dubplate-server restore --from-file <snapshot>`, then `dubplate-server doctor` and `member list`. Re-run any removals or demotions made since the snapshot (the runbook's "After a restore").
8. Verify Immich: log in, compare the asset count with the pre-disaster number the runbook records. dubplate: `doctor` is clean and a track plays.

*Mail server*

9. Install the same Stalwart version as the `VERSION` file records. Stop it. Copy the restored data directory to the path `storage.data` names. Start it.
10. Repoint DNS (A, MX, SPF, DKIM, PTR) at the new IP. Set Hetzner reverse DNS. Port 25 stays blocked on a new account until Hetzner lifts it, so budget for that delay (from the architecture context).
11. Verify: log in over JMAP, count messages per mailbox against the pre-disaster numbers, send and receive a test message, and check the DKIM selector resolves.
12. If the raw copy will not start, use the Vandelay archive: `vandelay export` into a fresh Stalwart.

## 6. Secrets

- **Names in the age store** (via `secret-set.sh NAME --stdin`, never the command line): `BACKUP_RESTIC_PASSWORD`, `BACKUP_LUKS_PASSPHRASE`, `BACKUP_LUKS_KEYFILE` (base64), `BACKUP_SSH_MAIL`, `BACKUP_SSH_MEDIA`. Add each to `registry.md`.
- **On pavilion:** TPM2-bound credentials loaded by systemd, so the password never appears in a unit file, an environment variable, or a process listing. Pass `--password-file "$CREDENTIALS_DIRECTORY/restic-password"`. restic's FAQ calls `RESTIC_PASSWORD_COMMAND` and password files safe and warns that inline assignment can leak through the process list ([FAQ](https://restic.readthedocs.io/en/stable/faq.html)).
- **For the second operator:** the LUKS passphrase slot, the restic password, and the LUKS header backup go into the Proton Pass shared vault. The keyfile slot and SSH private keys stay on pavilion only. Losing the restic password loses the data permanently ([docs](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)). A second repository key (`restic key add`) for the second operator is possible, but one shared password is simpler.
- **Ordering hazard:** the age key lives in 1Password today. The backup passwords must be in Proton Pass before 1Password is retired, or the drive is unreadable.

## 7. Pitfalls

- **Locks.** A reboot or sleep mid-backup leaves a lock. restic treats locks older than about 30 minutes as stale and `restic unlock` clears only those ([forum](https://forum.restic.net/t/detecting-stale-locks/1889/25)). Add `--retry-lock 5m` (unverified flag name for 0.19; check `restic backup --help`).
- **Sleeping USB drive.** I found no report tying spin-down to restic failures. Test a run after a long idle and a drive that took a minute to spin up.
- **UAS and SMART.** See section 4.
- **Prune on slow disks.** See section 1. Cache lives on the internal disk by default, which helps; keep it there.
- **User timers need linger.** Already on for glw907 per `bluefin-admin.md`; the staleness notifier depends on it, the backup itself does not.
- **ostree.** `/etc` is writable and persistent, so units and credentials survive upgrades. The base image can change its package set; record "restic from base image" in the runbook.
- **Mount points.** Mount under `/run/media` or `/mnt` created at runtime, not a path in the image.
- **Stalwart restore compatibility.** A raw RocksDB copy ties you to a version; hence the `VERSION` file.

## Recommendation

**Data flow, server to drive.**

1. About 03:00, a root timer on each server prepares `/srv/backup-export` (Immich: ACL read access to `UPLOAD_LOCATION`, which already holds the 02:00 dump; Stalwart: warm copy, brief stop, delta copy, start; dubplate: snapshot to the export). It writes `STAGED-AT` and `VERSION`.
2. About 04:30, pavilion's system timer (or the next boot, via `Persistent=true`) runs. It checks `STAGED-AT`, then pulls with `rsync -a --delete --max-delete=N` over the `restrict,command="rrsync -ro …"` key into `/var/lib/server-backup/mirror/<server>` on the internal disk.
3. If the LUKS drive is present, a privileged step opens and mounts it with the keyfile credential. `restic backup` of the mirror goes into `restic-mail` or `restic-media`, tagged with the server and the staged version. `forget` runs per policy. Then unmount and close.
4. State files record success or a miss. A user timer notifies on 3 and 10 consecutive misses. Weekly and monthly jobs run `check`, the sample-restore drill, and SMART.

Restic is the history and integrity layer. The servers are never given a write path or a credential. The USB drive holds only encrypted restic repositories, so a plugged-in drive in another machine yields nothing without both LUKS and restic passwords.

## Risks

- **The residual risk of the ruling, stated once:** the drive is the only backup copy, so one event that takes the drive (failure, theft, fire, or flood at the house) during a server loss takes mail and photo history with it.
- **Challenge to the decided architecture:** "pavilion pulls with restic" is not a native restic mode. It works only through the staged-mirror design above. The mirror on pavilion's internal disk is in practice a second copy of the latest state, which sits outside the "drive only" wording. Geoff decides whether to keep it (see open questions).
- **Stalwart on RocksDB has no documented online backup** as of mid-2026. The Stalwart agent should weigh a store backend with an online backup path (the docs' [backup page](https://stalw.art/docs/management/cli/database/backup) as summarized by search lists SQLite `.backup` and Litestream; I could not fetch the page, so this is unverified) against RocksDB's speed, or accept a nightly seconds-long stop.
- **dubplate's backup verb targets rclone remotes.** A local-export path is unverified.
- A compromised pavilion reads everything. That is inherent in any pull model with one trusted collector.
- Pavilion off for a long stretch gives no alert. A server-side check would need a write path from pavilion, which this design avoids.
