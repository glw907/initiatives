# Immich: PikaPods to a self-managed Debian 13 Hetzner server (research brief, 2026-10-17)

Scope: move Immich off PikaPods onto the shared media server (Debian 13, Docker Compose), co-tenant with dubplate. Every claim carries a link. "Unverified" marks anything I could not confirm from a primary source. Measured facts about the live instance come from read-only GET calls to `https://photos.907.life/api` made on 2026-10-17.

## 1. Version, cadence, install method, upgrades

**Current version.** The newest release is [v3.3.3](https://github.com/immich-app/immich/releases/tag/v3.3.3), published 2026-10-14 (a performance fix for the explore page and people queries, no migration warnings). The PikaPods pod reports v3.3.1 (`/server/version`, `/server/about`). Patch releases arrive about weekly; the pod itself ran v3.2.4 until about 2026-10-12.

**Cadence.** Minor releases land every three to seven weeks: [v2.2.0 2025-10-30, v2.3.0 11-19, v2.4.0 12-18, v2.5.0 2026-01-27, v2.6.0 03-19, v2.7.0 04-07, v3.0.0 07-02, v3.1.0 07-29, v3.2.0 09-10, v3.3.0 10-07](https://github.com/immich-app/immich/discussions/categories/announcements). Each minor is preceded by several `-rc` tags.

**Breaking-change history.** Immich uses semantic versioning and states that [breaking changes, including API and deployment changes, are meant to occur only in major releases](https://docs.immich.app/install/upgrading). Only v3.0.0 carries the breaking-change label in the recent announcements. Its [release notes](https://github.com/immich-app/immich/releases/tag/v3.0.0) drop pgvecto.rs, remove several API endpoints, tighten OAuth, and require numpy 2.4 for ML; the [v3 migration post](https://immich.app/blog/v3-migration) adds that x86 CPUs must support x86-64-v2 (the [requirements page](https://docs.immich.app/install/requirements) says most CPUs since about 2012 qualify; unverified for Hetzner's CX hardware specifically). The restore flow also changed in v2.5.0 ([backup docs](https://docs.immich.app/administration/backup-and-restore)). Since we install fresh at v3.x, none of the v1/v2 migrations (pgvecto.rs to VectorChord) apply.

**Supported install method.** [Docker Compose is "the recommended method to run Immich in production"](https://docs.immich.app/install/docker-compose). The sidebar lists an install script (labelled Experimental), Kubernetes, Portainer, and several NAS or community routes, but Compose is the only one the docs call production-grade. Use it. The current release compose file runs four containers: immich-server, immich-machine-learning, valkey, and Postgres from `ghcr.io/immich-app/postgres:14-vectorchord0.4.3-pgvectors0.2.0` (fetched from the [latest release assets](https://github.com/immich-app/immich/releases/latest/download/docker-compose.yml) on 2026-10-17). It sets `restart: always` and enables container healthchecks.

**Upgrades and rollbacks.** The procedure is: read the release notes, set `IMMICH_VERSION` in `.env`, run `docker compose pull && docker compose up -d` ([upgrading](https://docs.immich.app/install/upgrading)). The mobile app works with the current and previous major, and the server needs a matching major, so upgrade clients first. The key rule: [downgrading is not supported, "even within the same minor version"](https://docs.immich.app/install/upgrading). Rollback therefore means restoring a pre-upgrade backup, not running an older image against a migrated database. Before each upgrade, take a manual database dump (Administration, Job Queues, Create Database Dump) and a Hetzner snapshot of the server's local disk. The `:v3` tag floats across minors; pin an exact tag like `v3.3.3` instead.

## 2. Migration path from PikaPods

**What PikaPods exposes.** SFTP is per pod: [host `<pod>.pikapod.net`, port 22, a generated username and password, writable only in subfolders](https://docs.pikapods.com/manage/files). Database access is a separate toggle that gives an [Adminer web login](https://docs.pikapods.com/manage/database), and the docs mention only SQLite and MongoDB. I found no page saying Immich pods get Postgres access, so assume none. PikaPods' own [manual backup recipe](https://docs.pikapods.com/manage/backup) is: enable SFTP and database access, stop the pod, copy files over SFTP, export the database, restart. Its [Immich page](https://docs.pikapods.com/apps/immich) covers only external libraries and a `/libraries` folder. Which Immich folders appear under SFTP is unverified; Geoff must enable SFTP and look.

**The database comes out through Immich itself.** This removes the biggest unknown. The pod runs Immich's automatic dump (`system-config`: `backup.database.enabled`, daily 02:00, keep 14). `GET /admin/database-backups` lists 14 dumps, the newest `immich-db-backup-20261017T020000-v3.3.1-pg16.10.sql.gz` at about 38.6 MB, and the API has `GET /admin/database-backups/{filename}` to download one ([OpenAPI spec](https://raw.githubusercontent.com/immich-app/immich/main/open-api/immich-openapi-specs.json)). The dumps live in `UPLOAD_LOCATION/backups`, so they should also sit under SFTP. The source database is Postgres 16.10. I did not download a dump (the sandbox refused), so its contents are unverified, but the size fits a database holding face and CLIP embeddings.

**Official restore path.** The [backup and restore page](https://docs.immich.app/administration/backup-and-restore) documents the fresh-install flow:

1. Put the old `backups`, `encoded-video`, `library`, `profile`, `thumbs`, and `upload` folders into the new `UPLOAD_LOCATION`.
2. Start the stack; on the welcome screen choose Restore from backup.
3. Immich enters maintenance mode, runs integrity checks, and lets you pick a dump or upload a `.sql.gz`.
4. It restores, runs migrations if needed, health-checks, and rolls back on failure.

The server must not have run against the database first; if it did, the docs say Postgres conflicts may appear and `DB_SKIP_MIGRATIONS=true` is the workaround. File paths live in the database and Immich does not rescan the library, so database and files must match.

**Which folders.** Critical and irreplaceable: `library`, `upload`, `profile`, plus the database. `thumbs` and `encoded-video` are regenerable by jobs. Copy them anyway (the docs estimate [thumbnails and transcodes add 10 to 20 percent](https://docs.immich.app/install/requirements)); regenerating avoids nothing worth the CPU time. Here that is roughly 2 to 4 GB (estimate, unverified).

**Version matching.** Restore at the same version as the dump (v3.3.1) and upgrade afterward. Immich shows a compatibility flag per backup and says [cross-version restores may need migrations and a matching version is preferred](https://docs.immich.app/administration/backup-and-restore). Pin `IMMICH_VERSION=v3.3.1` for the restore, then step to the then-current v3 patch.

**Postgres major version risk.** The source is Postgres 16; the current release compose ships Postgres 14. The docs do not address restoring across Postgres majors (the page I fetched is silent). A dump from 16 loaded into 14 may or may not work; I found no report either way. `ghcr.io/immich-app/postgres` publishes [14, 15, 16, 17 and 18 tags with VectorChord 1.1.1](https://github.com/immich-app/immich/pkgs/container/postgres), and Immich accepts [Postgres 14 up to but excluding 20 and VectorChord 0.3 up to but excluding 2.0](https://docs.immich.app/administration/postgres-standalone). Settle it in the rehearsal: try the stock image first; if the load errors, use a `16-vectorchord` tag. Do not guess on the server.

**Fidelity check against the live instance.** The restore carries everything held in the database: 155 people, the 1 shared album ("January Car Crash", 5 assets, with a shared link), 3 shared links, 5 users (Geoff 15.1 GB, the second operator 4.2 GB, three empty accounts), partner shares, favorites, archive state, metadata edits, and all server settings (storage template, job concurrency, ML models, SMTP). Face and CLIP embeddings travel inside the dump, so ML does not need to re-run on 3,816 assets.

**Fallbacks and why they are worse.** [immich-go](https://github.com/simulot/immich-go) is compatible with v2 and v3, has a server-to-server `from-immich` command, and recreates albums and tags in general, but the README does not confirm that `from-immich` keeps favorites, archive state, people, or faces, and it calls itself early and not extensively tested. Treat it as an assets-plus-albums fallback only. Any API re-upload re-creates assets as new rows with new IDs, which breaks shared links and loses face names (unverified for each field, but the people tables are database-resident). Keep it as the plan C if the dump cannot be loaded at all.

## 3. Cutover and exposure

**Facts.** The Cloudflare proxy caps request bodies at [100 MB on Free and Pro, 200 MB on Business](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/). The Immich mobile app does not chunk uploads; a maintainer said [chunking is "on the To Do list but no concrete ETA"](https://github.com/immich-app/immich/discussions/13573), and a user report describes large videos failing and the app stopping silently ([discussion 13573](https://github.com/immich-app/immich/discussions/13573), [discussion 23862](https://github.com/immich-app/immich/discussions/23862)). The library holds 92 videos totalling 7.65 GB, an 83 MB average, so some videos probably exceed 100 MB. The current proxied hostname has the same limit, which means the status quo may already fail on large videos.

**Cloudflare Tunnel.** I found no primary source stating whether Tunnel traffic escapes the 100 MB cap. Tunnel traffic still enters through Cloudflare's edge, so I expect the cap to apply. Unverified; do not rely on Tunnel for large uploads.

**Recommendation: direct exposure, DNS-only, Caddy with Let's Encrypt.** Reasons:

- It removes the 100 MB cap, which is the one functional defect of the current setup.
- Immich documents Caddy as a one-line `reverse_proxy` to port 2283 with automatic HTTPS ([reverse proxy docs](https://docs.immich.app/administration/reverse-proxy)). The nginx-only upload tuning (body size, buffering, 600 s timeouts) has no Caddy equivalent that needs setting; Traefik is the one that needs a timeout raise.
- [Caddy gets certificates over HTTP or TLS-ALPN challenge on ports 80 and 443](https://caddyserver.com/docs/automatic-https) and renews them itself, so no Cloudflare API token lands on the server. The DNS challenge would need a custom Caddy build, which Debian's package does not provide.
- Debian 13 packages [Caddy 2.6.2](https://packages.debian.org/trixie/caddy), which is old; the Caddy project's own apt repository is the alternative. Choose one in the runbook. The version gap matters little for a plain reverse proxy, but security updates are the reason to prefer the upstream repo (unverified which is better maintained; decide at build time).
- The cost: the server IP becomes public in DNS. For a family photo host with key-only SSH, a Hetzner Cloud Firewall allowing only 22, 80, and 443, and Immich's own login, this is acceptable. The IP is not secret anyway once it appears in certificate transparency logs.

**Mobile apps.** If `photos.907.life` keeps its name and moves to the new IP, no client change is needed: the hostname, `externalDomain`, and shared-link URLs stay valid. Sessions and API keys are database rows, so they should survive the restore (unverified; check in the rehearsal by testing the existing API key against the restored copy). The apps keep their asset-sync state by checksum. If a client misbehaves, log out and in again. Test one phone against a temporary hostname such as `photos-new.907.life` during the rehearsal.

**Cutover sequence.** Rehearse on a temporary hostname, then at the final window: freeze uploads, take a fresh dump, stop the pod, copy the delta, restore, switch the DNS record from proxied CNAME to DNS-only A and AAAA, and confirm Caddy fetches its certificate on the first request. Keep the pod stopped, not deleted, for a week.

## 4. Sizing

**Requirements.** The [docs](https://docs.immich.app/install/requirements) say minimum 6 GB RAM and 8 GB recommended, minimum 2 cores and 4 recommended, and that 4 GB systems can run with ML disabled. Postgres needs at least 2 GB if Docker limits are set. Postgres data should sit on local SSD, never a network share.

**ML memory.** The [CLIP page](https://docs.immich.app/features/searching) lists about 1 GB peak for the default `ViT-B-32__openai`; bigger models reach 3 to 4 GB. I found no published figure for the default face model `buffalo_l` or the OCR model; read `docker stats` on the rehearsal copy. Models [unload after 300 seconds idle](https://docs.immich.app/install/environment-variables) (`MACHINE_LEARNING_MODEL_TTL`), one worker is the default, and more workers duplicate models.

**Why load stays low here.** The restore brings the embeddings, so there is no bulk ML run. ML only touches new uploads and the nightly cluster task. Live settings already show low concurrency (face detection 2, smart search 2, video conversion 1, ffmpeg preset `ultrafast`, 720p H.264, transcode `required`).

**Controls.**

- Cap the ML container (for example `mem_limit: 3g`, `cpus: 2`); the [FAQ warns](https://docs.immich.app/FAQ) a memory limit works by killing the container, which is acceptable for ML because jobs retry.
- Set job concurrency to 1 and ffmpeg threads to 1 or 2, as the FAQ suggests.
- Do not cap Postgres or the server tightly.
- `buffalo_s` and disabling OCR cut memory, but need a face-detection rerun and lose accuracy; skip both.
- [Remote ML](https://docs.immich.app/guides/remote-machine-learning) can run on pavilion for a bulk rerun with the local container as fallback. It is optional, and the docs warn the remote container has no security.
- For dubplate, set `OOMScoreAdjust` negative and a `MemoryLow` on its unit so the kernel kills ML first (my recommendation, not from a source).
- Add a 2 GB swap file; Hetzner images ship without swap (unverified).

**Disk.** Originals 19.3 GB, plus 10 to 20 percent for derivatives, plus Postgres at [1 to 3 GB](https://docs.immich.app/install/requirements), plus 14 dumps at about 40 MB, gives about 28 GB for Immich (estimate). Add dubplate's 6.6 GB, Docker images (about 6 to 8 GB, estimate), and the OS. About 45 to 50 GB of an 80 GB disk. Local disk is enough. A [Hetzner volume](https://docs.hetzner.com/cloud/volumes/overview/) offers up to 5000 IOPS but is excluded from server snapshots and backups, and attaches to one server; keep Postgres on the root disk regardless, and add a volume only when the library outgrows it.

**Server type and a finding that challenges the plan.** The [15 June 2026 price adjustment](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/) makes location the dominant cost (monthly, excl. VAT and IPv4):

| Option | vCPU / RAM / disk | EUR | USD |
|---|---|---|---|
| CX33, Falkenstein, Nuremberg or Helsinki (Intel, x86) | 4 / 8 GB / 80 GB ([source](https://www.bitdoze.com/md/hetzner-cloud-cost-optimized-plans.md)) | 8.49 | 9.99 |
| CAX21, same EU sites (Arm) | 4 / 8 GB / 80 GB | 10.49 | 12.49 |
| CPX32, EU | 4 / 8 GB / 160 GB ([sparecores](https://sparecores.com/server/hcloud/cpx32)) | 35.49 | 41.99 |

The US sites list only CPX and CCX types; [CX and CAX are not offered there](https://www.bitdoze.com/md/hetzner-cloud-cost-optimized-plans.md). The new price applies to new orders and rescales; [unchanged existing rentals keep their terms](https://www.vincentschmalbach.com/hetzner-cheap-cloud-unavailable-price-increases/), so musicbox probably stays at its old price until replaced (unverified for this account). Moving the media server from Hillsboro to the EU cuts the 8 GB option from about 73 USD to 10 USD a month, but costs latency from Alaska (not measured) and means a different region than musicbox. Hetzner also says a server's location cannot be changed; you [rebuild from a snapshot](https://docs.hetzner.com/cloud/servers/faq/). This account's ability to order is unverified (the Hetzner API call was refused in this session); check in the console before committing.

**Arm.** Immich publishes arm64 images, and Arm NN acceleration needs Mali GPUs, so CAX runs ML on CPU like x86 ([hardware acceleration](https://docs.immich.app/features/ml-hardware-acceleration)). It works, but CAX21 costs more than CX33, and the dubplate and Stalwart binaries would need arm64 builds. Prefer CX33.

## 5. Backup and restore

**What a full restore needs.** The [docs](https://docs.immich.app/administration/backup-and-restore): all of `UPLOAD_LOCATION` (at minimum `library`, `upload`, `profile`) plus the database. Immich writes its own gzip dump daily at 02:00 into `UPLOAD_LOCATION/backups` and keeps 14. Dumps hold metadata only, not photos.

**Consistency.** Best is to stop immich-server during the backup. Otherwise [dump the database first, then copy files](https://docs.immich.app/administration/backup-and-restore): the worst case is unknown files that can be re-uploaded, while the reverse order can leave broken assets. The nightly 02:00 dump already satisfies "database first"; schedule the pull for later, with a margin.

**Pull-based restic.** [restic backs up local paths and has no remote-source mode](https://restic.readthedocs.io/en/stable/040_backup.html); `--stdin-from-command` runs a command and stores its output. A pull design needs one hop:

- Option A (recommended): on pavilion, a timer runs `rsync -a --delete` over SSH into a staging directory on the USB drive, then `restic backup` of the staging directory. Files and dumps are plain on disk between runs, and the staging mirror doubles as a ready copy.
- Option B: mount the server read-only with sshfs and run restic over the mount. Fewer copies, but a flaky link mid-run is harder to reason about.
- Give pavilion a dedicated SSH key restricted on the server to a read-only forced command (`rrsync -ro`) so the server holds no backup credentials and pavilion cannot write back.
- Add `--one-file-system` care: restic skips mounts under that flag, so a sshfs or staging mount needs deliberate handling.
- The server-side order is unattended: 02:00 Immich dump, then pull at a later hour with `Persistent=true` on pavilion's timer.

**Restore drill, fresh server.**

1. Provision Debian 13 and Docker; place `.env`, compose file, and Caddyfile from the repo.
2. Restic-restore the library tree to `UPLOAD_LOCATION`, then `docker compose up -d` at the pinned version of the dump.
3. On the welcome screen, Restore from backup and choose the newest dump.
4. Check the integrity page ([missing files, untracked files, checksum mismatches](https://docs.immich.app/administration/system-integrity)), then users, people, album, a shared link, a sampled original, a new upload, and a restart.

Run this drill on pavilion before cutover; it is the same procedure as the migration rehearsal.

## 6. Hardening and ops

- **Docker.** Install `docker-ce` and the compose plugin from [Docker's Debian 13 repo](https://docs.docker.com/engine/install/debian/), not Debian's `docker.io` ([Immich warns that the distro's outdated Docker package causes errors](https://docs.immich.app/install/docker-compose)). Docker [publishes ports through its own iptables rules, bypassing ufw](https://docs.docker.com/engine/install/debian/). Bind Immich to loopback (`127.0.0.1:2283:2283`) and keep a local patch of the upstream compose file in the servers repo; Caddy is the only listener on 80 and 443. Add the Hetzner Cloud Firewall as the outer layer.
- **Logs.** Docker's json-file driver has [no rotation by default](https://docs.docker.com/engine/logging/drivers/json-file/); set `max-size: 10m`, `max-file: "3"` in `daemon.json`.
- **Health.** The compose file already enables healthchecks. Add a systemd timer that fails loudly if `/api/server/ping` stops answering, and watch the nightly integrity checks.
- **Updates.** Use `unattended-upgrades` for Debian security only. Do not auto-update Immich: it rules out downgrades and ships schema changes. Pin the tag, read each release's notes, upgrade by hand about monthly after a manual dump and snapshot. No Watchtower.
- **Admin CLI.** `immich-admin` ships in the server image: [reset-admin-password, list-users, enable-maintenance-mode, schema-check](https://docs.immich.app/administration/server-commands). Put the three commands the second operator might need in the emergency section.
- **Settings worth checking after restore** (live values):
  - Keep the storage template (`{{y}}/{{y}}-{{MM}}-{{dd}}/{{filename}}`); changing it later triggers a file-move migration, so do not touch it during the move.
  - OAuth is off and password login on; leave both.
  - SMTP is `smtp.fastmail.com:465`. Hetzner [blocks 25 and 465 by default](https://docs.hetzner.com/cloud/servers/faq/), so album-invite mail will fail from the new server. Switch to port 587 (STARTTLS) now, and to Stalwart when mail moves.
  - Trash is on at 30 days; user delete delay is 7 days.
  - Set `IMMICH_TRUSTED_PROXIES` to the proxy address so logs and rate limits see real client IPs ([env vars](https://docs.immich.app/install/environment-variables)).
  - Consider turning off the new-version check if the box should make no outbound lookups (optional).
  - Three failed-job counters exist on the pod (36 background tasks, 2 thumbnails, 1 facial recognition); clear or retry them on the rehearsal copy to learn whether they are real.

## 7. Known pitfalls

- **Config rename on v3 upgrade.** A [Cloudron thread](https://forum.cloudron.io/topic/15680/immich-broken-after-update-to-3.0.1/12) reports an old stored `libopus` audio codec value failing config validation before migrations run after v3.0. The pod already runs v3.3.1 with a valid config, so a fresh restore at v3.3.1 should not hit it, but it shows config lives in the database and can break on upgrade. The fix suggested there came from an AI assistant and is unverified.
- **Old vector extension.** An [Unraid report](https://forums.unraid.net/topic/198609-immich/page/2/) describes a crash loop (`$libdir/vectors` missing) when a database made with pgvecto.rs met a newer image. Not applicable to a clean v3 database, which is another reason to rehearse with the real dump.
- **Search path in manual restores.** The documented command-line restore rewrites `search_path` with `sed` so VectorChord types resolve. Use the UI restore, or copy the documented command exactly. A [coop-cloud recipe](https://git.autonomic.zone/recipe-maintainers/immich/commit/393bfa6fc8ce9b1a0a5286c1af45b14268ca39cd) also warns against dropping the database, because the old extension's worker can crash Postgres.
- **A blank instance that already ran.** If first start shows "create admin account," the restore did not reach the database in use ([ZimaSpace checklist](https://shop.zimaspace.com/blogs/support-tips/safe-immich-migration-checklist-new-home-server), vendor content). Never let a blank instance take uploads before restoring.
- **Files and database drift.** Immich stores paths; copying files without the matching dump, or the reverse, yields broken or untracked assets. The integrity checks flag both.
- **PikaPods specifics.** I found no PikaPods forum or Reddit report about leaving with an Immich pod, so there is no community precedent to lean on. PikaPods' daily server backups are [not guaranteed complete for apps with databases](https://docs.pikapods.com/manage/backup), so do not treat them as the safety net. Database access is probably not offered for the Immich pod; the in-app dump is the route.
- **Cloudflare cap.** See section 3; uploads over 100 MB fail through the proxy and the app does not retry.
- **Search tool limits in this session.** A few fetches were refused by the sandbox (Hetzner API, one Cloudflare limits page, one PikaPods forum search). Items affected are marked unverified.

## Recommendation

1. Install Immich with the official Docker Compose files on the media server, pinned to an exact v3 tag, Caddy in front, loopback-only binding, local disk only.
2. Migrate by database dump plus the full `UPLOAD_LOCATION` tree, not immich-go. Pull the dump with `GET /admin/database-backups/{filename}` or SFTP; pull files with SFTP and `rsync` or `rclone`.
3. Expose it DNS-only with Caddy and Let's Encrypt on 80 and 443, keeping `photos.907.life`. This removes the 100 MB Cloudflare cap and needs no client change.
4. Size the server at 8 GB and 4 vCPU. ML load is small because the embeddings restore from the dump. Cap ML at about 3 GB and protect dubplate with systemd memory settings.
5. Challenge to the decided architecture: the 8 GB option is about 10 USD a month in the EU (CX33) and about 73 USD a month in Hillsboro (CPX31). Choose the EU region unless Alaska latency to dubplate matters more than roughly 60 USD a month, and check that CX is orderable on this account first.
6. Back up by a pavilion-side rsync into staging plus restic, on a read-only forced-command key, after the 02:00 Immich dump. Run the restore drill before cutover.

8. Keep the pod stopped for a week, then delete it. Record the dump file names, image digests, and tags in the servers repo.

## Risks

- Postgres 16 to 14 load failure: mitigated by rehearsal and a 16-tag image.
- Hetzner CX capacity or this account being restricted: fallback is a CPX32 in the EU (about 42 USD) or CPX31 in the US (about 73 USD).
- Files copied at a different moment than the dump: mitigated by the freeze, the stopped pod, and the integrity checks.
- Public IP exposure: mitigated by key-only SSH, the Cloud Firewall, and loopback binding.
- ML or transcoding memory spikes hurting dubplate: mitigated by container limits, systemd OOM ordering, and swap.
- Single backup copy on the USB drive (a decision already made): a failed drive plus a failed server loses the library; the restore drill and a periodic `restic check` reduce, not remove, this.
- Immich's no-downgrade rule: every upgrade needs a fresh dump and snapshot first.
