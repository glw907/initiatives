# Stalwart on Debian 13 at Hetzner Cloud: research brief (2026-10-17)

Scope: one Stalwart server for 907.life with two users, built from code. Read-only research. Sources are the Stalwart docs source ([stalwartlabs/website](https://github.com/stalwartlabs/website), commit of 2026-10-03, served at stalw.art/docs), the server repo and releases, the support forum, and Hetzner's API and docs. Hetzner prices come from a read-only `GET /v1/server_types` and `/v1/pricing` call made today. The account bills in USD with no VAT.

## 1. Version, cadence, breaking changes, upgrades

The current release is [v0.16.26](https://github.com/stalwartlabs/stalwart/releases/tag/v0.16.26), out 2026-10-11. The 0.16 line has shipped a patch about once a week since [v0.16.0](https://github.com/stalwartlabs/stalwart/releases/tag/v0.16.0) on 2026-04-20: 27 releases in 26 weeks. Each one fixes 10 to 40 items in the [CHANGELOG](https://github.com/stalwartlabs/stalwart/blob/main/CHANGELOG.md). Some of those fixes touch exactly what this server will use. v0.16.25 fixed three DKIM rotation bugs, one of which sent mail unsigned. v0.16.26 fixed RocksDB rewriting every stored blob on each compaction. It also added a "Breaking:" item mid-line: x86_64 builds now need an x86-64-v2 CPU. Hetzner's current CPUs meet that, but it shows that a patch release can still break things.

0.16.0 was a full redesign of configuration and management ([UPGRADING/v0_16.md](https://github.com/stalwartlabs/stalwart/blob/main/UPGRADING/v0_16.md)). The TOML files are gone. A small `config.json` describes only the datastore, and every other setting is a JMAP object stored in the database. The REST API became JMAP. Account names must be full email addresses, and DAV paths changed to `/dav/cal/alice%40example.com`. A fresh install avoids all of that migration pain.

Version 1.0 is close. The vendor's [road to 1.0 post](https://stalw.art/blog/road-to-stalwart-1-0/) (2026-06-21) says 1.0 will finalize the database schema, "most likely around October". A later [August post](https://stalw.art/blog/how-we-use-ai/) mentions a `v1.0.0` development branch. That branch is not public; the repo shows only `main` and Dependabot branches. The [migration-proxy post](https://stalw.art/blog/migration-proxy/) (2026-06-10) says the vendor does not "foresee 1.0 introducing the kind of major breaking changes" and intends 1.0 to be "an automated upgrade from v0.16". It calls this an aim, "not yet a guarantee".

On upgrades, the [upgrade page](https://stalw.art/docs/install/upgrade) says patches are safe, minors need the release notes, and operators should upgrade "only when necessary". The same page still promises 1.0 in "the first half of 2026", so the docs lag the code. Within 0.16, each release note says to replace the binary. I found no documented downgrade path, so treat rollback as "restore the pre-upgrade backup and the old binary". That is unverified as a supported procedure.

## 2. Install method

- Distro package: none for Debian. Arch carries [stalwart 0.16.8](https://archlinux.org/packages/extra/x86_64/stalwart/) and FreeBSD has ports. I found no Debian or Ubuntu repository.
- Official script: [install.sh](https://github.com/stalwartlabs/stalwart/blob/main/install.sh) always downloads `releases/latest`. It takes no version argument and checks no hash. It writes its own unit, creates the `stalwart` user, and uses FHS paths (`/usr/local/bin/stalwart`, `/etc/stalwart/config.json`, `/var/lib/stalwart`) ([Linux docs](https://stalw.art/docs/install/platform/linux)).
- Docker: the [Dockerfile](https://github.com/stalwartlabs/stalwart/blob/main/Dockerfile) is `debian:trixie-slim` plus the same binary. Staff [confirmed](https://support.stalw.art/t/1512) that the official image cannot write the wizard's default log file under `/var/log/stalwart`, so `docker logs` stays empty. A [June report](https://github.com/stalwartlabs/stalwart/issues/3190) says auto-ban banned the Docker bridge IP, which locked out everyone. That report was auto-closed for triage and is unverified.

**Recommendation:** run the native binary at a pinned version, with no Docker and no install.sh. The repo holds a `VERSION` file and the expected SHA-256. Each release asset carries a GitHub digest and a `.sigstore.json` bundle, for example `stalwart-x86_64-unknown-linux-gnu.tar.gz` at `sha256:ed5095ff…` for 0.16.26. Provisioning downloads the versioned asset and verifies it with `gh attestation verify` or the pinned hash. It installs the binary and a repo-owned copy of the [upstream unit](https://github.com/stalwartlabs/stalwart/blob/main/resources/systemd/stalwart-mail.service). That unit uses `Type=notify`, which needs 0.16.26 or later, and `AmbientCapabilities=CAP_NET_BIND_SERVICE`. Reasons: a single-purpose host gains nothing from a container runtime. Client IPs reach auto-ban unaltered. Logs go to journald. An upgrade is a binary swap the repo records.

## 3. Storage backend and backups

All four stores default to RocksDB on local disk. The docs call RocksDB "the recommended backend for single-node installations" ([RocksDB](https://stalw.art/docs/storage/backends/rocksdb), [wizard](https://stalw.art/docs/install/platform/linux)). In the Community edition, PostgreSQL works as a datastore; only read replicas are Enterprise ([PostgreSQL](https://stalw.art/docs/storage/backends/postgresql)). Running it here would mean a second service to operate for two users. FoundationDB is for clusters.

**RocksDB has no online backup.** The server does not use RocksDB checkpoints or BackupEngine; the source tree has neither. Both the built-in `--export` dump and the [database console](https://stalw.art/docs/management/maintenance/database) need the server stopped. The export docs also say it is "not a substitute for proper backup procedures" ([migration utility](https://stalw.art/docs/management/maintenance/migration)). A [request](https://support.stalw.art/t/170) for a hot export through a RocksDB secondary instance, and a [checkpoint request](https://support.stalw.art/t/896), have no response yet. Staff [gave the supported recipe](https://support.stalw.art/t/386) on 2026-05-28: "stop the server, rsync (or filesystem-snapshot) the directory …, restart. RocksDB is consistent on shutdown".

**SQLite was weighed and rejected.** The SQLite store opens in WAL mode ([source](https://github.com/stalwartlabs/stalwart/blob/main/crates/store/src/backend/sqlite/main.rs)). A live `sqlite3 .backup` or `VACUUM INTO` copy would therefore be consistent with no downtime. That is its one real advantage. Against it: SQLite is not the default and fewer operators run it. The 0.16.0 notes also fix "SQLite: thread pool exhaustion". With the default blob setting, every message body lands inside one large database file that each copy rewrites in full. RocksDB's stop can be cut to seconds, which removes SQLite's advantage.

**Backup recipe (RocksDB):** a root timer, or a forced-command SSH call from pavilion, runs these steps:
1. `rsync -a --delete /var/lib/stalwart/ /srv/backup-export/stalwart/` while the server runs (warm copy).
2. `systemctl stop stalwart`.
3. Run the same rsync again. Only the WAL, the MANIFEST, and new SST files change, so this pass is short.
4. `systemctl start stalwart`, and write the `VERSION` file beside the copy.

Pavilion then pulls the copy read-only. The server holds no backup credentials. Sending MTAs retry deferred deliveries, so a stop of a few seconds loses no mail. Clients reconnect. This agrees with the [backups brief](2026-10-17-backups.md). That brief cites a stalw.art "database backup" page, but no such page exists in the docs source.

**Second, logical layer:** [Vandelay](https://stalw.art/docs/migration/import-export/backup) runs from pavilion over JMAP. It keeps one SQLite archive per account covering mail, contacts, calendars, Sieve scripts, and identities. Each run refreshes the archive incrementally. Restore is `vandelay export`. This layer does not depend on Stalwart's internal schema. It survives a bad upgrade or a corrupted store. It is also new (v1.0.12) and has one [reported failure after an upgrade](https://support.stalw.art/t/744); the drill must test it. [`stalwart-cli snapshot`](https://stalw.art/docs/management/cli/snapshot) can check config drift and strips secrets by default. One user [hit snapshot errors](https://support.stalw.art/t/611) in June.

**Restore to a fresh server:** install the binary named in `VERSION`, place `config.json`, restore `/var/lib/stalwart`, and start. Everything lives in that directory: accounts, settings, DKIM keys, ACME certificates, mail. Restoring it restores the whole server. Then move the IP or update DNS. Keep the IPv4 and IPv6 as Hetzner Primary IPs that outlive the server, so a rebuild keeps the PTR records and the IP's sending reputation.

## 4. Sizing and Hetzner types

Stalwart idles near 100 MB. The docs say 1 GB of RAM and one core suit 5 to 10 users ([requirements](https://stalw.art/docs/install/requirements)). One operator on the forum [reported a 619 MB peak](https://support.stalw.art/t/1826) over two months. The 36k-message import will cost the most CPU, because the full-text and spam pipelines run on every message, and it happens once.

The size of the mailbox on disk is not measured yet. The context gives a count but no byte total. Fastmail exposes usage through JMAP Quota ([RFC 9425](https://www.rfc-editor.org/rfc/rfc9425.html)), so read it before choosing the disk. Plan for raw mail plus index overhead (unverified, guess 1.5x), plus one full warm copy for the backup step. A 40 GB disk fits a mailbox up to about 10 GB raw. Beyond that, add a Hetzner Volume at $0.0767/GB-month.

Orderable types today (USD per month, IPv4 extra at $0.60):

| Type | vCPU / RAM / disk | US (ash, hil) | EU (fsn1, nbg1, hel1) |
|---|---|---|---|
| CPX11 | 2 / 2 GB / 40 GB | $20.49 | gone after 2025-12-31 |
| CPX21 | 3 / 4 GB / 80 GB | $37.49 | gone |
| CX23 (was CX22) | 2 / 4 GB / 40 GB | not offered | $6.49, available in hel1 only today |
| CAX11 (Arm) | 2 / 4 GB / 40 GB | not offered | $6.99, available in fsn1 only today |
| CPX12 | 1 / 2 GB / 40 GB | not offered | $13.49 |

The [15 June 2026 price adjustment](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/) roughly tripled US prices: CPX11 went from $6.99 to $20.49 and CPX21 from $13.99 to $37.49. EU prices rose less. Servers ordered before that date keep the old price, but a rescale moves them to current pricing. **The CX line and Arm are EU-only.** A "CX22-class" mail server therefore implies an EU location. In the US, the smallest type is a CPX11 at about three times the price. Either one is enough for two users. Availability also shifts week to week, so provisioning code should name a fallback type and location.

## 5. Configuration as code

This is now a first-class path ([declarative deployments](https://stalw.art/docs/configuration/declarative-deployments)). `config.json` holds only the DataStore object and can be rendered from the repo. Everything else goes in an NDJSON plan applied with [`stalwart-cli apply`](https://stalw.art/docs/management/cli/apply):

- `upsert` creates or updates objects by a natural key and never deletes anything. `reconcile` also deletes any object of that type the plan omits. `--dry-run` checks the plan offline only; there is no plan-against-live diff. Re-applying always issues updates, so "idempotent" here means the end state converges, not that an unchanged rerun is a no-op.
- Secrets in the plan are `SecretKey` values that can be `EnvironmentVariable` or `File` references ([DnsServer reference](https://stalw.art/docs/ref/object/dns-server)). The plan can therefore sit in git while values arrive as root-owned files. Certificates accept the same forms ([TLS](https://stalw.art/docs/domains/tls-certificates)).
- The documented bootstrap: template `config.json`, start once with `STALWART_RECOVERY_MODE=1` and `STALWART_RECOVERY_ADMIN` set, apply the plan against the recovery listener on 8080, then restart normally ([bootstrap mode](https://stalw.art/docs/configuration/bootstrap-mode)).
- The CLI (v1.0.13, versioned separately, with a Homebrew tap) downloads the server's schema and builds its commands from it, so it follows server upgrades.
- The DKIM keys, ACME account and certificates, spam model, and accounts live in the database, not in git. The backup carries them.

Run `apply` on the server over SSH against a loopback-only listener. Do not expose the management API.

## 6. TLS, DKIM, DNS, MTA-STS, TLS-RPT, DANE, autoconfig

- **ACME is built in**, with TLS-ALPN-01 (port 443), HTTP-01, DNS-01, and DNS-PERSIST-01. DNS challenges need automatic DNS management ([TLS](https://stalw.art/docs/domains/tls-certificates)).
- **DNS records:** each Domain exposes a generated `dnsZoneFile` covering MX, SPF, DKIM, DMARC, SRV, MTA-STS, TLS-RPT, CAA, TLSA, autoconfig, and autodiscover. Read it with `stalwart-cli get domain <id> --fields dnsZoneFile`. Automatic publishing supports Cloudflare ([DNS records](https://stalw.art/docs/domains/dns-records), [providers](https://stalw.art/docs/server/dns/provider)), but it puts a DNS-edit token on the mail server.
- **DKIM rotation** defaults to an Ed25519 key plus an RSA key, rotated every 90 days, and requires automatic DNS ([rotation](https://stalw.art/docs/domains/dkim-rotation)). The rotation bugs fixed twelve days ago in 0.16.25 included "outgoing mail is sent unsigned" and "a new key that was never published". One user [reported](https://github.com/stalwartlabs/stalwart/issues/3193) Ed25519 signatures failing at Gmail while RSA passed. That report is unverified, and DMARC needs only one aligned pass.
- **MTA-STS:** Stalwart serves the policy itself, defaulting to `testing` mode ([MTA-STS](https://stalw.art/docs/mta/transport-security/mta-sts)). Point `mta-sts.907.life` at the server as DNS-only and include it in the certificate SANs. TLS-RPT reports arrive and are parsed ([reports](https://stalw.art/docs/mta/reports/tls)).
- **DANE:** 907.life has no DS record today, so DNSSEC is off. Inbound DANE would need Cloudflare DNSSEC plus TLSA records kept in step with each certificate renewal. Stalwart does that only under automatic DNS ([0.16.0 notes](https://github.com/stalwartlabs/stalwart/releases/tag/v0.16.0)). Under manual DNS, a renewal that changes the key breaks DANE senders. Outbound DANE is checked by default when the recipient publishes TLSA records ([DANE](https://stalw.art/docs/mta/transport-security/dane)).
- **Autoconfig:** Stalwart supports PACC, Mozilla autoconfig, and Autodiscover v1 and v2 ([autoconfig](https://stalw.art/docs/server/autoconfig)). PACC and `/.well-known/caldav`, `carddav`, and `jmap` are fetched from the domain apex. The apex 907.life is the Cloudflare-proxied website, so the site or a Cloudflare redirect rule must forward those paths to the mail host.

## 7. Protocols

The [RFC list](https://stalw.art/docs/development/rfcs) covers JMAP core and Mail (RFC 8620/8621), WebSocket, Blob, Quotas, JMAP for Sieve ([RFC 9661](https://stalw.art/docs/sieve/jmap), on by default), JMAP Contacts (RFC 9610), JMAP Sharing (RFC 9670), JMAP Calendars (an IETF draft, not yet an RFC), CalDAV and CardDAV with scheduling, IMAP4rev2, ManageSieve ([RFC 5804](https://stalw.art/docs/sieve/managesieve)), and POP3. The admin surface is JMAP objects under `urn:stalwart:jmap`, so poplar and future filter tooling speak a single protocol. Vandelay ships Fastmail examples for its [CalDAV](https://stalw.art/docs/migration/import-export/import/caldav) and IMAP importers. Its [JMAP importer](https://stalw.art/docs/migration/import-export/import/jmap) names Fastmail directly.

Gaps:
- There is no webmail; it is planned after 1.0 ([roadmap](https://stalw.art/blog/roadmap/)).
- Masked email, alerts, the dashboard, telemetry history, and undelete are Enterprise-only ([alerts](https://stalw.art/docs/telemetry/alerts), [account manager](https://stalw.art/docs/management/webui/account-manager)).
- ARC sealing was removed in 0.16.0.
- Unverified reports to test before cutover: JMAP push events [never delivered](https://github.com/stalwartlabs/stalwart/issues/3169), and iOS Contacts [garbling vCard 3 names](https://github.com/stalwartlabs/stalwart/issues/3265).

## 8. Spam filter, webadmin, hardening, ports

**Spam filtering:** most rules are ported from Rspamd, with DNSBLs, Pyzor, and an FTRL logistic classifier ([spam filter](https://stalw.art/docs/spamfilter/)). Its defaults are conservative: it never rejects on score and only adds `X-Spam-Status` headers, which Sieve can act on. The classifier makes no decisions until it has 100 ham and 100 spam samples ([training](https://stalw.art/docs/spamfilter/classifier/training)). Autolearn takes ham from senders in the address book and from replies to sent threads ([autolearn](https://stalw.art/docs/spamfilter/classifier/autolearn)). Expect worse filtering than Fastmail for the first weeks. Core rules can update automatically from [stalwartlabs/spam-filter](https://github.com/stalwartlabs/spam-filter). For a pinned, boring server, apply rule updates on purpose rather than automatically.

**Auto-ban** is the built-in fail2ban ([auto-ban](https://stalw.art/docs/server/auto-ban)). Its defaults: 100 auth failures a day, 35 relay or recipient probes, 150 loitering connections, 30 scans, and instant bans for exploit URL paths. A banned client sees TLS connections close with zero bytes and no log line, as one [forum thread](https://support.stalw.art/t/1512) shows. A buggy client or a wrong password can therefore look like an outage. The runbook needs an "unban" step, and ban periods should be set (they default to indefinite).

**Webadmin and the API:** the WebUI at `/admin` downloads from GitHub's `latest` release on first start ([requirements](https://stalw.art/docs/install/requirements)), and its version floats on a 30-day cache ([applications](https://stalw.art/docs/management/applications/update)). Lock it down three ways:
- Block `/admin` from non-loopback addresses with an `allowedEndpoints` rule ([access control](https://stalw.art/docs/http/access-control)).
- Give the admin account `allowedIps` of loopback only.
- Reach the WebUI over an SSH tunnel to a listener bound to `127.0.0.1:8080`.

The docs say never to use the admin account for IMAP, JMAP, or DAV ([security](https://stalw.art/docs/install/security)).

**Ports** (Hetzner Cloud Firewall plus the listener list):
- Open: 25, 465, 993, 443, and 22 (keys only).
- Open 587 only if a client needs STARTTLS, and 80 only for the legacy `http://autoconfig` lookup.
- Close or remove: 143, 110, 995, 4190 (JMAP for Sieve replaces ManageSieve), and public 8080.

Outbound 25 needs Hetzner's limit request. Hetzner enforces that block per account, and the request can be filed after one month and a paid invoice ([Hetzner FAQ](https://docs.hetzner.com/cloud/servers/faq/)).

## 9. Monitoring for a household

The Community edition has no alerting, so monitor from outside and keep alerts few and real:
1. **Liveness:** an external check of `https://<mailhost>/healthz/live` ([HTTP endpoints](https://stalw.art/docs/http/)), TCP connects to 25, 465, and 993, and certificate expiry.
2. **End-to-end flow:** a daily job queries JMAP for a DMARC aggregate report from Google or Microsoft in the last 48 hours, which proves inbound delivery works. The same reports show whether outbound DKIM and SPF pass. On success it pings a dead-man's switch such as [healthchecks.io](https://healthchecks.io/docs/configuring_notifications/), which alerts by Pushover or SMS. The alert must never go by email, because email is the thing that broke.
3. **Server state:** disk free, `systemctl is-active stalwart`, queue size via the CLI, and the backup timestamp. The Prometheus endpoint `/metrics/prometheus` is available in Community.
4. **Ad hoc:** the WebUI's delivery troubleshooter ([troubleshoot](https://stalw.art/docs/management/troubleshoot)).

Per the calm-desktop rule, only "mail not flowing" and "backup stale" should page.

## 10. Known pitfalls from 2026 operators

- **A Debian MTA package stops Stalwart for good.** The unit has `Conflicts=postfix.service sendmail.service exim4.service` and `Restart=on-failure`. When apt pulls in exim4, Stalwart stops cleanly and never restarts. Staff [diagnosed this](https://support.stalw.art/t/1826) on 2026-10-01. Fix: pin `exim4*`, `postfix`, and `sendmail*` to priority -1 in apt preferences, and use `Restart=always`.
- **Silent corruption.** One 0.16 user [reported](https://support.stalw.art/t/859) RocksDB "Merge operator failed" errors, and later a store that kept syncing but quietly dropped mail. Every one of that user's backups already held the fault. The root cause is unconfirmed. The defense is retention depth, the logical Vandelay layer, and the end-to-end probe.
- **Mail accepted but lost or invisible.** Reports include [Sieve dropping mail](https://github.com/stalwartlabs/stalwart/issues/3207) after a failed activation and [messages never indexed](https://github.com/stalwartlabs/stalwart/issues/3217) after a burst of large mail. Both were auto-closed for triage and are unverified. Test Sieve changes on a probe account first.
- **Bug intake moved.** GitHub issues are auto-closed and sent to [support.stalw.art](https://support.stalw.art). The real bug status lives there and in the CHANGELOG.
- **Trash and Junk expire after 30 days** by default ([maintenance](https://stalw.art/docs/email/settings/maintenance)). Imported old Trash and Junk will vanish on the first nightly run unless `expungeTrashAfter` is set before the import. Whether "older" counts from the received date or the move date is unverified.
- **Fixed bugs to stay past:** RocksDB disk never freed on delete (fixed in 0.16.10), RocksDB LOG growing without limit (0.16.25), DNSSEC failures on some MX lookups ([report](https://support.stalw.art/t/1772); patched resolver in 0.16.26).
- **Recovery mode** (`STALWART_RECOVERY_MODE=1`) is the documented way back in when listeners or the admin login fail ([recovery mode](https://stalw.art/docs/configuration/recovery-mode)). It belongs in the second operator's emergency section.

## Recommendation

1. **Version:** build and rehearse on the newest 0.16.x. If 1.0 ships before cutover, cut over on 1.0.1 or later. Otherwise cut over on 0.16.x and treat the move to 1.0 as one planned upgrade with a stopped backup taken first. Pin the exact version in `VERSION`. Upgrade deliberately, roughly monthly or when a fix matters, after reading the CHANGELOG.
2. **Install:** pinned native binary with a verified hash or attestation, a repo-owned unit with `Restart=always`, apt pins against any other MTA, and Debian 13 from Hetzner's `debian-13` image.
3. **Storage:** RocksDB for every store on local disk. Back up by warm rsync, stop, delta rsync, start, then a pavilion pull. Add Vandelay per-account archives as a second layer. Restore drills cover both layers.
4. **Config:** `config.json` and an NDJSON `upsert` plan in the `servers` repo, applied on the host through `stalwart-cli` against a loopback listener. Secrets go in as `File` references.
5. **DNS:** manual management at launch. A repo script publishes Stalwart's `dnsZoneFile` records through the Cloudflare API, keeping one writer for the zone and no DNS token on the mail host. Manual DKIM: keep the generated keys and rotate them yearly by hand. MTA-STS in `testing`, then `enforce` once TLS-RPT is clean. Set up TLS-RPT and raise DMARC from `p=none` once alignment is clean. Skip DANE at launch, and revisit it with automatic DNS after 1.0.
6. **Exposure:** open only the ports in section 8, restrict `/admin` and the admin account to loopback, and set auto-ban periods.
7. **Size:** CX23 (4 GB) in hel1 if an EU location is acceptable; otherwise CPX11 (2 GB) in hil. Either is enough. Measure the mailbox size first, and keep the IPs as Primary IPs.

## Risks

- **Churn.** A weekly patch train is still fixing data-path bugs, and 1.0 brings a schema decision. Mitigations: pin the version, upgrade only with a stopped backup taken first, and test on a scratch server.
- **A single backup copy** on one USB drive, for the system that is the account-recovery root (Geoff's ruling, restated in the backups brief).
- **Silent failure modes:** auto-ban lockouts, apt conflicts, and accepted-then-lost mail. Only the end-to-end probe catches the last of these.
- **Spam filtering** will be weaker than Fastmail's while the classifier trains.
- **Hetzner IP reputation** and the outbound-25 approval are outside Stalwart's control. Hetzner decides the unblock case by case.
- **Vendor concentration.** One company writes the server, the CLI, the backup tool, and the migration tool.
