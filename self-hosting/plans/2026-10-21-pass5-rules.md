# Pass 5 (ward): permission rules

The narrow allow and deny rules Pass 5 needs, for a workstation PR on branch `self-hosting-pass5-rules` in the plan sitting. The planner wrote them here because the auto mode classifier refused its own edit of the settings source as self-modification (2026-10-21 about 06:00 UTC). The rules come in two halves, because the workstation's auto mode text admits an edit to `permissions.allow` "when Geoff asked for that rule in the session", and excludes "a deny or ask rule change". So the conductor lands the allow half on Geoff's ask, and Geoff types the deny half himself in the same worktree before the PR opens. If the classifier refuses any part of the allow edit, or of `claude-tooling-sync apply` after the merge, Geoff makes that part by hand in the sitting.

## Why each rule exists

On 2026-10-21 at 04:01 UTC the classifier denied Pass 3's `cd .../photos; bash cloudflare/r2.sh --apply 2>&1 | tail -15; ...` (servers#7, `## Stop`). The allow rule `Bash(cloudflare/r2.sh --apply)` was in place, but a Bash rule "matches the command text Claude writes, after Claude Code splits compound commands and strips wrappers. It doesn't match the same program invoked in a different form" (<https://code.claude.com/docs/en/permissions>, "What a Bash rule doesn't match"), and `bash` is not one of the stripped wrappers ("`timeout`, `time`, `nice`, `nohup`, and `stdbuf`, plus the shell builtins `command` and `builtin`"). So the classifier decided the call. The fix is the exact form: the executor prompt writes each live command in full, one live script per Bash call. No rule takes a `bash <script>` form. The workstation's auto mode text forbids "a wildcarded interpreter", the permission-modes docs say a broad rule granting arbitrary code execution is dropped on entering auto mode, and the form is one the prompt forbids anyway. `scripts/dry-run.sh` was the one script that needed it, so L1 makes that file executable.

## The deny half (Geoff types it)

In the same file and the same worktree, append to `permissions.deny` after the last `npx wrangler` rule:

```json
"Bash(vandelay * --prune)",
"Bash(vandelay * --prune *)",
"Bash(imapsync)",
"Bash(imapsync *)"
```

Deny rules win over allow rules ("Rules are evaluated in order: deny, then ask, then allow"). No allow rule names raw `vandelay` now, so the `--prune` denials guard a hand-typed call and any later rule. The `curl` rules put the URL first because "Claude Code matches everything before the first `*` as written", and a rule with a `*` before the rest of the command draws a startup warning.

## The proof

After the PR merges and `claude-tooling-sync apply` runs, the conductor proves the rules with `claude -p --permission-mode dontAsk --output-format json`, where anything a rule doesn't allow is refused and the classifier plays no part. It runs from a scratch directory under its job's `tmp` that holds stub scripts at each rule's path (`scripts/dry-run.sh`, `scripts/archive.sh`, `scripts/imap-sweep.sh`, `scripts/vandelay-run.sh`, `scripts/rcpt-check.sh`, and `cloudflare/access.sh`, each mode 755) and a stub directory first on `PATH` for `brew`, `vandelay`, `curl`, and `imapsync`. Every stub appends its argv to one log file and exits 0, so nothing reaches an account. The session is told to run each form below once, as written.

These forms are meant to run, and each must appear in the log:

- `scripts/dry-run.sh hcloud`
- `cloudflare/access.sh --token ward`
- `scripts/archive.sh --prefix vandelay proof.sqlite`
- `scripts/imap-sweep.sh rehearse 2026-10-20`
- `scripts/imap-sweep.sh rehearse-clean`
- `scripts/vandelay-run.sh inspect proof.sqlite`
- `scripts/rcpt-check.sh ward.907.life proof.txt`
- `brew install stalwartlabs/tap/vandelay`
- `curl --url smtps://smtp.gmail.com:465 -K proof.curl`
- `curl --url smtps://ward.907.life:465 -K proof.curl`
- `curl --url smtp://ward.907.life:25 -K proof.curl`
- `curl --url imaps://imap.gmail.com:993 -K proof.curl`
