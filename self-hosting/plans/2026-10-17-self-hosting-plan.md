Option (c), restoring to a new server and promoting it, reduces to (a), because the design keeps replacing a server that still exists with Geoff. ## Secrets in the age store

The workstation's main checkout stays on `main` with a clean `secrets/values.age`, so `git pull --ff-only` always works there and every launch's `rev-list --count HEAD..origin/main` check can pass. A pass never stores a secret into it. Instead:

- **Where a secret is written.** Every secret a pass creates goes into that pass's own workstation worktree and that pass's own plaintext overlay. The session runs `secret-set.sh` and `secret-receive` with `--values <the worktree's secrets/values.age>` and `--local $XDG_RUNTIME_DIR/self-hosting/secrets-<pass>`, the flags 0.10 adds over the overrides the script already honors ("Each path can be overridden from the environment, so a test or a worktree edit can point the script at a scratch store without touching the live one"). So `~/.local/secrets` is written only from `main` (by `sync.sh --local` after a merge, or a store into the main checkout), and never loses a name that is live there. Today each store rewrites the whole file from the one store it read, so the last writer wins across stores (second verification read, N1, probed).
- **How a pass reads its names.** The servers repo's loader `scripts/lib/secrets.sh`, used by `render.sh`, `deploy.sh`, and `dry-run.sh`, sources every overlay under `$XDG_RUNTIME_DIR/self-hosting/` and then `~/.local/secrets`, so `main`'s value wins for a name both hold and an overlay supplies only the names not yet merged. A pass removes its overlay once its PR has merged and `sync.sh --local` has run. Pass 0 is the one exception: until 0.10 lands the flags it sets `VALUES` alone, with Geoff present, and 0.10 merges the same day.
- **When it is committed.** The session commits `values.age` and the workstation `secrets/registry.md` after each store, pushes, and opens the workstation PR as a draft at the first push. The PR merges in that pass's packet. A credential Geoff hands over in an attended sitting, like the members' late Fastmail credentials, goes into a short-lived worktree whose PR he merges in the same sitting, as workstation PR #81 was.
- **The order before `restic init`.** For each restic password, and each token a server can't be rebuilt without (the R2 write token, the heartbeat token, the tunnel token): generate it on the workstation, store it as above, decrypt it back and compare hashes, commit and push, and confirm the pushed blob decrypts to the same hash.
- **When a lock may make it irreplaceable.** A bucket's lock rules land only once that bucket's restic password is on `origin/main`, checked by content, not ancestry, since the workstation repo allows squash and rebase merges: after a fetch, decrypt `origin/main:secrets/values.age` to `/dev/shm` under a trap and compare the password's hash with the pass's record. So orpheus's lock (bucket `servers-backup-orpheus`) is the first step of I1, after Pass 2's packet merges, and ward's (`servers-backup-ward`) is the first step of C1, after Pass 5's. Both still meet the design's timing: "after `restic init` and the first verified backup on the media server, and after the last rehearsal import on the mail server, before cutover". Until then the buckets hold rehearsal backups only, with PikaPods and Fastmail still in production. The drills don't need the lock.
- **A conflict in `values.age`.** git can only pick a whole side of a binary file, and a wrong pick drops entries. The closing session handles it before it sends the packet, since the conflict would otherwise surface at Geoff's merge after the executor has gone: it fetches and test-merges `origin/main`; on a `values.age` conflict it decrypts the branch store to `/dev/shm` under a trap (`secret-set.sh` shreds its own copy on exit), takes `origin/main`'s file in a merge commit, never a rebase, re-stores each of the branch's own names, and checks every name's hash. A branch carrying `values.age` is never force-pushed.
- **The main checkout's store stays clean.** A bare `secret-receive NAME` still writes the main checkout's store by default, so the conductor's pre-launch checks and every pass's close run `git -C ~/.dotfiles diff --quiet -- secrets/values.age`; a dirty store stops the launch, and its names move into a worktree branch.
- **The two registries.** The workstation's `secrets/registry.md` lists every name in the store, as the store's own documentation asks. The servers repo's `secrets/registry.md` lists which server or script reads each name.

## Dispatch note

Every pair dispatch carries the two samples `pass-core` "Lifecycle" step 1 quotes, verbatim, and anything beyond a task goes to its PR's "Found, not done" list, filed through `log-issue`. Pair arms are `general-purpose` subagents at `model: sonnet`, effort `medium`, with `description` `<pass> task <id>`, `isolation: "worktree"`, and the setup command first. An arm never touches a live account: provisioning, `--apply`, DNS writes, and token use run in the main loop only. An arm's Bash starts from the user profile, so the live tokens are in its environment, and shell state doesn't carry between Bash calls; the isolation therefore lives in the test harness (above), not in the setup command.
