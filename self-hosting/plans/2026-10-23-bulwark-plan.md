# Bulwark webmail: plan

## Brief

This plan builds the approved design `self-hosting/specs/2026-10-21-bulwark-design.md` (initiatives#114, `38d5b27`): Bulwark on orpheus at `webmail.907.life`, signing in to ward, themed by Survey's theme-limited recipe, with its upkeep and upgrades in the runbook. One servers branch and one workstation branch, whose PRs come back to Geoff in one packet through `conductor-servers`. The planned path is 440 minutes against the design's 300, under the 600-minute line where the standing answer applies. Two rulings below need Geoff at plan approval; nothing else needs him before launch. The three plan reviews and their fold (`self-hosting/research/2026-10-23-bulwark-plan-review-fold.md`) rebuilt the theme's output form, the live checks, and the back-out.

Eight facts found at planning or review correct the design's mechanisms without changing its outcome, and each goes in the servers PR's `## Decisions` and `docs/decisions.md`:

1. **CORS.** Stalwart has no per-origin CORS. Its one switch, `Http.usePermissiveCors`, sends `Access-Control-Allow-Origin: *` with the fixed allow-headers `Authorization, Content-Type, Accept, X-Requested-With`, a method list, and no `Access-Control-Allow-Credentials` (Stalwart v0.16.27, `crates/common/src/config/network.rs:404-427`). Ward sends no CORS header today: preflights from `https://webmail.907.life` to `/jmap/session` and `/.well-known/jmap` answered 204 with none (probed 2026-10-23). Bulwark's browser code calls the JMAP server directly (`lib/jmap/client.ts:1397`), so the switch must go on. The Fetch standard does not expose a response to a credentialed request when the allowed origin is `*`, and a request carrying `Authorization` stops at its preflight unless that header is allowed, so another site cannot read ward's answers with a visitor's credentials. What the switch does open is ruling 2: any page can now send wrong passwords to ward from a household member's browser.
2. **Auto-ban.** Bulwark's sign-in routes check each password from orpheus (`app/api/auth/session/route.ts:154`, `resolveJmapIdentity`), so the ban risk the design names is real. Stalwart's forwarded-header trust is global: with `Http.useXForwarded` on, it reads `Forwarded` and `X-Forwarded-For` from every connection (`crates/http/src/request.rs:749-775`), so turning it on would let any client choose its own address. The plan instead adds Stalwart `AllowedIp` objects for orpheus's IPv4 and IPv6 addresses. An allowed address skips the per-address and the per-login failure count (`is_auth_fail2banned`, `crates/common/src/network/security.rs:298-309`), the recipient, scanner, and loiter bans (`:218-290`), and the authenticated HTTP rate limit (`crates/common/src/auth/rate_limit.rs:22`), for every process on orpheus. This is ruling 1.
3. **The throttle.** Stock Caddy has no rate limiter (that is the third-party `caddy-ratelimit` module), so the design's Caddy throttle is not built. Bulwark budgets sign-in failures per client address: 5 per 15 minutes, with no global ceiling (`lib/auth/verify-budget.ts:16-17, 113-121`), keyed on the address Caddy forwards, so Bulwark trusts exactly one proxy hop (`TRUSTED_PROXY_DEPTH`, default 1, `lib/admin/session.ts:166`). Under ruling 1 it is the only failure limit on the webmail path. Stalwart's own floor on a new password stays at its default, zxcvbn score 3 and 8 characters (`crates/registry/src/schema/structs_impl.rs:3428-3430`).
4. **The record type.** `webmail` is a CNAME to `orpheus.907.life`, like `dav` (`cloudflare/dns/orpheus`), in place of the design's A and AAAA pair.
5. **The secret's owner.** The design says "a root-only file"; the container runs as uid 1001, `nextjs` (Bulwark `Dockerfile:51, 56`), so the file is 0400 owned by uid 1001. On the host, uid 1001 is the next free account id (`roles/cloudflared/operators.sh:70` creates operators with a bare `useradd`), so the role reserves it as a system user `bulwark` before any operator can take it.
6. **The theme's form.** Bulwark reads an installed theme from three files in its config directory: `themes/registry.json`, `themes/<id>.css` holding compiled `:root` and `.dark` variables, and `themes/<id>.skin.css` (`lib/admin/plugin-registry.ts:358-366, 457-494`). A `manifest.json` is read only from a ZIP uploaded through the admin API, which is off, so the build writes the installed form directly.
7. **Survey's second accent and the mark.** Survey's `--color-secondary` and `--color-accent` have no accent hook in Bulwark: Bulwark's `secondary` and `accent` are shadcn's quiet grounds, and its `chart-1` to `chart-5` are defined but drawn by no component (`app/globals.css:71-75`; no `components/` or `app/` file uses them). So they go under the design's standing answer for a hook that cannot take a Survey value, and into the drafted upstream issue. The marks take Survey's own color for the benchmark triangle, `--site-contour` (`theme/components.css:68-73`).
8. **Outbound defaults.** The design keeps telemetry and settings sync off. Two more defaults leave the estate, and the plan closes them in the same posture: the hourly update check to `version.telemetry.bulwarkmail.org` (`instrumentation.node.ts:66-71`) goes off, since the monthly review carries upgrades, and `/api/translate`, which sends message text to the public MyMemory API (`.env.example:455-461`), answers 404 at Caddy. Web push stays, since it registers only after a member grants the browser's permission (`components/push-notification-prompt.tsx:294`). Bulwark also remembers every sign-in for 30 days, with the mailbox password encrypted inside the cookie, unless the sign-in page offers a box (`.env.example:342-344`, `lib/auth/session-cookie.ts:2`), so the page offers it, unticked (`app/(main)/[locale]/login/page.tsx:204`).

The advisory watch the design names (Pass 6's C6) is not built yet. This plan amends C6's line in the base plan to watch `bulwarkmail/webmail` too, and T9 adds it to the watch list if C6 has merged first.

## Rulings needed

Each is a yes-or-no question for the plan's packet. The tasks build the recommended answer; the other answer is the one named edit.

1. **Keep the orpheus allowlist, with Bulwark's per-address budget as the webmail path's only failure limit?** Recommended: yes. Without it, about 100 wrong passwords a day through webmail, from any mix of clients, ban orpheus for 24 hours (Stalwart's default `authBanRate`, `structs_impl.rs:35589-35592`; `authBanPeriod` 86400000 in `roles/stalwart/plan.ndjson:6`), which takes webmail away from both users and blocks orpheus's own submission on port 587; Bulwark's budget has no global ceiling to stop that (fact 3). With it, a guesser spread over many addresses gets 5 tries per address per 15 minutes against any mailbox, the admin account included, with no account-level stop, and every service on orpheus inherits ban-free access to ward. The mailbox passwords are generated (base plan L3) and the admin password is 32 random characters, so the recommendation rests on them; T9 amends `docs/decisions.md:109`, which says the auto-ban covers the admin account, and records the residual risk. Yes builds T4's `AllowedIp` line and T7's address check. No drops T4's `AllowedIp` line, its test, and T7 step 9, and the runbook's unban step then covers orpheus.
2. **Accept that the CORS switch lets any web page a household member opens spend that member's address's ban allowance?** Recommended: yes. After the switch, a hostile page can send wrong-password JMAP requests from the member's browser, and 100 a day ban that address for 24 hours on every protocol, locking out every device behind it (risk review R3; the review found no path that does this today). It needs a page aimed at this household, and the unban is on the emergency screens. Yes records it beside fact 1 and adds this cause to the runbook's "Unban a client from Stalwart's auto-ban". No also sets `authBanPeriod` to 3600000 (one hour) in `roles/stalwart/plan.ndjson:6` in T4, which shortens the ban for every client, attackers included.
