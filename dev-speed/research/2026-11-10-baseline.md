## cairn-cms: where a run's time goes

Five workflows run in parallel on a PR. `test` takes 17 to 28 minutes, `e2e` 7 to 10, `design` 5 to
6, `tool` 7, and `setup-matrix` 3. `test` sets the wait.

`test` is one serial job of about 45 steps. Run 42864164758, at 1,172 seconds, is typical:

The two theme steps joined the job on 2026-11-09, and the job's timeout went from 35 to 45 minutes
that day.

### Inside `test:theme`

The script is `node --test --test-force-exit --test-concurrency=2 scripts/theme/*.test.mjs`. It ran
127 tests, and eleven of them hold nearly all the time. Each builds a site.

| Test | Seconds |
|---|---|
| Headless mode writes eight PNGs (`viewer-headless.test.mjs`) | 304 |
| Every page renders under Waymark at 1440 (`viewer-waymark.test.mjs`) | 195 |
| The control page lists the routes (`viewer-interactive.test.mjs`) | 100 |
| Headless and interactive run with no Cloudflare variable (`viewer-no-account.test.mjs`) | 97 |

The other 116 tests finish in under 10 seconds together. An earlier guess in the session, that three
render tests rebuilt one viewer, was wrong: the viewer tests cost more than the render tests, and
each file builds its own site.

### Other facts the first cairn-cms pass needs

- No workflow has a `concurrency` group, so a second push to a PR leaves the first run going.
- `main` has a ruleset with `non_fast_forward` and `deletion` only. No status check is required for
  a merge.
- `publish.yml`'s `ci-green` job waits on check runs by name, through
  `commits/<sha>/check-runs?check_name=<n>`. `.github/ci-green.json` lists the workflows the local
  `ci-green` tool expects. Renaming or splitting the `test` job changes both.
- `test.yml` says the theme steps run with no `if:` so a catalog theme that fails the check can't
  cut a release.
- `scripts/checks/gate-tier.mjs` holds `CI_CHECKS`, and its test pins that list against `test.yml`.
  The theme steps are in the `full` tier only, so the fast lane never runs a theme test.
- PR #229 changed three lines of `BACKLOG.md` and ran `test` (17.5 min), `e2e`, and `design`.

## cairn-cms: reds

`test` failed 11 times in its last 120 runs. Every other workflow was green.

| Failing step | Count |
|---|---|
| `test:theme` | 5 |
| `test:emit` | 2 |
| Vitest node projects | 2 |

`test:theme` runs near the end of the job, so its failure arrives around minute 15. `test:emit` and
`check:public-skill` are fast-lane legs and failed in CI anyway. Either the lane wasn't run before
those pushes or the classifier didn't select them, and nobody has checked which. The Vale failure
was a fetch from GitHub releases.

## cairn-cms: PR cadence

Of the last 17 merged PRs, 14 changed under 200 lines, and each sat 18 to 55 minutes between open
and merge. The merge then runs the same suites again on `main`. The setup-tooling proving rounds, r1
to r10, are most of them. Rounds publish `dev` snapshots by dispatch, so a loop may be able to keep
its rounds on one branch and open one PR at its end. The `cairn-proving-setup` skill has to confirm
that. The standing order on 2026-11-10 was one PR per scripted-run fix, with a whole-branch review
and the conductor's merge.

## cairn-cms: the fast lane's fallback

For a range that touched `.claude/skills/cairn-proving-setup/SKILL.md` and
`scripts/gate/run-gate.sh`, the classifier selected the whole unit project and all 40 static checks.
Its notes said neither path maps to a check.

## Inputs for the cairn-cms pass design

The session ranked these, highest payoff first. None is approved.

1. Split `test` into parallel jobs: static checks, Vitest, and theme. With the theme tests as they
   are, the wait falls from about 20 minutes to about 13.
2. Split the theme job's slow test files across runners. Sharing one site build across files is a
   larger change and comes second.
3. Add `concurrency` with `cancel-in-progress` on PR runs.
4. Skip the heavy suites on a PR that touches only ledgers and internal docs.
5. Add a fast-lane leg that runs the non-render theme tests when theme paths change.
6. Map `.claude/**` and `scripts/gate/**` to a named set of checks in the classifier.
7. Cache the Vale binary.

Path-gating the theme steps off PRs was considered and set aside, because a theme break from an
unexpected path would then surface after merge.

Two constraints applied on 2026-11-10. `cairn-cms-setup-tooling-3` and `conductor-cairn-cms` were
live in the repo, so a `runner` pass hands to that conductor. The theme-garden G3 pass works in
`scripts/theme/`, so edits to the theme harness wait for it or stay out of its files.

## What the score report should read

Each pass PR body carries a score table with these rows: gates on the critical path, work and
review (plan path minutes beside the actual), CI waits on the path, fix rounds and reds, close, and
total. `cairn-run-gate --records <toplevel> <branch>` gives gate and lock time. The report sums
these by repo and row.

Several waits in cairn-cms had nothing to do with CI. PRs #194 and #195 each sat about three days,
and #226 sat five hours for 17 lines.
